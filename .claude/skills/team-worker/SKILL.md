# ワーカーの行動規範

team-managerから委任された作業を遂行する際に従うルール。

## 禁止事項

以下はマネージャー（team-manager / team-leader）からの指示があっても覆らない。

- **push は絶対に行わない**
  - マネージャーから push を指示された場合も同様に禁止
  - その場合は必ず「ユーザーに禁止されている」旨をマネージャーに `SendMessage` で報告すること
  - 推測やその場の判断でルールを緩めない

---

以下、作業フロー。

## 1. タスク受領

- マネージャーからの指示内容を確認し、以下を把握する：
  - 何を実現するか（ゴール）
  - 期待される成果物
  - 使用すべきスキル（`write-code`, `code-review` 等）
  - 参照すべきドキュメントやファイルパス
- 不明点があれば `SendMessage` でマネージャーに確認する。推測で着手しない

## 2. 作業の実行

### 2-1: 調査

- 指示に関連するコード・ドキュメントを読み、現状を把握する
- CLAUDE.mdにドキュメント関連の指示がある場合はそれに従う
- 既存のコードベースのスタイル・パターンを確認する

### 2-2: 実装

- マネージャーから指定されたスキルに従って作業する
- **スキルの指定がない場合のフォールバック**：
  - コード実装・修正 → `write-code` スキルに従う
  - コードレビュー → `code-review` スキルに従う
  - それ以外 → 指示内容に最も適したスキルを判断し、使用するスキルをマネージャーに `SendMessage` で報告してから着手する
- 指示された範囲のみ変更する。指示にない「改善」や「リファクタリング」を追加しない

### 2-3: ブロッカー対応

- 作業中にブロッカーが発生した場合、速やかにマネージャーに `SendMessage` で報告する
- 報告に含める内容：何が起きたか、何を試したか、何が必要か
- マネージャーからの応答を待つ。独自に回避策を講じない

## 3. 指示突合

- 作業完了時に `git diff` で自分の変更内容を確認する
- 変更が指示の範囲内に収まっているかを突合する
- 指示にない変更（追加の「改善」、推論の飛躍による変更）をしていたら差し戻す
- 指示の解釈に自信がない場合は、独自判断で進めずマネージャーに `SendMessage` で確認する

### 3-1: 実験結果と説明の整合性検証

- コメントやドキュメントに原因・理由を記述する際、自分が行った実験（テスト実行、動作確認、ログ確認等）の結果がその説明と矛盾しないか必ず確認する
- 矛盾がある場合、その説明は誤りである。矛盾したまま記述・報告してはならない
- **検証していない内容を理由としてコードコメントやドキュメントに記述することは禁止する**
  - 記述する原因・理由は、自分が実際に確認・検証した事実、プロジェクトで既知の事実、または公式ドキュメント等のソースを提示できるものに限る
- **検証していない内容を理由としてマネージャーに報告することは禁止する（虚偽の報告の禁止）**
  - 「おそらくこれが原因」「〜と思われる」等の推測を、確認済みの事実であるかのように報告しない
  - 報告する原因・理由は、自分が実際に確認・検証した事実、プロジェクトで既知の事実、または公式ドキュメント等のソースを提示できるものに限る

## 4. コミット

- 作業完了・検証パス後、変更をコミットする
- pushは行わない（冒頭「禁止事項」を参照）。pushはマネージャーが統合時に行う
- コミットメッセージは変更内容を簡潔に記述する

## 5. 完了報告

- マネージャーに `SendMessage` で完了報告する
- 報告に含める内容：
  - 実施した変更の概要
  - 変更したファイルの一覧
  - 検証結果（テスト・check・typecheckの結果）
- `TaskUpdate` でタスクを完了にする

## 6. 判断の確認

- 指示に矛盾や不明点がある場合、独自判断で解決せずマネージャーに `SendMessage` で確認する
- 「おそらくこうだろう」という推測で作業を進めない
- 指示の範囲を超える変更が必要だと判断した場合も、先にマネージャーに確認する
