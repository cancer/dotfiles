仕様ないし仕様書をレビューする。

## 引数
$ARGUMENTS

## 引数の形式

以下のいずれかの形式で受け付ける：

1. **ファイルパス**: プロジェクト内の仕様書ファイル
2. **GitHub issue/PR URL**: `https://github.com/owner/repo/issues/123` など
3. **issue番号**: `#123` または `123`（現在のリポジトリのissueとして扱う）
4. **自由記述**: 仕様の説明テキスト

## 実行手順

### Step 1: 仕様の読み込み

引数の形式に応じて仕様を取得する。

**ファイルパスの場合:**
指定されたファイルを読み込む。

**GitHub issue/PRの場合:**
```bash
gh issue view <number> --repo <owner/repo> --json number,title,body,labels,comments
```
または
```bash
gh pr view <number> --repo <owner/repo> --json number,title,body,labels,comments
```
コメント欄にも補足や追加要件がないか確認する。

**自由記述の場合:**
そのまま仕様として扱う。

### Step 2: 関連情報の収集

仕様の内容に応じて、以下を必要に応じて調査する：

- 仕様が言及しているコードベース上の既存実装
- 関連する他の仕様書・ADR・ドキュメント
- 仕様が前提としている外部仕様やAPI

### Step 3: レビュー

以下の観点についてチェックする。

**完全性**
- 目的・背景が明記されているか
- 対象スコープ（何を含み、何を含まないか）が明確か
- 正常系のフローが網羅されているか
- 異常系・エッジケースが考慮されているか（エラー時の振る舞い、境界値、空・null・未定義の扱い）
- 非機能要件（パフォーマンス、セキュリティ、アクセシビリティなど）への言及が必要に応じてあるか
- 用語の定義が必要な箇所で定義されているか

**明確性**
- 曖昧な表現がないか（「適切に」「必要に応じて」「など」が具体的な基準なしに使われていないか）
- 複数の解釈が可能な記述がないか
- 具体例やサンプルが、理解を助けるために十分に示されているか
- 条件分岐の網羅性 — すべての条件の組み合わせについて振る舞いが定義されているか

**一貫性**
- 仕様内で矛盾する記述がないか
- 用語が統一されているか（同じ概念に異なる名前を使っていないか）
- 既存の仕様・システムの振る舞いと矛盾しないか

**実現可能性**
- 技術的に実装可能か
- 既存のアーキテクチャ・技術スタックとの整合性があるか
- 依存する外部システム・APIが利用可能か
- 暗黙の前提条件が存在しないか

**テスト可能性**
- 各要件が検証可能な形で記述されているか（合格基準が明確か）
- テスト困難な要件がないか
- 受け入れ条件が定義されているか

**仕様と実装の分離**
- 実装詳細（具体的なクラス設計、関数シグネチャ、変数名・カラム名・テーブル名、データ構造の内部表現、アルゴリズムの実装手順、特定のストレージ技術・ミドルウェア・インフラ構成要素への言及など）が仕様に混入していないか
- 「何を実現するか（What）」ではなく「どう実装するか（How）」の記述になっている箇所がないか
- 技術的制約として必要な記述と、不必要に実装を縛る記述を区別できているか

## 出力形式

各観点について以下の形式で報告する：

### [観点名]

| # | 箇所 | 指摘 | 重要度 |
|---|------|------|--------|
| 1 | 該当箇所の引用または参照 | 具体的な指摘内容 | high/medium/low |

- **high**: 仕様として成立しない、または実装時に重大な問題を引き起こす
- **medium**: 解釈の揺れや考慮漏れがあり、実装者によって結果が変わりうる
- **low**: 改善が望ましいが、現状でも実装は可能

指摘がない観点は省略してよい。

## 完了前チェックリスト

レポートを返す前に確認する。

- [ ] 6観点すべて（完全性・明確性・一貫性・実現可能性・テスト可能性・仕様と実装の分離）を通した
- [ ] 各指摘に該当箇所の引用/参照と重要度を付けた
- [ ] 関連する既存実装・仕様・外部仕様を必要な範囲で確認した
