# ユーザー判断傾向の分析

直近のセッションログを分析し、ユーザーの技術的判断の傾向を抽出する。

## 目的

ユーザー固有の判断基準を学習し、code-review や review-respond がユーザーと同じ判断を再現できるようにする。

## 引数
$ARGUMENTS

引数のパース:
- 第1引数: 期間指定（`7d`, `3d`, `2w` 等）。省略時は `7d`
- 第2引数: プロジェクトパス。省略時は現在のプロジェクト
- `--model <name>`: 分析を実行するモデル。未指定なら `haiku`

## モデルルーティング

`--model` の値に応じて、分析処理を以下の委譲先に振り分ける。

| `--model` 値 | 委譲先 | 備考 |
|---|---|---|
| `haiku` （デフォルト） | このskill自身で実行 | フロントマターの `model: haiku` で動作 |
| `sonnet` / `opus` | `Agent` ツール（`subagent_type: "general-purpose"`、`model: <指定>`） | Claudeの別モデルに委譲 |
| `gpt` / `gpt-*` | `Skill("codex:rescue", args: ...)` | 素の `gpt` ならモデル指定なし、`gpt-*` なら argsに `--model <name>` を含める |
| `co-opus` | Bashで `copilot --model claude-opus-4.6 -p "<プロンプト>" --yolo` | |
| `co-gpt-*` | Bashで `copilot --model gpt-* -p "<プロンプト>" --yolo`（`co-` を除いたモデル名を渡す） | |

未知のモデル名が指定された場合は実行せず、サポート対象を提示して終了する。

## 分析対象の限定

**以下の2種類のみを分析対象とする。それ以外は除外する。**

### 1. ユーザーが自ら判断を下したケース

AIの提案を待たずに、ユーザーが方針・結論・選択を先に示した場面。ここにユーザー固有の判断基準が最も純粋に現れる。

例:
- 「ここはXではなくYでいく」
- 「この設計は〜の理由でだめ」
- 「優先度はA > B」

### 2. AIの提案を却下・修正したケース（とその結果）

AIの判断とユーザーの判断がずれた場面。何がどうずれ、ユーザーがどう修正したかに、AIのデフォルトでは再現できない判断基準が現れる。

例:
- AIがリファクタを提案 → ユーザーが「今はやらない」と却下
- AIが設計Aを提案 → ユーザーが設計Bに修正
- AIの指摘に対してユーザーが「それは問題ではない」と判断

### 除外するもの

- **AIの提案をそのまま承認したケース** — 「異議なし」はユーザーの判断基準の証拠にはならない。AIの判断傾向が混入する。

## 分析の単位

**判断の結果だけでなく、判断に至るまでの会話の流れを分析する。**

各判断イベントについて以下を抽出する:

1. **文脈**: 判断の直前にどんな情報が提示されていたか（コード、diff、エラー、選択肢など）
2. **判断の過程**: ユーザーがどういう観点・言葉で判断を述べたか。何を重視し、何を軽視したか
3. **AIとのずれ**（却下・修正の場合）: AIがどういう根拠で何を提案し、ユーザーがどこに異議を唱えたか
4. **結果**: その判断がどういう結果につながったか（わかる範囲で）

## 実行手順

### Step 0: 委譲先の決定

上記「モデルルーティング」に従って委譲先を決定する。デフォルト（haiku）の場合はskill自身で以降のStepを実行する。それ以外の委譲先の場合は、以降のStep 1〜5の内容をタスクプロンプトとしてまとめ、委譲先に渡す。

### Step 1: セッションログファイルの収集

全プロジェクトのセッションログを横断的に収集する（判断傾向はユーザー個人の特性であり、プロジェクト固有ではないため）。

1. `~/.claude/projects/` 配下の全ディレクトリを対象とする
2. 引数の期間を `find -mtime` 用の日数に変換する
3. 対象ディレクトリ内の `.jsonl` ファイルを列挙する
4. `subagents/` 配下のファイルは除外する

```bash
find ~/.claude/projects/ -name "*.jsonl" -not -path "*/subagents/*" -mtime -7 -type f
```

### Step 2: 判断イベントの抽出

各セッションログから、ユーザーメッセージとアシスタントメッセージを時系列で読み取る。

```bash
# ユーザーメッセージの抽出
jq -r 'select(.type == "user") | .message.content | if type == "string" then . elif type == "array" then .[0].text // "" else "" end' "$LOG_FILE"

# アシスタントメッセージの抽出
jq -r 'select(.type == "assistant") | .message.content | if type == "array" then [.[] | select(.type == "text") | .text] | join("\n") elif type == "string" then . else "" end' "$LOG_FILE"
```

大きいファイル（5MB超）は `head -c 2000000` と `tail -c 2000000` でサンプリングする。
セッション数が多い場合（10件超）は、Agentツールを使ってバッチ分析を並列化する。

以下のパターンを判断イベントとして検出する:

**ユーザー主導の判断:**
- ユーザーが方針・設計・選択を先に述べている（AIの提案に対するレスポンスではない）
- ユーザーが理由付きで方向性を指示している

**AIの提案への却下・修正:**
- AIが提案・推奨した直後に、ユーザーが否定・修正・別案を示している
- 「それは違う」「そうじゃなくて」「〜の方がいい」「やらなくていい」等のパターン

### Step 3: 会話フローの分析

各判断イベントについて、判断の前後3〜5ターンの会話を含めて以下を分析する:

- **判断カテゴリ**: 命名 / モジュール分割 / エラー処理 / 設計パターン / テスト方針 / パフォーマンス / 可読性 / 仕様解釈 / 優先順位 / スコープ判断 / その他
- **ユーザーが重視した観点**: 何を根拠に判断したか（可読性、保守性、パフォーマンス、チーム慣習、顧客要件、期限等）
- **ユーザーが軽視した観点**: AIが提示したが無視またはに退けた観点
- **判断の傾向**: 保守的 vs 積極的、理想主義 vs 実用主義、短期最適 vs 長期最適 等

### Step 4: 傾向の集約

個別の判断イベントを横断的に分析し、以下の構造で傾向をまとめる:

```markdown
## 判断傾向プロファイル

### 分析期間・対象
- 期間: YYYY-MM-DD 〜 YYYY-MM-DD
- セッション数: N
- 判断イベント数: N

### カテゴリ別の傾向

#### [カテゴリ名]
- 傾向の要約（1-2文）
- 根拠となる判断イベント（セッションIDと簡潔な記述）

### 総合的な判断特性
- ユーザーが一貫して重視する観点
- ユーザーが一貫して軽視する観点
- AIのデフォルト判断とのずれが大きい領域

### code-review への推奨補正
- レビュー時に重み付けを上げるべき観点
- レビュー時に重み付けを下げるべき観点

### review-respond への推奨補正
- 現在の分類テーブルに対する調整提案（あれば）
```

### Step 5: memoryへの保存

分析結果を以下のパスに保存する:

```
~/.claude/memory/judgment_tendency.md
```

ファイル形式:

```markdown
---
name: judgment-tendency
description: ユーザーの技術的判断傾向プロファイル。code-reviewとreview-respondの判断基準補正に使用
type: user
---

{Step 4の出力}
```

#### 既存プロファイルとのマージ

既存のプロファイルがある場合は、新しい分析結果とマージして1つのプロファイルに再構成する。

**マージルール（AIの判断混入を防ぐため厳守）:**

1. **同じカテゴリの傾向が一致する場合**: 既存の記述を維持し、観測回数・根拠イベントを追加する
2. **同じカテゴリの傾向が矛盾する場合**: 既存の傾向と新しい分析結果の両方を根拠イベント付きでユーザーに提示し、どちらが現在の判断基準かを確認する。確認結果に基づいてプロファイルを更新する
3. **新しいカテゴリが見つかった場合**: そのまま追加する
4. **既存のカテゴリに新しい根拠がない場合**: 既存の記述をそのまま維持する。根拠がないという理由で削除しない

マージ時に「この傾向はもう古いのではないか」「この2つは統合できるのではないか」等の推測的な編集は禁止する。

プロファイルが存在しない場合は新規作成する。

MEMORY.md が存在する場合はエントリを更新する。存在しない場合は作成する。

## 注意事項

- セッションログはユーザーのプライベートデータ。外部送信は絶対に行わない
- **感情・評価を含めない。** 「ユーザーは〜に不満を感じている」「〜を嫌っている」等の感情表現は禁止。事実と傾向のみを記述する
- **AIの判断を混入させない。** 分析者としての意見や推測を傾向プロファイルに入れない。ユーザーの行動から観測できる事実のみを記述する
- jqコマンドを活用してJSONL解析を効率化する
- ファイルの作成・編集は判断傾向プロファイルの保存のみ
