# companion の設計（合意版）

## 位置づけ

companion は会話コンテキストを固定する役。常駐し、聞き、復唱して確定し、足りない項目を聞き、固まったら State を渡す。ゴールを置くのはユーザー。工程の順序・作業の監督・検収は別の部品が持つ。

会話が既定の状態であり、渡す義務はない。依頼が一度も形にならなければ会話のまま終わる。

## 分担

| 担い手 | 担うもの |
|---|---|
| LLM（companion） | 会話、復唱、「種類の判定に進むか」の引き金 |
| Jev | 引き金が引かれたときの「成果物の種類」「種類ごとのヒアリング項目の抜け」「確定事項との矛盾」 |
| 規則 | 閾値、implement のときの工程ゲート（gate-catalog.md（同ディレクトリ））、ゲート間の依存 |

引き金を LLM に任せる理由: 見落としても「進めて」で走り、失うのは 1 ターン。走らせすぎても Jev を 1 回余計に呼ぶだけ。Jev の支出は会話のターン数ではなく「渡そうとした回数」に比例する。

速度の実測（同じ State、2 問）: Jev は `judge.py` 起動込みで 0.4〜0.9 秒、subagent は sonnet 10.6 秒 / haiku 18.0 秒。答えは一致。

## State

Jev と作業係が読む唯一の入力。companion の解釈を入れない。

1. ユーザー発言の引用（要約しない）。長いときは「復唱して肯定を得た確定事項」と「直近 N ターン」を機械的に残す
2. 依頼の原文（issue 本文・コメント、仕様書、貼られた文書）
3. 事実
   - スクリプトが集めたもの: `.git` とマニフェストの有無、issue / PR の種別、計画書の有無、既存テストの有無
   - **作業係の報告**（ラベル付き）。報告内の提案は確定事項ではない。ユーザーがそれを受けて決めた発言だけが確定事項に入る
4. companion 自身の発言は入れない

## 1 層目: 成果物の種類（choice 1 問 + none）

会話が何で終わるかで 3 つ。

| 種類 | 会話の終わり方 | その先 |
|---|---|---|
| implement | コードが変わる | 統合後のワークフロー。init / plan / spike / review / PR は中の工程ゲート。既存 PR への対応は「対象が PR である implement」 |
| know | 答えを知って終わる（調査、コードベースの把握、仕様の点検） | research / explore / spec-review |
| write | 文書が残る | 執筆 |

`none` が最上位、または最上位が閾値未満なら「何を受け取りたいか」を聞く。壁打ちは種類ではなく companion の素の状態。

複数の種類が続く場合（調べてから実装）は、引き金ごとに 1 つ渡し、結果を State に積み、次の引き金で次を渡す。順序の規則は持たない。

## 2 層目: 種類ごとのヒアリング完了項目（noul、no の項目だけ聞く）

問いはすべて「ユーザーが述べたか」で立てる（作業係の報告は数えない）。

### implement

| 問い | no のとき聞くこと |
|---|---|
| 作業する対象（リポジトリ、issue、PR、ファイル）が特定されているか | どこに対して作業するか |
| 完了条件が、実行して合否が一つに決まる形で述べられているか | 何が動けば完成か |
| 今回やらないこと（対象外）が述べられているか | 作らないものは何か |
| 守るべき制約（変えないもの、既存の設計、規約）が述べられているか | 触ってはいけない範囲は |
| 受け取りたい成果物の形（PR / コミット / 動くもの）が述べられているか | 何を受け取りたいか |
| 却下した案と確定した方針が引用で残っているか | （復唱して肯定を取る） |

工程ゲートが on になったときの追加項目（計画の粒度、レビューの比較基準など）は gate-catalog.md（同ディレクトリ） 側に置く。

### know

| 問い | no のとき聞くこと |
|---|---|
| 知りたい問いが 1 文で述べられているか | 何を知りたいか |
| 答えの形（可否、比較表、手順、原因、該当箇所）が述べられているか | どういう形で欲しいか |
| 範囲（リポジトリ、ライブラリ、バージョン、環境）が特定されているか | 対象は何か |

### write

| 問い | no のとき聞くこと |
|---|---|
| 読者が述べられているか | 誰向けか |
| 媒体（社内ブログ、外部記事、README）が述べられているか | どこに載せるか |
| 題材と結論が述べられているか | 何を伝えたいか |
| 分量や締切が述べられているか | どのくらいの長さか |

### 共通

| 問い | yes のとき |
|---|---|
| 最新の確定事項は、それ以前の確定事項と矛盾するか | 「前に○○と言われたが変えるか」を聞く |

## 3 層目

implement のときだけ gate-catalog.md（同ディレクトリ） の工程ゲート（G2 → G3 → G0 → G1 → G4〜G10）。

## 渡した後

作業係の報告を State に「作業係の報告」として積み、companion が要約して伝える。ユーザーの新しい発言が要件を変えるかは LLM が判断し、変えるなら復唱して確定事項に追記し、進行中の作業係へ伝える。

## 閾値

初期値 yes ≥ 0.7、no ≤ 0.3。外に出して運用で調整する。

## 決めていないこと

- State の「直近 N ターン」の N
- 閾値の実値
- dev-workflow / proto-workflow の統合の進め方（人間が入口で選ぶ理由が消えるので統合する方向までは合意）
