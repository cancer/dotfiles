# director の「考えるフェーズ」: ゲートのカタログ（案）

目的: 会話で確定した要件を実装し切るのに必要な工程を、固定の問いと規則で決める。Jev は工程ごとの noul に答えるだけで、問いの列挙・順序・依存は本カタログが持つ。

## 0. 決定（2026-11-07、以下の節より優先する）

ユーザーと合意したもの:

- dev-workflow と proto-workflow を 1 本に統合する
- 統合後のワークフローは引数 effort（中 / 高）を受け取る。effort は品質の評価・改善をどの程度行うかだけを表す
  - 中: 機械的チェック（lint・型・テスト）と変更ファイルの範囲の突合をスクリプトで通したうえで、verify-task / test-review / code-review を 1 周
  - 高: 同じ 3 種を指摘 0 まで（上限 3 周）＋統合後レビュー
- effort は呼び出し側の LLM が会話から判断して渡す。Jev は使わない
- PR は effort に含めない（どこで決めるかは未決定）

### 各ゲートの収まる先（案。合意ではない）

| ゲート | 収まる先（案） |
|---|---|
| G2 使い捨て / G3 実装を伴うか | dispatch の種類判定と呼び出し側 LLM の判断 |
| G0 新規構築 / G1 参照の種別 | 機械的な確認。dev-workflow の「初期構築の判定」「参照の同定」に既にある |
| G4 計画の有無 / G6 実測が要る仮定 / G8 統合 | ワークフロー内の工程（dev-workflow Phase 1・2・5） |
| G5 本番前提 / G7 レビュー反復 | effort 引数（上記の決定） |
| G9 PR | effort に含めないことのみ決定。どこで決めるかは未決定 |
| G10 完了報告の体裁 | 既存の完了報告の節 |

## 1. 答えの出どころと優先順位

1. **ユーザーの明示**: 「proto で」「PR まで」「レビューは要らない」のように工程を名指しした発言。State に引用し、該当ゲートは Jev に問わず固定する
2. **Jev の判定**: 固定の問いに対する noul の確率。`yes` 閾値以上なら入れる、`no` 閾値以下なら外す
3. **ユーザーへの確認**: 閾値の間に落ちたゲートだけを `AskUserQuestion` で聞く。聞いた答えは 1 として State に追記し、依存するゲートを問い直す

閾値の初期値は yes ≥ 0.7、no ≤ 0.3。verify-task の `rules.json` と同じく外に出して調整する。

## 2. State の組み立て（LLM が書く。解釈は入れない）

順に並べる。全体で 30,000 字以内。

1. ユーザーの発言の引用（要約しない）。長いときは「director が復唱しユーザーが肯定した確定事項」と「直近 N ターン」を機械的に残す
2. 依頼の原文（issue 本文・コメント、仕様書、依頼文）
3. スクリプトが集めた事実: `.git` とマニフェストの有無、issue / PR の種別、計画書の有無（会話で作ったならそのパス）、既存テストの有無、デフォルトブランチ
4. director 自身の発言は入れない。入れる場合は「director の発言」とラベルを付けて区別する

## 4. ゲート間の規則（Jev は知らない。規則側で弾く）

- 判定順は G2 → G3 → G0 → G1 → G4 以降。使い捨てのコードや調査だけの依頼は、空ディレクトリでも init-project を要しないため、G0 より先に G2・G3 で抜ける
- G2 が yes なら以降を判定しない
- G3 が no なら G0 と G5〜G9 を判定しない
- G0 が yes なら他は判定しない（init-project の後に再実行）
- G9 yes かつ G7 no は矛盾。ユーザーに「レビューなしで PR を作るか」を確認する
- G8 は decompose の出力が出るまで決まらない。intake 時点では「未定」として持ち、decompose 後に規則で埋める
- G6 は intake 時の Jev 判定と decompose の出力の両方で見る。どちらかが yes なら spike
- G5 が no で G7 が yes の組（試作だがレビューは通す）は許す。推論量は G5 に従う
- ユーザーの明示は常に Jev の判定を上書きする。明示と規則が矛盾する場合（「PR まで、レビューなしで」）はユーザーに確認する

## 5. 再判定のタイミング

工程を 1 つ終えるごとに State を更新して問い直す。特に:

- decompose の出力後: G6（仮定の列挙）、G8（タスク数と依存）
- spike の結果後: decompose をやり直すので G4〜G9 を問い直す
- ユーザー確認の回答後: 回答を State に追記し、依存するゲートだけ問い直す

## 6. 問いの `criteria` に使う既存の文（出典）

- G2: dev-workflow description「『使い捨て』『テスト不要』と明示された単発コードは対象外（inline で直接対応）」
- G3: director の表の非実装行（research / plan / spec-review / article-writer など）
- G5: proto-workflow「起動条件」: 動くものを早く得て、判断材料にする・見せる・仮定を確かめることが目的なら proto。育てるかどうかは判定に使わない。dev-workflow description「最初から本番投入するコードとして作る依頼」
- G6: dev-workflow「プロトタイプ検証への割り込み」の検知の 4 条件
- G7: dev-workflow「レビューの反復」の前提（他者が読む PR に出す前に指摘 0 にする）
- G9: dev-workflow Phase 6 / proto-workflow 7.「PR は作成しない。明示された場合だけ」

## 7. このカタログで扱わないもの

- モデルと推論量の段の選択そのもの（`delegate-to-codex/references/model-routing.md` の 1 文テストに従う。G5 は既定を切り替えるだけ）
- 各工程の内部手順（review-loop の 3 周上限、矛盾の解決順など）。それは工程側の文書が持つ
- director の表にある非実装スキルの選択（G3 が no のときの振り分け）。必要なら「表の行 + none」の choice を別に置く
