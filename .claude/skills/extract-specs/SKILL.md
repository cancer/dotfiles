# セッション履歴からの仕様抽出

セッション履歴を走査し、仕様として文書化すべき暗黙の決定事項・要件・ルール・制約を抽出する。

## 引数
$ARGUMENTS

引数のパース:
- 第1引数: 期間指定（`7d`, `3d`, `2w` 等）。省略時は `7d`
- 第2引数以降: 対象キーワード（絞り込み用）。省略時は全セッションを対象

例:
- 引数なし → 直近7日間、全セッション
- `14d` → 直近14日間
- `7d 認証` → 7日間、「認証」を含むセッションのみ
- `API設計` → 直近7日間、「API設計」を含むセッションのみ（期間の形式でなければキーワードと判定）

## 抽出対象

以下のカテゴリに分類して抽出する:

### 1. 設計判断（Design Decisions）
- 技術選定の理由と結論（「AではなくBを採用した、なぜなら〜」）
- アーキテクチャ上の方針決定
- 命名規則の合意
- ディレクトリ構造やファイル配置の決定

### 2. ビジネスルール（Business Rules）
- ドメイン固有の振る舞い定義（「〜の場合は〜する」）
- 値の制約・バリデーションルール
- 状態遷移のルール
- 優先順位・順序のルール

### 3. インターフェース仕様（Interface Specs）
- API のリクエスト/レスポンス形式の合意
- コンポーネントのprops/イベントの定義
- データ型・スキーマの決定
- 外部システムとの連携仕様

### 4. エッジケースと例外処理（Edge Cases & Error Handling）
- 議論の中で発見されたエッジケースとその対処方針
- エラー時の振る舞いの決定
- 境界値・空値の扱い

### 5. 制約・前提条件（Constraints & Assumptions）
- パフォーマンス要件
- セキュリティ要件
- 互換性の制約
- 外部依存の前提

### 6. 未決事項・先送り事項（Open Items）
- 議論されたが結論が出なかった項目
- 「あとで考える」「次のフェーズで」と先送りされた項目
- 一時的なワークアラウンドとその理由

## 実行手順

### Step 1: セッションログファイルの収集

1. 現在のプロジェクトのパスを特定する（`pwd` の結果を使用）
2. プロジェクトパスから対応するディレクトリ名を推定する（先頭の `/` を除去し、残りの `/` を `-` に置換）
3. `~/.claude/projects/` 配下で、そのディレクトリ名に前方一致するディレクトリを列挙する（worktree用の派生パスを含めるため）
4. 引数の期間を `find -mtime` 用の日数に変換する（`7d` → `-mtime -7`、`2w` → `-mtime -14`）
5. 対象ディレクトリ内の `.jsonl` ファイルを列挙する（`subagents/` 配下は除外）

```bash
find "$PROJECT_DIR" -name "*.jsonl" -not -path "*/subagents/*" -mtime -$DAYS -type f
```

キーワードが指定されている場合は `grep -l` で絞り込む。

### Step 2: セッションログの読み取りと分類

各セッションファイルからユーザーメッセージとアシスタントメッセージの両方を抽出する。

```bash
# ユーザーメッセージの抽出
jq -r 'select(.type == "user") | .message.content | if type == "string" then . elif type == "array" then .[0].text // "" else "" end' "$LOG_FILE"

# アシスタントメッセージの抽出
jq -r 'select(.type == "assistant") | .message.content | if type == "array" then [.[] | select(.type == "text") | .text] | join("\n") elif type == "string" then . else "" end' "$LOG_FILE"
```

注意事項:
- 大きいファイル（5MB超）はサンプリングする（`head -c 3000000` と `tail -c 3000000`）
- セッション数が多い場合（8件超）は、Agentツールを使って並列分析する

### Step 3: 仕様候補の抽出

各セッションのやりとりを読み、以下のシグナルに注目して仕様候補を抽出する:

**強いシグナル（高確率で仕様化すべき）:**
- ユーザーが明示的に「〜にする」「〜とする」「〜にしよう」と決定を述べている
- 「〜のルールは〜」「〜の場合は〜する」といった振る舞い定義
- 「〜は禁止」「〜してはいけない」といった制約の明示
- 実装後にユーザーが修正を要求し、最終的に合意した仕様

**中程度のシグナル（検討の余地あり）:**
- 議論の結果、アシスタントが提案しユーザーが承認した方針
- コードレビューで指摘された結果変更された振る舞い
- テストケースから読み取れる暗黙の仕様

**弱いシグナル（コンテキストとして記録）:**
- 「あとで」「TODO」「暫定的に」といった先送りの言及
- 複数案が挙がったが明確な結論が出なかった議論

### Step 4: 重複排除とマージ

複数のセッションで同じ決定事項が言及されている場合は、最新の合意内容にマージする。矛盾がある場合は、後のセッションの内容を優先しつつ、変遷を記録する。

### Step 5: レポート出力

以下の形式でレポートを出力する:

```markdown
# 仕様抽出レポート

**対象期間**: YYYY-MM-DD 〜 YYYY-MM-DD
**分析セッション数**: N件

## 設計判断

| # | 決定事項 | 根拠・経緯 | セッション日付 | 確度 |
|---|----------|-----------|---------------|------|
| 1 | 具体的な決定内容 | なぜその判断に至ったか | YYYY-MM-DD | 高/中 |

## ビジネスルール

| # | ルール | 条件・例外 | セッション日付 | 確度 |
|---|--------|-----------|---------------|------|
| 1 | 具体的なルール | 適用条件や例外 | YYYY-MM-DD | 高/中 |

## インターフェース仕様
（同様の表形式）

## エッジケースと例外処理
（同様の表形式）

## 制約・前提条件
（同様の表形式）

## 未決事項・先送り事項

| # | 項目 | 経緯 | セッション日付 | 理由 |
|---|------|------|---------------|------|
| 1 | 未決の項目 | 議論の経緯 | YYYY-MM-DD | 先送りの理由 |

## オープンクエスチョン

| # | 問い | 経緯 | セッション日付 |
|---|------|------|---------------|
| 1 | 未解決の問い | どこで生じた問いか、なぜ未解決か | YYYY-MM-DD |
```

**確度の定義:**
- **高**: ユーザーが明示的に決定した、または修正指示の結果として確定した
- **中**: アシスタントの提案をユーザーが承認した、またはコードレビューを通じて確定した

該当する抽出結果がないカテゴリは省略してよい。

## 注意事項

- セッションログはユーザーのプライベートデータ。外部送信は絶対に行わない
- 抽出は事実ベースで行う。セッション内で実際に議論・決定された内容のみを対象とする
- 推測や補完で仕様を「創作」しない。やりとりから読み取れる範囲に留める
- 同じ決定が複数セッションに跨がる場合は、最終的な結論を報告する
- ファイルの作成・編集は行わない（分析・レポート出力のみ）
