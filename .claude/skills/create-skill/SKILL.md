新しいスキルを、品質基準を満たす形で作成する。

## 引数
$ARGUMENTS

## 引数の形式

作りたいスキルの目的や、発火させたい場面を自然言語で受け取る。曖昧なら着手前にユーザーに確認する。

## スキルファイルの配置

- ユーザースコープ: `~/.claude/skills/<skill-name>/SKILL.md`
- プロジェクトスコープ: `.claude/skills/<skill-name>/SKILL.md`

## 実行手順

### 1. 目的と発火条件の確定

「どの場面で発火してほしいか」「入力は何か」「何を返すか」を確定する。ユーザーが実際に経験した問題が起点にあるかを確認する。単なる思いつきなら、本当に必要かを問い返す。

### 2. 既存スキルとの境界確認

`~/.claude/skills/` 配下の既存スキルの description を Grep で調べ、目的が重なるものが無いか確認する。

- **重なる既存スキルがある**: 新設ではなく `edit-skill` での拡張を提案する
- **近いが別物**: 新スキルの description に「〜は○○の領分」という境界句を入れて区別する

### 3. スキルタイプの判定（これが本文の形を決める）

| タイプ | 例 | 本文の形 |
|---|---|---|
| 規律（規則を守らせる） | TDD・完了前検証 | 鉄則＋失敗パターン表＋Red Flags |
| 手順（やり方を示す） | 実装・レビュー・調査の進め方 | 番号付きの手順＋成果物の型 |
| 参照（情報を引く） | API・コマンド一覧 | 表・箇条書き |

### 4. SKILL.md の作成

次の品質基準に沿って本文を書き、ファイルを作成する。

### 5. 確認

作成した内容を表示し、ユーザーに確認を促す。

## 品質基準（5観点）

- **① 発火条件（description）**: いつ使うかを書く。何をするかの要約や手順の要約を書かない（手順を要約するとエージェントが本文を読まず要約に従い、本文が空文になる）。「〜と頼まれた場面で使う」等のトリガー語と、紛らわしい既存スキルとの境界句を入れる
- **② 入力**: `argument-hint` と「引数の形式」節で、受け取る引数とその解釈を明示する
- **③ 成果物**: 肯定形で「何を返すか」を書く（出力形式・レポート構造など）。「〜しない」の羅列で形を規定しない
- **④ チェックリスト**: 完了前に満たすべき条件を、埋めるべきスロットとして置く
- **⑤ 失敗防止**: 下記「失敗の型に形を合わせる」に従う

## 失敗の型に形を合わせる

守らせたい失敗の型によって、効く形が違う。型を取り違えると逆効果になる。

| 失敗の型 | 効く形 | 効かない形 |
|---|---|---|
| 規則を知っていて圧力下で破る | 禁止＋失敗パターン表＋Red Flags | 「なるべく〜」の柔らかい助言 |
| 従うが出力の形が崩れる（冗長・要約化） | 肯定形のレシピ／成果物契約 | 「〜するな」の禁止列挙 |
| 作るものから必須要素が抜ける | テンプレート内の必須スロット | 近くの散文リマインド |
| 条件で振る舞いを変えたい | 観測可能な条件に紐づけた分岐 | 無条件ルール＋例外句 |

**禁止形は規律の失敗だけに使う**。出力の形が崩れる・要素が抜ける型に禁止形を当てると、圧力下でエージェントが「〜するな」と交渉して、むしろ不要な出力が増える。肯定形レシピは交渉の余地を残さない。

## 完了前チェックリスト

- [ ] ユーザーが経験した実問題が起点にある（思いつきでない）
- [ ] 目的が重なる既存スキルが無い（あれば edit-skill を提案した）
- [ ] スキルタイプを判定し、本文の形をそれに合わせた
- [ ] description はトリガー語中心で、手順の要約になっていない
- [ ] 5観点（発火・入力・成果物・チェックリスト・失敗防止）を満たす
- [ ] 名前は英小文字・数字・ハイフンのみ

## 注意事項

- 検証済みでない品質基準を「テスト済み」と偽らない。スキルは振る舞いを形作るコードであり、本来は発火するかを実地で確かめてから配備するのが理想
- プロジェクト固有の作業は、ユーザースコープではなくプロジェクトスコープに作る
