指定されたコードをソフトウェアエンジニアリングの原則に基づいてレビューする。

## 引数
$ARGUMENTS

引数から以下を特定する：
- レビュー対象（ファイルパスまたはディレクトリ）

## 判断基準 knowledge の参照

レビュー開始前に、レビュー観点の根拠となる既存 knowledge を `mcp__knowledge__search_knowledge` で検索する（例: 「コードレビュー 判断基準」「レビュー 観点」）。ヒットしたら `mcp__knowledge__read_knowledge` で本文を読み、その原則に沿って観点を調整する。

- knowledge はレビュー観点の根拠・重み付けにのみ使う。knowledge の内容そのものをレビュー出力に含めない
- 該当する knowledge が無ければ、デフォルトの観点でレビューする（以下の通り）。

**このスキルはどのモデルで実行するかを判断しない。** 実行エンジンと推論量の選択は呼び出し側の責務である（`dev-workflow` は `delegate-to-codex` 経由でこのスキルを Codex に実行させる）。ここに書くのは手順だけとする。

委譲時は、レビュー対象のdiffと下記レビュー観点を委譲先へのタスクプロンプトに含めること。

委譲先がレビュー結果を返したら、その内容を出力形式に従って整形して報告する。

## レビュー観点

**堅牢性**
- エッジケースのテストが存在するか（null/undefined、空配列、境界値など）
- エラーを握りつぶしていないか
- フェイルファスト — 異常な状態を早期に検出して即座に失敗させているか
- 型で不正な状態を表現不可能にしているか（any/asの不要な使用がないか）。ただし型パズルや、型安全性のためだけに実装を歪めていないか
- 引数や共有データを直接変更していないか（不変性）

**変更容易性**
- SOLID原則に従っているか
  - 関数の変更理由が複数ないか
  - 新しいケースの追加にswitch/ifの分岐追加で対応していないか
  - 親クラスのメソッドを空実装やthrowでオーバーライドしていないか
  - インターフェースは利用者が必要とするメソッドだけを含めているか
  - 外部依存（DB・API・ファイルシステム）は差し替え可能か
- DRY — コードの見た目ではなく知識・ロジックの重複を排除しているか
  - 共通の意味・意図を持つ知識・変数・ロジックが単一の情報源になっているか
  - コメント・ドキュメントもDRYの対象としているか
  - 見た目が似ているだけで意味が異なるコードを無理にまとめていないか
- 隠れた依存・グローバル状態がないか

**低認知負荷**
- 変数・関数名は意図が一目でわかる名前か（略語・汎用名を使っていないか）
- 早期リターンを活用し、ひとつの関心事の処理が終わり結果が導かれた時点で関数を抜けているか
- 条件分岐が複雑になっていないか

**その他**
- コードを自然言語に翻訳しただけのコメントがないか
- 既存のコードベースのスタイル・パターンに従っているか
- 適切にモジュール分割が行われているか
    - 関連するコードは1つのファイルにまとめる（過剰な分割の禁止）
    - 1つのファイルは1つの関心事に集中させる（過剰な結合の禁止）
    - モジュールとして適切な粒度でないにも関わらず、re-exportするだけのファイルがないか

## 出力形式

各観点について以下の形式で報告する：

### [観点名]

| 場所 | 指摘 | 重要度 |
|------|------|--------|
| `file:line` | 具体的な指摘内容 | high/medium/low |

指摘がない観点は省略してよい。最後に全体の所感を簡潔に記載する。

## 完了前チェックリスト

レポートを返す前に確認する。

- [ ] 全観点（堅牢性・変更容易性・低認知負荷・その他）を通した
- [ ] 各指摘に `file:line` と根拠（原則名・具体的リスク）を添えた
- [ ] 各指摘に重要度（high/medium/low）を付けた
- [ ] 判断傾向プロファイルがあれば観点の重み付けに反映した
