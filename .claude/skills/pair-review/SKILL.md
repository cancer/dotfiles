ユーザーとペアレビューを行ってください。

## 引数
$ARGUMENTS

## 引数の形式

以下のいずれかの形式で指定できます：

1. **ファイル/ディレクトリパス**: `src/components/Button.tsx` や `src/utils/`
2. **GitHub PR URL**: `https://github.com/owner/repo/pull/123`
3. **PR番号**: `123`（現在のリポジトリのPRとして扱う）
4. **組み合わせ**: PR番号とファイルパスの両方を指定可能（例: `123 src/utils/`）

PR指定がある場合は、PRの変更ファイルをレビュー対象とする。ファイル/ディレクトリ指定がある場合は、その範囲に絞る。

## ワークフロー

### フェーズ1: 準備

1. 引数を解析し、レビュー対象のファイルを特定する
2. PR指定がある場合は `gh pr diff <number> --name-only` で変更ファイル一覧を取得する
3. 対象ファイルを読み込み、コード全体を把握する

### フェーズ2: 概要の提示

以下の形式でレビュー対象の概要をユーザーに提示する：

```
## レビュー対象

| ファイル | 行数 | 概要 |
|---------|------|------|
| `path/to/file` | N行 | ファイルの役割の簡潔な説明 |

## 初見の所感

コードを読んだ上での全体的な印象を簡潔に記載する（良い点・気になる点の両方）。
```

提示後、ユーザーに以下を確認する：

- 気になる箇所や深掘りしたい箇所はあるか
- 特に注目してほしい観点はあるか

### フェーズ3: 対話的レビュー

ユーザーが指定した箇所について深掘りする。以下のルールに従うこと：

- **ユーザーが気になる箇所を指定する** → その箇所を詳細に分析し、所見を述べる
- **ユーザーが観点を指定する** → その観点に絞ってコード全体をチェックする
- **ユーザーが「他に気になる点は？」と聞く** → `code-review` スキルのレビュー観点に基づき、未議論の指摘を提示する

各指摘について、ユーザーと以下を議論する：

- 問題の内容と影響
- 修正が必要かどうか
- 修正する場合のアプローチ

**議論の結果を以下の3分類で記録する：**

- **指摘する**: 合意した指摘事項（PRコメントとして投稿する）
- **保留**: 追加調査や他メンバーの意見が必要
- **見送り**: 議論の結果、指摘不要と判断したもの

このフェーズはユーザーが「レビュー完了」「まとめて」等の意思を示すまで繰り返す。

### フェーズ4: レビュー結果のまとめ

議論した内容を以下の形式でまとめてユーザーに提示する：

```
## レビュー結果サマリー

### 指摘事項

| # | 場所 | 内容 | 重要度 |
|---|------|------|--------|
| 1 | `file:line` | 指摘内容 | high/medium/low |

### 保留

| # | 場所 | 内容 | 理由 |
|---|------|------|------|
| 1 | `file:line` | 内容 | 保留理由 |

### 見送り

| # | 場所 | 内容 | 理由 |
|---|------|------|------|
| 1 | `file:line` | 内容 | 見送り理由 |
```

ユーザーに最終確認を取る：

- 指摘事項の内容・重要度に問題がないか
- 投稿するコメントの文面に問題がないか（ユーザーの言葉として投稿されるため）
- PRコメントとして投稿してよいか

### フェーズ5: PRコメントの投稿

ユーザーの承認後、以下の手順でPRコメントを投稿する。

#### 5-1. PR番号の確認

- 引数でPR指定がない場合、現在のブランチに対応するPRを `gh pr view --json number` で取得する
- PRが存在しない場合は、会話内のまとめのみで完了とする（その旨をユーザーに伝える）

#### 5-2. コメント文面の作成

投稿するコメントは **ユーザー本人の言葉として投稿される**。以下のルールに従うこと：

- ボット署名（`🤖 *This comment was posted via Claude Code*` 等）を **付けないこと**
- 「AIが」「Claudeが」等の三人称表現を使わないこと
- ユーザーが自分で書いたレビューコメントとして自然に読める文面にすること
- **柔らかい表現を心がけること**（威圧的・断定的な言い回しを避ける）
- **固すぎない口語的な丁寧語を用いること**（「〜した方がよさそうです」「〜かもしれません」等。「〜すべきです」「〜してください」のような硬い表現は避ける）
- フェーズ4で提示したコメント文面をユーザーに確認してもらい、修正指示があれば反映すること

#### 5-3. インラインコメントの投稿

各指摘事項について、該当行にインラインレビューコメントを投稿する。

```bash
gh api repos/{owner}/{repo}/pulls/{number}/reviews -f event=COMMENT -f body="" -f comments="[$(cat <<'COMMENTS'
[
  {
    "path": "<file-path>",
    "line": <line-number>,
    "body": "<comment-body>"
  }
]
COMMENTS
)]"
```

投稿が困難な場合（行番号がdiffに含まれない等）は、通常のPRコメントとして投稿する。

#### 5-4. サマリーコメントの投稿

PRにサマリーコメントを投稿する。**`comment-issue` スキルは使用しないこと**（署名が自動付与されるため）。直接 `gh pr comment` を使用する。

```bash
gh pr comment <number> --body "$(cat <<'EOF'
<サマリー本文>

---
*@<github-username> の監修のもと[Claude Code](https://claude.ai/claude-code)が投稿しています*
EOF
)"
```

`<github-username>` は `gh api user --jq .login` で取得したユーザー名を使用する。

## 注意事項

- **ユーザーの承認なしにPRコメントを投稿しないこと**
- **ユーザーが議論を終了する意思を示すまで、フェーズ3を継続すること**
- **インラインコメントはユーザー本人の言葉として投稿する（ボット署名を付けない）**
- **サマリーコメントには `@username の監修のもとClaude Codeが投稿しています` の注釈を付ける**
- 自分の意見を押し付けず、ユーザーの判断を尊重すること
- 指摘に根拠を示すこと（原則名、具体的なリスク、影響範囲など）
- 良いコードには積極的に言及すること（レビューは問題指摘だけではない）
