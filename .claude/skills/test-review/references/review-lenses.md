# LLM レビューの観点と判断基準

機械検出で出た事実を「どう解釈するか」を決めるための基準。ここでの判断はすべて区分「LLMレビュー」または「人による最終判断」になる。仕様が渡されていない状態で仕様の妥当性を判断してはいけない。

## 1. テストの深さとレベル配置

対象の性質から適切なレベルを決め、実際の配置（`scan.json` の `declared_level`）と比べる。

| 対象の性質 | 適切なレベル | 理由 |
|---|---|---|
| 入出力が値で決まる計算・判定・変換 | 単体 | 分岐と境界値を安く網羅でき、失敗時に原因箇所が一意に決まる |
| 永続化・トランザクション・外部サービス連携・スキーマ整合 | 統合 | モックでは、実際のドライバやスキーマの制約による失敗を再現できない |
| 収益・認証・データ喪失に関わる利用者導線 | E2E | 構成要素が個別に正しくても、結線・設定・権限の誤りは通しでしか検出できない |

`level_mismatch`（単体テストとして配置されているが外部依存を持つ）を指摘するには、対象がどちらなのかを先に決める必要がある。

- 対象が値の計算であるなら、依存を伴って単体テストに置かれている状態が違反である（根拠は上表の 1 行目）
- 対象が連携の確認であるなら、単体として分類されている状態が違反である（実行時間の期待値と実行タイミングが分類と食い違う）

どちらかが言えるならその違反を根拠付きで書く。どちらとも言えないときは、その関数が「値の計算」なのか「連携の確認」なのかを問いとして立て、質問へ回す。どう直すか（依存を押し出すのか、統合へ移すのか）は書かない。

**この順序は棄却にも同じに掛かり、踏んだことが出力から読めなければならない。** 検出を「意図した統合テストなので正当」として落とす場合も、対象が「連携の確認」であると実装から確定させ、何を開いて確認したかを書く（出力契約の「棄却した検出」節）。

- 対象の性質は、実装のシグネチャと処理内容で決める。依存が引数で注入された関数であり、テスト対象の変換が入力から出力への値の導出であるなら、対象は値の計算であって、実 I/O は検証に不要である
- ファイル名の `.integrate` / `tests/integration/`、テスト内のコメントに書かれた「実 server でなければ観測できない」という主張、テスト名は、いずれも分類の**宣言**であり、その分類が妥当かの判断ではない。これらだけを根拠にした棄却は不成立である
- 実装を開いても性質が決まらないなら、棄却せず質問（または未判断）に落とす

## 2. 上位の重いテストが下位ロジックを代替していないか

次の 3 条件が揃うと、分岐の網羅を E2E・統合テストが肩代わりしている疑いが立つ。

- `targets.json` の対象関数が分岐や例外経路を複数持つ
- その関数を直接呼ぶ単体テストが `candidate_tests` に無い、または単体テストのケース数が分岐数より明らかに少ない
- 一方で E2E・統合テストがその経路を通っている（カバレッジ上は覆われている）

このとき「カバレッジは足りているが、失敗時に原因箇所が特定できず、実行コストが分岐数に比例して膨らむ」という影響を書く。カバレッジ率そのものを指摘の根拠にしない。**覆われている＝検証されている、ではない**（実行されただけで期待値が固定されていない場合がある）。

## 3. テスト意図の表現

テスト名、準備、実行、期待値の 4 つが、読者に同じ命題を伝えるかを見る。

- テスト名が振る舞い（入力条件と期待結果）を述べているか。`works`, `test1`, `returns correctly` は命題を含まない
- 準備が、その命題に必要な条件だけを作っているか。無関係な固定値が多いと、どの条件が結果を決めているのか読めない
- 期待値がテスト名の主張と一致しているか。名前が境界値を述べているのに、期待値が存在確認だけなら不一致
- 1 つのテストが複数の命題を検証していないか（失敗時にどの命題が壊れたか分からない）

`weak_assertion_only` / `no_assertion` の自動検出と重なる場合、指摘は 1 件に統合し、区分は「自動検出」にしたうえで意図の食い違いを LLM の追記として書く。

## 4. 実装の内部手順への結合

内部手順に結び付いたテストは、振る舞いが変わっていないリファクタリングで壊れる。次を結合の兆候として扱う。

- モックの呼び出し回数・順序・引数だけを検証し、戻り値や状態変化を検証していない（`mock_only_assertion`）
- テスト対象の private な手順（内部メソッド名、内部の中間データ構造）に依存している
- モックの数が対象の協力者数を超えている、またはモックがモックを返す段数が深い
- 広いスナップショットで差分全体を固定しており、意図した命題が読めない

ただし、副作用そのものが仕様である場合（通知が 1 回だけ送られる、リトライが 3 回で止まる、監査ログが必ず残る）は、呼び出し検証が正当な検証である。この区別を書かずに「モック偏重」とだけ指摘してはいけない。

## 5. 生き残った変異の解釈

`metrics.json` の `changed_scope.survived_mutants_in_changed` を、変異が触った箇所の意味で分類する。

- 業務上の意味を持つ条件・境界・演算子（金額計算、権限判定、上限値）が変異しても検出されない → 仕様漏れの候補として重要度を上げる
- ログ出力、メトリクス、パフォーマンス最適化、等価な書き換え（`>=` と `>` が同じ結果になる文脈）→ 等価変異の可能性を明記し、重要度を下げる
- 変異箇所がそもそもカバレッジ外（`NoCoverage`）→ ミューテーションの指摘ではなく未検証行の指摘として扱う

生存変異は「テストが弱い」ことの証拠であって、「仕様が誤っている」ことの証拠ではない。仕様漏れかどうかは、その条件が仕様上意味を持つかに依存するため、仕様資料が無ければ人による最終判断へ回す。

## 6. 指摘は違反と根拠で閉じる（対応内容は書かない）

観点 1〜5 で見つけたものは、次の 2 つのどちらかに落ちる。中間はない。

| 状態 | 書き方 |
|---|---|
| 何に反しているかを言える | 違反の内容と、反している対象（仕様・計測値・設計原則）、その所在（`file:line`・レポート値） |
| 何に反しているかを言えない | 観点 6.5 に従い質問にする |

前者では、対応は違反状態の解消であり、指摘と根拠から一意に決まる。手段を書き添えない。たとえば「変更した割引計算の分岐に対する検証が無い（`src/pricing.ts:12-14`、カバレッジ `DA:13,0`）」まで書けば、何が解消された状態かは決まる。そこから「単体テストを足すか、依存を切り出してから足すか」を導くのは実装者の領域である。

上位テストによる代替（観点 2）や実装内部手順への結合（観点 4）でも同じ。「統合テストだけが分岐を保証している」という状態を根拠付きで書くところまでが担当で、テストレベルの置き換え方は書かない。

観点 1 のレベル配置の表は、**どのレベルが妥当かを判断して指摘の根拠にするため**に使う。「単体に移すべき」という手段の指示として使わない。

## 6.5. 足りない根拠は、在処に応じて取りに行く

推測で埋めた指摘は、実測に基づく指摘と同じ強さで読まれてしまう。埋めずに答えを取りに行く。取りに行く先は問いの種類で決まる（手順 2.5 の表）。

**記録に属する問い**は自分で探す。人は答えを持っていない。

| 問い | 探す先 |
|---|---|
| 無効化（`it.skip` / `#[ignore]` / `describe.skip`）の理由と復帰条件 | `git log -S "#[ignore]"`、`git blame` で該当行、そのコミットの PR 本文 |
| この差分が何を直す変更か | コミットメッセージ、PR 本文、リンクされた issue |
| CI が何を実行しているか（`.only` の影響、レポートに現れないテスト） | CI 設定ファイル、テストランナーの設定（`allowOnly` 等）、`git ls-files` で追跡状態 |
| レポートの採取リビジョン | レポート内のパス・件数と作業ツリーの突き合わせ、CI のログ・成果物のメタデータ |

見つからなければ「記録が残っていない」ことを指摘として書く。無効化の理由が読めない状態は、次に触る人が復帰の可否を判断できないため、判断材料の欠落そのものである。

**記録に無かった問いは実装者に問う**。差分を書いたのはエージェントであり、実装時の判断（なぜその依存を残したか、なぜそのテストを止めたか）はそのコンテキストにしか無い。同一セッションに居るなら `SendMessage` で直接問う。居ないなら「記録が残っていない」ことを指摘として書く。

実装者へ問うときは、答える側が答えられる形にする。「無効化の理由が不明である」では答えようがない。「`saturates_at_limit` の `#[ignore]` は失敗の一時回避か、恒久的に不要と判断したものか。前者なら `saturating_sub` への変更と関係するか確認したい」のように、何を答えれば根拠になるかを添える。

答えが得られた項目は、その回答を出所付きで根拠として引用し、指摘に格上げする。答えが得られない項目（実装者が居ない、または「決めていない」）は、意図がどこにも固定されていない事実を指摘として書く。テストで固定できない理由がここにあるためで、人に決めてもらう必要はない。

## 7. 確信度の付け方

| 水準 | 条件 |
|---|---|
| 高 | 機械検出の事実と、コードを読んで確認した内容が一致し、仕様解釈を必要としない |
| 中 | 事実は確認できるが、妥当性の判断に仕様または運用上の前提（頻度・影響範囲）の推定が入る |
| 低 | 事実の一部が未計測・未確認、または仕様が分からず影響を見積もれない |

確信度「低」の指摘を削るのではなく、区分「人による最終判断」として残す。レビュー担当者が確認すべき問いを、そのまま問いの形で書く。

## 8. 棄却も根拠で閉じる

観点 1〜5 は、検出を上げる判断にも落とす判断にも同じに適用される。棄却は検出の件数分だけ発生する頻出操作なので、ここに根拠を省く抜け道があると、レビューの大半が無根拠になる。

| 状態 | 出力先 |
|---|---|
| 実物を開き、検出が指す状態が成立していないと確認できた | 「棄却した検出」（開いて確認したもの / 確認した内容 / 判定） |
| 実物を開いていない、または開いても判断できない | 未判断として残し、確認に必要な問いを質問へ |

棄却してよい典型は検出器の限界である。検出器が文字列リテラルを正規化するため意味のある差分が消えて `duplicate_test_body` が出る、仕様上の拒否結果が `null` / `undefined` であるため `toBeNull` が `weak_assertion_only` に数えられる、といったものはいずれも実物を開けば確認できる。**要求されているのは棄却の禁止ではなく、棄却の根拠である。**

棄却の根拠に使えないもの（いずれもレビュー対象の自己申告か、未確認の事項）:

- テスト内・実装内のコメントに書かれた意図の説明
- ファイル名・ディレクトリ名による分類の宣言、テスト名、`describe` の見出し
- 未計測の項目（実行結果が `not_measured` のまま「回帰防止として機能している」と結論することはできない。実行され得るかを知らない状態で、回帰防止手段として正当という結論は成立しない）
