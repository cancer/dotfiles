テストコードと変更コードを分析し、レビュー担当者が判断できる材料を提示する。

このスキルの成果物は結論ではなく**根拠付きのレビュー候補**である。テストの十分性を確定させたり、コードを修正したりしない。機械的に判定できる事実はスクリプトへ委譲し、LLM は仕様と設計の解釈が必要な部分だけを担当する。両者を混ぜると、観測できていない推測が観測事実として読まれてしまうため、各指摘には必ず判定区分を付ける。

## 適用しない場面

- 実装コード起点で「テストが無い箇所」を網羅列挙したい → `test-analyze`
- 実装の設計・堅牢性のレビュー → `code-review`
- これからテストを書く手順 → `test-driven-development`
- テストを実行して直したい → このスキルはテストを実行しない（後述の禁止事項）

## 引数

$ARGUMENTS

| 引数 | 意味 |
|---|---|
| `<path>...` | レビュー対象。**省略時は git 差分**（`--base` の基点から HEAD まで）を対象にする |
| `--base <ref>` | 差分の基点。省略時は `origin/HEAD` → `origin/main` → `origin/master` → `main` → `master` の順に merge-base を試す |
| `--exclude <pattern>...` | スキャン対象から除外するパスのグロブ（手順 1-2 の `scan_tests.mjs` のみ）。`--targets` 経由で解決されたテストにも効く。パス全体との完全一致で判定し、`*` は `/` にもマッチする（`src/generated/*` は `src/generated/a/b.test.ts` も除く）。大文字小文字は区別し、先頭の `./` は除いた形で照合する |
| `--spec <path>...` | 仕様・設計資料（ファイルまたはディレクトリ）。テストがどの命題を固定しているかの対応付けに使う |
| `--known-issues <path>` | 既知の不具合情報。過去に壊れた箇所は、テストが無いことの重要度を上げる根拠になる |
| `--answers <path>` | 前回の「未解決の質問」への回答（`Q1: ...` の形式）。**再評価モードに入る** |
| `--previous <path>` | 前回のレビュー結果。回答が影響しない指摘をそのまま引き継ぐために使う |
| `--use-cache` | `.claude/test-review/*.json` を再利用し、機械検出（手順 1）をスキップする。コードが変わっていない再評価で使う |
| `--implementer <agent-name>` | 実装者への問い合わせ先（手順 2.5 の ②）。省略時は問い合わせず、記録のみで判断する |
| `--test-json <file>` | Vitest / Jest の JSON レポート。**複数指定すると実行間のばらつき・不安定さを比較する** |
| `--nextest-json <file>` | cargo nextest / cargo test の libtest JSON。複数指定可 |
| `--coverage-lcov` / `--coverage-json` | LCOV（llvm-cov, tarpaulin, vitest）/ istanbul coverage-final.json |
| `--mutation-json <file>` | Stryker の report JSON または cargo-mutants の outcomes.json |
| `--slow-threshold-ms <n>` | 遅いテストの閾値（既定 1000） |

レポート系引数は任意である。渡されなかった種別はスクリプトが `not_measured` として返すので、**「未計測」と「問題なし」を区別して報告する**。レポートの生成コマンドは `references/report-inputs.md` にまとめてある。レポートが渡されていない場合は、該当コマンドを出力に記載する（実行はしない。実行するかどうかは読み手が決める）。

## 再評価モード（`--answers` が渡された場合）

「根拠が足りず判断できない」で終わった項目に答えが付いたときの経路。**全体をやり直さない。** やり直すと、回答と無関係な指摘の確信度や並び順が揺れ、何が変わったのかが読めなくなる。

1. `--use-cache` があれば手順 1 をスキップし、`.claude/test-review/*.json` を再利用する（コードが変わっていない前提。変わっているなら付けずに再実行する）
2. `--previous` の前回結果を読み、回答が影響する指摘を特定する。影響しない指摘は**判断も文面もそのまま引き継ぐ**
3. 影響する指摘だけを、回答を根拠に加えて再判断する。回答で確信度が上がる／区分が「人による最終判断」から外れる／指摘が消える、のいずれかが起きる
4. 回答から新しく導かれた指摘は追加してよい（例: 回答が述べた無効化の原因が、コードの実行経路と一致しない）。**新規と明記し、回答を根拠として引用する。** 回答と無関係な新規指摘は追加しない（それは再評価ではなく再レビューであり、引き継ぎの意味が消える）
5. 出力の冒頭に**変更点**を置く（どの質問に答えが付き、どの指摘がどう変わったか）。答えが付かなかった質問は質問節に残す

回答によって指摘が消えることもある（例: `#[ignore]` の理由と復帰条件が判明した → 復帰条件が不明という部分は解消され、無効化そのものの指摘は残る）。消えた指摘も変更点に記載する。前回あった指摘が黙って消えると、読み手は見落としと区別できない。

### 回答ではなく修正が返ってきたら reject する

**質問は修正要求ではない。** 求めているのは当時の判断（情報）であり、コードが変わっても「なぜそうなっていたか」は回収できない。再評価は回答を根拠に読み直す処理なので、入力が修正であれば成立しない。

`--answers` の内容が問いへの答えではなく修正の報告（「直しました」「該当コミット: <sha>」だけで意図の記述が無い）である場合、再評価せず次のメッセージで終える。

> test-review: Q<N> に対して修正が返っていますが、質問は修正要求ではありません。求めているのは当時の判断（なぜその状態だったか）です。修正後のコードは新しいレビュー対象なので、`--answers` を付けずに再実行してください。意図が判明している場合は、その内容を回答として渡してください。

コードが変わった状態を「回答」として受け取ると、二重に壊れる。判断材料が回収されないまま解消扱いになり、かつ `--previous` の指摘が現在のコードと対応しなくなる。

reject の際、記録（コミット本文・PR）を照会して当時の判断が見つかった場合は、その事実をメッセージに添える。**記録から見つかった判断は、誰が持ってきたかに関係なく正当な根拠である**（手順 2.5 の ①）。ただし reject 自体は変えない。`--answers` を外した通常実行に入れば、① がその記録を拾って質問ごと解消する。

## 実行手順

### 0. 判断基準 knowledge の参照

レビュー観点の根拠となる既存 knowledge を `mcp__knowledge__search_knowledge` で検索する（例:「テスト 戦略 単体 統合」「検証手段 選択基準」）。ヒットしたら `mcp__knowledge__read_knowledge` で本文を読み、観点の重み付けに反映する。knowledge の内容そのものは出力に含めない。

### 1. 機械検出（スクリプト実行）

`SKILL_DIR` はこのスキルのディレクトリ（既定 `~/.claude/skills/test-review`）、`OUT` は対象リポジトリ直下の `.claude/test-review/`。3本ともレビュー対象のコード・テストを変更せず、テストも実行しない（書き込みは `$OUT` 配下の JSON のみ）。Node.js 20 以降の標準モジュールのみで動く（`node:util` の `parseArgs` が安定版になったのが 20.0.0）。

```bash
# 1-1. 変更コード側の検証対象候補（分岐・例外経路・境界値候補・対応テストの有無）
node "$SKILL_DIR/scripts/changed_targets.mjs" [<path>...] [--base <ref>] --out "$OUT/targets.json"

# 1-2. テストコードの静的スキャン
#      （無効化・focused マーカー・空/弱い検証・モック偏重・外部依存・分類乖離・重複）
#      外部依存はテスト本文だけでなく beforeEach 等の準備フックとファイル先頭の初期化も見る
node "$SKILL_DIR/scripts/scan_tests.mjs" --targets "$OUT/targets.json" [<追加パス>...] [--exclude <PATTERN>]... --out "$OUT/scan.json"

# 1-3. 既存レポートの正規化・集計（実行時間・ばらつき・カバレッジ・ミューテーション）
node "$SKILL_DIR/scripts/collect_metrics.mjs" [レポート引数...] --targets "$OUT/targets.json" --out "$OUT/metrics.json"
```

1-2 は `--targets` から対象テストを解決する（`changed_test_files` と `targets[].candidate_tests[].file`）。差分に含まれないがレビュー対象の実装を検証しているテストを取り逃さないための経路なので、`--targets` は省略しない。ユーザーがテストディレクトリを明示した場合だけ、追加パスとして併せて渡す。

出力 JSON の `findings[]` はそのまま「自動検出」区分の指摘の素材になる。`severity_hint` は並べ替えの初期値であって最終判定ではない。変更の重要度（決済・認証・データ破壊の可逆性）を踏まえて上下させ、上下させた場合は理由を書く。

スクリプトが検出できない範囲を把握しておく。いずれも 2 で LLM が読む対象になる。

- テスト本文には現れず、呼び出し先の実装が持つ外部依存（テストが間接的に DB・時刻に触るケース）
- モックの設定だけで検証が無いテストのうち、検証がヘルパー関数に切り出されているもの
- 対応テストの推定はファイル名・import・関数名の一致に基づくため、命名が離れていると `has_candidate_test: false` になりうる
- `declared_level` はパスからの推定であり宣言そのものではない。`tests/` `__tests__/` 配下は単体と統合が混在しうるため `unknown` になり、その範囲では `level_mismatch` は出ず `external_dependency` として出る
- 引用符を含む正規表現リテラル（`s.split(/"/)` など）以降は、そのテスト本文の解析が崩れる。該当テストで `no_assertion` が出た場合は実物を開いて確認する
- 本文を持たず関数参照だけを渡すテスト（`it("name", helperFn)`）は解析できないため件数に載らない。テスト件数が体感より少ない場合はこの形を疑う
- カバレッジ・ミューテーションの突き合わせ結果が空でも「未検証行なし」とは限らない（レポートのパス基準が異なる場合。`references/report-inputs.md` の最終節を参照）

### 1.5. 機械検出だけで打ち切る判断（LLM レビューへ進む前のゲート）

機械検出は安い。LLM レビューは対象コードを読み込むため高い。機械検出の時点で先に直すべき欠陥が出ているなら、**LLM レビューへ進まずそこで報告を返す**。直したあとに再実行すれば、変わった前提のうえで読める。

次のいずれかに該当したら、手順 2 へ進まず、下記の**打ち切り時の出力**だけを返して終える。

| 打ち切る条件 | 理由 |
|---|---|
| `metrics.json` に `failing_test` がある | テストが失敗している状態のカバレッジ・変異・実行時間は、いま守れている範囲を表さない |
| `scan.json` に `focused_test` がある | 実行対象がファイル単位で欠けているため、緑であることの意味が確定しない |
| `scan.json` の `disabled_test` が有効テスト数を上回る | 検証の大半が動いていない。深掘りの前に無効化の理由を確定させる必要がある |
| 対象テストが 0 件（`scan.json` の `tests` が空） | 読む対象が無い。パス指定か `--targets` の解決を先に直す |

#### 打ち切り時の出力

通常の出力契約は使わない。指摘ごとに根拠・影響・確信度・区分を書こうとすると、そのためにコードを読むことになり、省いたはずの LLM レビューが実質的に走る。次の 3 つだけを書く。

1. 打ち切り条件と観測値（どの kind が何件、所在はどこか）
2. 機械検出の全件を**スクリプト出力のまま**転記した表（kind / 所在 / evidence）。解釈・言い換え・影響の記述を加えない
3. 続けるために確定させる必要がある前提（上の条件に対応するもの）

このモードでは次を行わない。**対象コード・テストを開いて読まない**（`scan.json` / `metrics.json` / `targets.json` の値のみで書く）。手順 2.5 の ①②（記録の探索・実装者への問い合わせ）も行わない。指摘の重要度の並べ替えもしない（`severity_hint` のまま）。

該当しなければ手順 2 へ進む。

### 2. LLM レビュー

`targets.json` / `scan.json` / `metrics.json` を読み、指摘候補の元になったテストコードと実装コードを実際に開いて確認する。JSON だけで指摘を書くと、根拠の引用が実物と食い違う。

観点と判断基準は `references/review-lenses.md` を読んで適用する（テストの深さとレベル配置、上位テストによる下位ロジックの代替、テスト意図の表現、実装内部手順への結合、生き残った変異の解釈、指摘と質問の切り分け）。

仕様資料・既知の不具合情報がユーザーから渡されている場合は、テストがその仕様のどの命題を固定しているかを対応付ける。渡されていない場合、仕様の妥当性は判断しない。

**判断材料が足りない項目は、推測で埋めずに質問にする。** 「無効化の理由が不明」「境界の期待値が仕様から読めない」「CI の実行対象か確認できない」を推測で指摘に混ぜると、根拠のある指摘と同じ強さで読まれてしまう。ただし質問を成果物に積んで終えるのでは、根拠が集まらないままレビューが止まる。**答えを取りに行く**（手順 2.5）。

### 2.5. 足りない根拠を集める

ここで足りないのは**実装についての根拠**である（このテストが何を止めているか、この分岐が何を意図しているか、この差分が何を直しているか）。仕様の妥当性は扱わない（`spec-review` の領分）。宛先は **渡された資料**・**記録**・**実装者** の 3 つで、この順に当たる。人は実装していないので答えを持たず、聞く段は存在しない。

**⓪ 渡された資料を読む（探索の前）**

`--spec` / `--known-issues` / `--answers` が渡されていれば先に読む。ここで埋まる根拠を ① ② で探し直すのは無駄で、しかも資料と食い違う推測を混ぜる余地を作る。

- `--spec`: テストが固定している命題と仕様の命題を対応付ける。仕様にある命題でテストが無いものは、根拠付きの指摘になる（推測ではなく資料との差分）
- `--known-issues`: 過去に壊れた箇所と未検証箇所が重なるなら、その重なりを根拠として重要度を上げる
- `--answers`: 前回「未解決の質問」に挙げた項目の回答。回答が根拠になった項目は指摘へ格上げし、質問節から外す

**① 記録を探す（資料で埋まらなかったもの）**

| 問い | 探す先 |
|---|---|
| 無効化（`it.skip` / `#[ignore]` / `describe.skip`）の理由と復帰条件 | `git log -S "#[ignore]"` / `git blame` / そのコミットの PR 本文 |
| この差分が何を直す変更か | コミットメッセージ / PR 本文 / リンクされた issue |
| CI が何を実行しているか（`.only` の影響、レポートに現れないテスト） | CI 設定 / テストランナー設定（`allowOnly` 等）/ `git ls-files` で追跡状態 |
| レポートの採取リビジョン | レポート内のパス・件数と作業ツリーの突き合わせ |
| 過去に検討して却下された設計 | セッションログ（`find-session` スキル）/ 設計資料 |

**② 実装者に問う（記録に無かったもの）**

`--implementer` が渡されているか、差分を書いたエージェントが同一セッションに生きているなら、そこが窓口である。LLM 同士なので往復が安く、実装時の判断（なぜその依存を残したか、なぜそのテストを止めたか）はそのコンテキストにしか無い。`SendMessage` で問う。宛先が分からない場合は問い合わせず、次へ進む。

実装者が居ない（過去セッションで、ログにも残っていない）場合、それは**「記録が残っていない」という確定した事実**である。推測せず、その事実を指摘として書く。無効化の理由が読めない状態は、次に触る人が復帰の可否を判断できないため、判断材料の欠落そのものである。

得られた答えは根拠として扱い、出所を明記して引用する（`git log <sha>` / `PR #123` / 実装者の回答）。

**人に聞く段は無い。** 実装したのは人ではなく、実装上の選択（境界をどちらに倒したか、どの依存を残したか）は人の記憶にない。記録にも実装者にも無いなら、そこで確定するのは「その意図がどこにも固定されていない」という事実であって、誰かに決めてもらう必要はない。決定を調達するのは実装者の仕事であり、レビューは根拠の欠落を指摘するところで閉じる。

① と ② は `Bash` / `Read` / `Grep` / `SendMessage` で完結するため、サブエージェントとして実行中でも同じように動く。対話可否による分岐は無い。

### 3. 出力

下記の出力契約に従って報告する。

## 出力契約

冒頭に対象範囲と計測状況のサマリを置き、続けて指摘を**重要度の高い順**に並べる。

```md
## 対象と計測状況

- 対象: <差分 base...HEAD / 指定パス>（実装 N ファイル / テスト M ファイル / テストケース K 件）
- 計測済み: 実行結果 N 回分 / カバレッジ / ミューテーション
- 未計測: <not_measured の内容>（この範囲は「問題なし」ではなく「未確認」）

## レビュー候補

### 1. <指摘の要約（断定形にしない）>

- **違反している根拠**: 何に反しているか（仕様・計測値・原則）と、その所在（`file:line`・テスト名・レポートの値）。実測値はそのまま引用する
- **想定される影響**: この状態が続いたときに検出できなくなる不具合の種類
- **確信度**: 高 / 中 / 低（＋その水準になった理由）
- **区分**: 自動検出 / LLMレビュー / 人による最終判断

## 未解決の質問

答えが得られず、かつ答えがあれば指摘が変わる項目だけを残す（資料・記録・実装者から取れたものは根拠へ、記録も実装者も無いものは「記録が残っていない」指摘へ移っているはず）。

**この節は再実行の入力になる。** 各項目に ID を付け、問いの形と、何を探して見つからなかったかを書く。回答を得た側は同じ ID で答えを書いたファイルを作り、`--answers <path>` で渡して再実行すれば、その答えを根拠に読み直せる。

```md
- **Q1** `src/quota.rs:22` の `#[ignore]` は失敗の一時回避か、恒久的に不要と判断したものか
  - 探した先: `git log -S "#[ignore]"`（該当コミット無し）/ PR 本文（記述無し）/ 実装者（宛先不明）
  - 答えで変わること: 一時回避なら「変更した境界が未検証」の確信度が中→高になる
  - 求めているもの: 当時の判断（情報）。コードの修正ではない
```

質問に「求めているもの」を書くのは、回答側が修正で応じるのを防ぐためである。修正が返ってきた場合の扱いは再評価モードの節を参照。

### 対応内容を書かない理由

根拠が揃っている指摘に対する対応は、その違反状態を解消することであり、指摘と根拠から一意に決まる。手段（どのテストをどのレベルに足すか、どう設計を変えるか）はそこから実装者が導く領域で、レビュー材料が指定するものではない。

選択肢を並べるのも同じ越権になる（推奨が 3 つに増えるだけである）。「許容」を選択肢に置くのも誤りで、根拠への違反を許容するかはレビューの外側の判断になる。

読み手が実装者側の LLM である場合、手段を教える価値はない。解消の方法は既に知っており、必要なのは「何に反しているか」と「その所在」である。逆に手段を書くと、根拠から導いた対応ではなくレビュー側の案の実装になり、その案が前提にしている事情（レビュー時点では観測できないリリース時期・体制・機能の寿命）が検証されないまま持ち込まれる。

根拠が揃っていないなら、指摘にせず「質問」へ回す。判断は 2 分岐しかない。

| 状態 | 出力先 |
|---|---|
| 根拠が揃っている（仕様・計測値・原則に反していると言える） | レビュー候補（違反・根拠・影響・確信度・区分） |
| 根拠が揃っていない（仕様が読めない、無効化の理由が不明、実行対象が不明） | 質問（何を答えればレビューが進むか） |

例（指摘: 変更した割引計算の分岐に単体テストが無い）:

- 追加テスト: `monthlyPrice` を直接呼ぶ単体テストで境界（9/10 席、49/50 席）を固定する。純関数なので依存の準備は不要。前提は「この割引ルールが今後も残る」こと
- 設計改善: 割引ルールを個別の関数へ分離し、それぞれを検証できる形にする。前提は「ルールが今後増える」こと。テストの追加より先に構造を変えるので着手コストは高い
- 許容: 統合テストが金額の合計値を固定しているため、丸ごと壊れれば検出される。前提は「境界の 1 ずれを見逃してよい」こと。見直す条件は割引ルールが 3 つ目に増えたとき

## 禁止事項

- **テストを実行しない**。実行時間・不安定さ・カバレッジ・ミューテーションは既存レポートからのみ読む。レポートが無ければ「未計測」と書き、生成コマンドを出力に記載する
- **本番データ・外部サービスに触れない**。マイグレーション、シード投入、外部 API 呼び出しはいずれも行わない
- **自動修正しない**。テストの追加・書き換え・削除・スキップ解除は行わない
- **対応内容を書かない**。「こう直す」「追加テストを推奨」「この選択肢がある」はいずれも書かない。指摘は違反と根拠までで、解消の手段は実装者が導く
- **断定しない**。「テストが不足している」ではなく「この分岐は未検証であり、仕様上必要かの確認が必要」と書く
- **足りない判断材料を推測で埋めない**。根拠は `file:line`、テスト名、計測値、レポート値のいずれかに限る。埋まらないものは指摘に混ぜず「質問」節へ移す
