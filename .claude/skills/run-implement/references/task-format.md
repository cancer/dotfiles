# タスク定義ファイルの形式

計画と全体設計は `dev-workflow` の外で決まっている前提とする。`dev-workflow` はタスクの分解・依存の判断・設計判断をしない。define-tasks は次の Markdown 形式でタスク定義を書く。

```markdown
# 計画: <タイトル>

## タスク

### T1: <タスク名>
- 対象: <変更・作成するファイル>
- 完了条件:
  - p1_<短い名前>: <命題を 1 文で>
  - p2_deliverable: <成果物を定める命題を 1 文で>
- 契約: 提供 C1 / 利用 なし

### T2: <タスク名>
- 対象: ...
- 完了条件:
  - p1_<短い名前>: ...
  - p2_deliverable: ...
- 契約: 提供 なし / 利用 C1

## 契約

### C1: <契約名>
- 提供: T1 / 利用: T2
- 内容: <型・関数シグネチャ・API のパスと入出力・スキーマ・イベント・エラー種別・命名>
```

## 記述規則

- 各タスクは対象、完了条件、契約を持つ。タスクが提供・利用する契約がない場合は `なし` と書く。
- 完了条件の各行は、`verify-task` の `propositions.json` の `statement` にそのまま写せる命題である。`dev-workflow` はタスクごとに命題を `propositions.json` に書き、`verify-task` に命題を導かせない。成果物を確定するタスクには、各完了条件に成果物の命題 `pN_deliverable` を 1 行含める。例: 「`<ブランチ>` から `<base>` への PR が作成され、base と競合せず、CI が通っている」「`<ブランチ>` にコミットされている」。
- PoC 用のタスク定義には成果物の命題を含めない。PoC の完了は実測する仮定が決着したことであり、成果物の作成ではない。
- タスク同士の対象ファイルを重ねない。対象が重なるタスクは 1 つにまとめる。
- タスク間の依存は書かない。契約で分けられる全タスクは並列に実行する。契約を結べない組は 1 つのタスクにまとめる。
- 実測が要る仮定は通常のタスク定義に含めず、仮定ごとの PoC 用タスク定義に分ける。
