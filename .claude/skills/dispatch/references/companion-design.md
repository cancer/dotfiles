# companion の設計（合意版）

## 位置づけ

companion は会話コンテキストを固定する役。常駐し、聞き、解釈を State に固定し、足りない項目を聞き、固まったら State を渡す。ゴールを置くのはユーザー。工程の順序・作業の監督・検収は別の部品が持つ。

会話が既定の状態であり、渡す義務はない。依頼が一度も形にならなければ会話のまま終わる。

## 分担

| 担い手 | 担うもの |
|---|---|
| LLM（companion） | 会話、依頼の項目別の解釈、「種類の判定に進むか」の引き金 |
| Jev | 引き金が引かれたときの「成果物の種類」「解釈の項目の抜け」「解釈と引用・承認された提案との矛盾」「項目ごとの裏付け」 |
| 規則 | 閾値、項目の既定値、implement のときの工程ゲート（gate-catalog.md（同ディレクトリ））、ゲート間の依存 |

引き金を LLM に任せる理由: 見落としても「進めて」で走り、失うのは 1 ターン。走らせすぎても Jev を 1 回余計に呼ぶだけ。Jev の支出は会話のターン数ではなく「渡そうとした回数」に比例する。

速度の実測（同じ State、2 問）: Jev は `judge.py` 起動込みで 0.4〜0.9 秒、subagent は sonnet 10.6 秒 / haiku 18.0 秒。答えは一致。

## State

Jev と作業係が読む唯一の入力。

1. **解釈**: companion がユーザー発言から書いた項目別の内容（`interpretation.json`）。各項目に出どころ（引用 / 承認された提案 / 既定値）を付ける
2. ユーザー発言の引用（要約しない）。解釈の根拠
3. ユーザーが承認した提案: 一括承認（「それで」「B 案で」「全部」）が指す提案の原文と、承認した発言の組。承認された提案は確定事項に入る
4. 依頼の原文（issue 本文・コメント、仕様書、貼られた文書）
5. 事実
   - スクリプトが集めたもの: `.git` とマニフェストの有無、issue / PR の種別、計画書の有無、既存テストの有無
   - **作業係の報告**（ラベル付き）。報告内の提案は、ユーザーが承認するまで確定事項ではない

解釈を State の中心に置く理由: 原本の引用だけでは一括承認の中身が欠け、Jev はいつまでも「述べられていない」と判定し、作業係は原本を自分で解釈することになる。解釈は消せないので、State に書き出し、Jev が抜け・矛盾・裏付けのない内容を確かめる。ユーザーへの復唱はしない。裏付けの確認は Jev と重なり、長い復唱はユーザーに読まれないため。

## 1 層目: 成果物の種類（choice 1 問 + none）

会話が何で終わるかで 4 つ。

| 種類 | 会話の終わり方 | その先 |
|---|---|---|
| implement | コードが変わる | 統合後のワークフロー。plan / spike / review / PR は中の工程ゲート。既存 PR への対応は「対象が PR である implement」 |
| know | 答えを知って終わる（調査、コードベースの把握、仕様の点検） | research / explore / spec-review |
| write | 文書が残る | 執筆 |
| init | 新しいプロジェクトができる | init-project。作成先パスと作るものだけを確定し、系統の確認は init-project に任せる |

`none` が最上位、または最上位が閾値未満なら「何を受け取りたいか」を聞く。壁打ちは種類ではなく companion の素の状態。

複数の種類が続く場合（調べてから実装）は、引き金ごとに 1 つ渡し、結果を State に積み、次の引き金で次を渡す。順序の規則は持たない。

## 2 層目: 解釈の点検（noul、固定の問い）

問いと既定値は `scripts/catalog.json` に固定し、毎回同じ問いを使う。

- 種類ごとの項目（`items`）は、解釈の値に対して合否のはっきりした細かい問いを持つ（例: completion は「確認手段があるか」「範囲語でない終わりの状態があるか」）。落ちた問いの文が、そのまま「何が足りないか」の説明になる
- 項目は `default`（値と出どころ）を持てる。ユーザー発言・承認された提案に無い項目は既定値で埋め、聞かない。聞くのは既定値も無い項目だけ
- 各項目には共通の問い（`item_questions`）として「内容がすべて引用・承認された提案・既定値に裏付けられているか」も付く。裏付けのない内容がどの項目にあるかまで示すため、解釈全体ではなく項目ごとに問う
- 共通（`common`）: 解釈が引用・承認された提案と矛盾するか
- 止まったときは、項目・解釈の値・落ちた問い・既定値・聞く文を固定の書式で示す（`judge_state.py` が `message` に組み立てる）。スコアだけを示さない
- 一度聞いて答えを得た項目は、再判定で問いが通らなくても止めない
- Jev の判定が通ったら、復唱せずにそのまま渡す

工程ゲートが on になったときの追加項目（計画の粒度、レビューの比較基準など）は gate-catalog.md（同ディレクトリ） 側に置く。

## 3 層目

implement のときだけ gate-catalog.md（同ディレクトリ） の工程ゲート（G2 → G3 → G0 → G1 → G4〜G10）。

## 渡した後

作業係の報告を State に「作業係の報告」として積み、companion が要約して伝える。ユーザーの新しい発言が要件を変えるかは LLM が判断し、変えるなら確定事項に追記し、進行中の作業係へ伝える。

## 閾値

初期値 yes ≥ 0.7、no ≤ 0.3。外に出して運用で調整する。

## 決めていないこと

- State の「直近 N ターン」の N
- 閾値の実値
- dev-workflow / proto-workflow の統合の進め方（人間が入口で選ぶ理由が消えるので統合する方向までは合意）
