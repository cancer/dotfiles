# テスト駆動開発（TDD）

先にテストを書く。失敗するのを見る。通す最小限のコードを書く。

**核心**: 失敗するのを見ていないテストは、正しいものをテストしている保証がない。テストを後から書くと必ず即座に通り、「通った」という事実は何も証明しない。

## 鉄則

```
失敗するテストなしに本番コードを書かない
```

これが既定。最初からテストを先に書けば、以下の是正はそもそも要らない。

**実装を先に書いていることに気づいたら、その時点で実装の手を止める。** 書き足すほど未検証コードがコンテキストに積もり、テストが実装に引きずられ、あとの手当てが高くつく。止めた上で:

- **テストは実装をなぞらず、仕様（Step 0 の要件）からアサーションを書き起こす。** 実装に癒着したテストは、誤った振る舞いを正解として固定してしまう
- 仕様から起こすのが難しければ、**実装を見ていない fresh-context のサブエージェントにテストだけ書かせる**（実装アンカリングを外すため）
- テストが効くかは **red-green で確認する**（実装を一時 revert → 正しい理由で失敗 → 戻す → 通る）。ただしこれが示すのは「振る舞いの欠如を検出できる」ことだけで、「仕様として正しい」ことではない
- 実装を消すかは別判断。**消してもコンテキストからは消えず** un-bias にはならないので、汚い探索コードを書き直した方が速いときだけ消す（儀式にしない）

**ルールの文言に従うことと、ルールの精神に従うことは同じ**。「精神的にはTDDだから」で後付けテストを正当化しない。

### 例外（ユーザーに確認してから）

- 使い捨てのプロトタイプ
- 生成コード
- 設定ファイル

「今回だけスキップ」と思ったら、それは合理化。立ち止まる。

## RED-GREEN-REFACTOR サイクル

すべてのテストが通るまで、以下を1振る舞いずつ繰り返す。

### RED — 失敗するテストを書く

- 実装対象の振る舞いを検証する最小のテストを1つ書く。テストのみを書き、実装コードには触れない
- 1つの振る舞いだけを検証する（テスト名に「〜と〜」が入るなら分割する）
- 名前は振る舞いを表す（`test1` ではなく `retries failed operation 3 times`）
- モックではなく本物のコードをテストする（モックは避けられない時だけ）

### RED を確認する — 失敗を必ず観察する（省略禁止）

- テストを実行し、**失敗すること**を目で確認する
- 期待どおりの理由で失敗しているか（「機能が無い」ための失敗か、タイポ等のエラーではないか）を確認する
- **この時点で通ってしまうなら**、既存の振る舞いをテストしている。テストを書き直す（RED に戻る）

### GREEN — 最小限のコードで通す

- テストが通る最小限の実装を書く。きれいである必要はない。まず通すことが目的
- テストが要求していない機能・オプション・将来の拡張を足さない（YAGNI）
- テストを再実行し、**通ること**と、既存テストが壊れていないこと、出力にエラー・警告が無いことを確認する
- 通らないなら、テストではなく実装を直す

### REFACTOR — 整える

- テストが緑のまま、重複除去・命名改善・関数抽出を行う
- リファクタ後にテストを再実行し、緑を維持していることを確認する
- 振る舞いは足さない

## 失敗パターンと現実

| 言い訳 | 現実 |
|---|---|
| 単純すぎてテスト不要 | 単純なコードも壊れる。テストは30秒 |
| 後でテストを書く | 後書きは即通る。何も証明しない |
| 後書きでも目的は同じ | 後書きは「これは何をするか」、先書きは「何をすべきか」を問う。別物 |
| もう手動で確認した | アドホックは記録も再現も不可。網羅の証明にならない |
| もう書いたので実装に合わせてテストを書く | それは実装をなぞるテスト。仕様からアサーションを導く。実装に合わせると誤りごと固定する |
| 実装を見ながらテストを書く | 実装アンカリングでバイアスする。仕様から書く。難しければ fresh-context に書かせる |
| テストが難しい | 難しいのは設計が悪い兆候。インターフェースを簡素化する（→ knowledge `tech/design`） |
| 全部モックが要る | 結合が強すぎる。依存を注入して差し替え可能にする |
| TDDは遅い | デバッグより速い。回帰も即検出できる。実用的なのは先書き |

## Red Flags — 手が止まったら見直す

- テストより先に本番コードを書いた
- 実装の後にテストを書いた
- 実装を見ながらテストを書いている
- テストが最初から通った
- なぜテストが失敗したか説明できない
- 「今回だけ」「精神的にはTDD」「これは特別」と考えている

**いずれも「実装の手を止め、仕様からテストを書き起こし直し、red-green で確かめる」の合図**。

## 完了前チェックリスト

- [ ] 新しい関数・メソッドにはテストがある
- [ ] 各テストが実装前に失敗するのを観察した
- [ ] 各テストが期待どおりの理由（機能欠如）で失敗した
- [ ] 通す最小限のコードを書いた
- [ ] 全テストが通り、出力にエラー・警告が無い
- [ ] エッジケース（null/undefined・空・境界値）とエラー経路を網羅した

チェックが埋まらない = TDDを飛ばしている。やり直す。

## バグ修正での使い方

バグを見つけたら、まずそのバグを再現する失敗テストを書く。RED を確認し、修正して GREEN にする。テストが修正の証明であり、回帰の防止になる。テストなしにバグを直さない。

## 強制の限界

このスキルはプロンプト上の規律であり、確実な強制は担保しきれない（長文脈で指示が薄れる・完了圧力で飛ばす）。同じ違反を繰り返すなら、pre-commit hook や CI のテスト必須パスなど帯域外の機構で裏打ちする。
