## 引数

`$ARGUMENTS` を依頼内容として受け取る。省略された場合は会話中の依頼を使う。

## 引数の形式

`$ARGUMENTS` は次のいずれかとする。

- State ファイルの絶対パス
- issue の URL または番号
- 依頼内容の自由記述

State のパスが渡された場合はその内容を読む。issue の URL または番号が渡された場合は issue の内容を読む。自由記述または会話中の依頼が渡された場合は、その記述を読む。

## 実行手順

1. 引数または会話中の依頼を読み、依頼内容を把握する。
2. リポジトリのブランチ戦略を探す。`CLAUDE.md`、`CONTRIBUTING.md`、`docs/` 等を読み、ベースブランチとブランチ名の規則を確認する。
3. ブランチ戦略から依頼内容に当てはまる規則を選ぶ。その規則に従ってベースブランチと名前を決める。たとえば機能追加は `develop` から `feature/...`、本番不具合は `main` から `hotfix/...` とする戦略なら、依頼の種類に合う規則を選ぶ。ベースブランチと名前はユーザーに質問せず決める。
4. 戦略が見つからない場合は、デフォルトブランチをベースにする。名前は「フォールバック命名規則」で決める。デフォルトブランチは `gh repo view --json defaultBranchRef --jq .defaultBranchRef.name` で取得する。`gh` が使えない場合は `git symbolic-ref refs/remotes/origin/HEAD` を使い、`refs/remotes/origin/` を除いた名前を使う。どちらでも取得できない場合は失敗として報告する。
5. リモートがあれば `git fetch --all` を実行する。その後、ベースブランチが存在することと、同名のローカルまたはリモートブランチがないことを確認する。同名ブランチがある場合、ベースブランチが存在しない場合、その他ブランチを安全に作成・切替できない場合は、ブランチを作らず理由を報告して終える。
6. リモートがある場合は fetch 後のベースブランチの最新のリモート追跡ブランチを起点にする。その参照がない場合は失敗として報告する。リモートがない場合はベースブランチのローカルブランチを起点にする。決めたベースブランチから新しいブランチを作って切り替える。今いるブランチを起点にしてはならない。
7. 成功時は下の「報告の形式（C1）」で報告する。

## 報告の形式（C1）

成功時は次の3項目を報告する。

- `ブランチ: <name>`
- `ベース: <base>`
- `根拠: <戦略文書のパス:行 と当てはめた記述> | フォールバック（ブランチ戦略の記載なし）`

戦略を適用した場合は、根拠に戦略文書のパス、行番号、依頼に当てはめた記述を示す。フォールバックを使った場合は `根拠: フォールバック（ブランチ戦略の記載なし）` と報告する。

失敗時はブランチを作らず、次の形式で理由を報告して終える。

- `失敗: <理由>`

## フォールバック命名規則

プロジェクトにブランチ戦略の定義がない場合に使用する。

- 形式: `topic/<issue-number>/<短い説明>`（例: `topic/42/add-dark-mode`）
- issue番号が不明な場合: `topic/<短い説明>`（例: `topic/fix-login-redirect`）
- `<短い説明>` は英語・ケバブケースで簡潔に
