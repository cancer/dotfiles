プロトタイプ・PoC・デモを、速度とコストを優先して作り切るワークフローを遂行してください。
要件定義の品質は `dev-workflow` と揃える。短縮するのは検収の多層化・PR の儀式であり、要件定義と TDD を短縮しない。

## 引数

$ARGUMENTS

## 1. 適用の判定（着手前）

### 起動条件

- プロトタイプ・PoC・デモの作成依頼では、ユーザーがスキル名を指定しなくても自発的に使う。
- 判定は依頼の目的で行う。動くものを早く得て、判断材料にする・見せる・仮定を確かめることが目的なら本スキルの領分である。
- 成果物をあとで育てるかどうかは判定に使わない。育てる前提のプロトタイプも本スキルで作る。本番化する段になったら「## 9. 昇格」で `dev-workflow` へ引き継ぐ。
- `dev-workflow` へ回すのは、最初から本番投入するコードとして作る依頼である。
- 判断がつかなければ `AskUserQuestion` で確認し、頭脳が都合のよい方へ解釈しない。

### 初期構築の判定

空ディレクトリからの新規プロジェクト初期構築は `init-project` の領分である。
依頼文の「新しく作る」だけで決めず、対象ディレクトリの状態を確認する。

```bash
test -e "$DIR/.git" && echo HAS_GIT; test -e "$DIR/package.json" -o -e "$DIR/Cargo.toml" && echo HAS_MANIFEST
```

- `.git` もマニフェストも無い場合は、初期構築として `init-project` へ回す。
- どちらかがある場合は、既存プロジェクトのプロトタイプ作成として本スキルを続ける。
- `$DIR` が確定していなければ、確認を終えるまで生成コマンドや委任を始めない。

### GitHub 参照の同定

引数が GitHub の番号なら、issue と PR が同じ番号空間を共有するため、種別を確認してから依頼文を書く。

```bash
gh api repos/<owner>/<repo>/issues/<番号> --jq '{type: (if .pull_request then "pr" else "issue" end), title, state}'
```

- issue なら本文とコメントを要求の起点にする。
- PR なら、レビュー対応・続きの実装・取り込みのどれかを確定する。
- URL や `owner/repo#番号` でも、対象と要求が曖昧なら `AskUserQuestion` で確認する。

## 2. 役割分担

**あなたは頭脳であり、手足は Codex である。**

- 頭脳は要求の確定、依頼文の設計、モデルと推論量の選択、検収の判断、報告を担う。
- Codex は調査、分解、実装、テスト、lint・型検査、git 操作の実務を担う。
- 委任経路は `delegate-to-codex` のみとする。別経路へ退避しない。
- 頭脳は要件を確定する。要件の解釈を Codex に委ねない。
- 頭脳は実装の Edit / Write を行わない。小さな実装でもこの分担を崩さない。

## 工程の並列化（全フェーズ共通）

**計画に列挙された工程の順序は、クリティカルパスではない。** 計画の一覧は読み手が追える順に並べたものであり、実行順の制約を表していない。前工程の出力が無ければ着手できないかという真の依存で判断し、依存の無い工程は並行して走らせる。

次の工程は、互いの出力を必要としない限り並行してよい。

- プロジェクト規約（`CLAUDE.md` など）の読み取りと、分解計画の委任。
- 依存の無いタスクの実装。
- 独立したタスクどうしの検収。先に報告が返ったタスクから検収する。
- 読み取りだけの委任。同一ツリーで並走してよい。

依存のあるタスクは依存元の完了と検収を待つ。同一の作業ツリーへ書き込む委任も直列にする。

**依存は「同じファイルを触るか」ではなく、境界の契約で切る。** 契約には型・シグネチャ・API・スキーマ・イベント・エラー種別・命名を含む。契約は頭脳が先に確定し、その内容を両側の依頼文へ書き切る。契約を確定できない場合は仮置きで並列化せず、直列に倒す。

並列化を理由に次の規律を緩めない。

- 書き込みを伴う委任はタスクごとに worktree を分ける。
- 機械的チェックは頭脳が自分で実行する。
- TDD とユニットテストを維持する。

## 3. 要件定義（dev-workflow と同等の厳密さ）

速度は曖昧な発注で稼がない。曖昧な発注は、プロトタイプを作り直すコストを増やす。

### 分解と調査

1. プロジェクトの `CLAUDE.md`、ブランチ規約、既存の実装パターン、テスト方法を確認する。
2. `delegate-to-codex` で分解計画を `-s read-only`、推論量 `max` で委任する。
3. 分解計画には、対象の読み込み結果、対応一覧、依存、対象ファイル、検証方法を含めさせる。
4. 計画を頭脳が読み、要求との一致と依存の妥当性を判断する。計画の採否は委任しない。

### 完了条件と対象外

- 完了条件を二値に落とす。「何が動けば完成か」を、コマンドと期待出力、または操作手順と観測結果で判定できる形にする。
- 完了条件は依頼文へ書く。実行して合否が一つに決まらない表現を残さない。
- やらないことを列挙する。認証、永続化、エラー処理、性能、対応環境など、今回作らないものを明記する。
- スコープを広げる提案を Codex に委ねない。対象外を増やす必要が出たら、ユーザーへ確認する。

### 実測が必要な仮定

次のいずれかに当たる仮定を、分解計画で列挙させる。

- 公式ドキュメントが可否を明言せず、文献調査を重ねても決まらない挙動に依存する。
- 採用する技術・基盤・ライブラリが、実行環境で成立するか未確認である。
- 性能・容量・レイテンシの要件を、計測なしには判定できない。
- 複数の設計案の採否が、実測値でしか決まらない。

「調べれば決まる」ものは実測に回さず、read-only の調査で決着させる。
実測が必要なら、仮定の決着そのものを目的にする。別工程として長く止めるのではなく、最初のタスクを仮定を決着させる最小の実装に置く。
合否は、Codex の要約ではなく、応答・計測値・エラーなどの生の出力で頭脳が判定する。

### 曖昧さと境界

- 曖昧な点や複数の解釈がある点は、`AskUserQuestion` でユーザーに確認する。頭脳が勝手に選ばない。
- 境界契約の確定と依存判断は「工程の並列化」に従う。

## 4. 省くものと、その代償

削るものと、代わりに失う検証を完了報告に残す。ユニットテストと TDD は省かない。

| 省くもの | 代わりに何をするか / 失うもの |
| --- | --- |
| `verify-task` / `test-review` / `code-review` の委任と反復 | 頭脳が `git diff` と機械的チェックを自分で行う。設計品質とテスト妥当性は検証されない |
| 統合後レビュー | 並列タスクの統合後は機械的チェックと完了条件の確認だけを行う。結合時の整合性レビューは行わない |
| PR 粒度の設計・複数 PR 分割 | 作業ブランチへのコミットで止める。PR 用の分割とレビューは行わない |
| 推論量 `max` の既定 | 実装は `medium` を既定にし、要件定義と分解だけ `max` にする。実装の判断量は意識的に絞る |

## 5. 実装委任

### 既定の進め方

- 分解計画の依存から、同時に着手できるタスクを依存グラフで確定する（計画の並び順で決めない）。依存が計画に書かれていなければ「未確定」として頭脳が依存を置く。
- 同時に走らせる書き込みタスクは、タスクごとに `git worktree` を切り、`delegate-to-codex` の `--cwd` をそのツリーへ向ける。ペインを分けても作業ツリーは共有されるので、ペイン分離は並列化の根拠にならない。
- 依存のあるタスクは依存元の完了（検収込み）を待って発注する。
- タスクが 1 つだけなら worktree を切らず作業ブランチで進めてよい。
- 読み取りだけの調査は同一ツリーで並走できる。境界契約を依頼文へ書き切る。
- 着手前にブランチを確認し、デフォルトブランチなら `create-branch` 相当で作業ブランチを作る。

### 依頼文に必ず含めるもの

依頼文は単体で完結させる。Codex はこの会話を見ていない。

- 実装者に読ませる絶対パス: `/Users/cancer/.claude/skills/write-code/SKILL.md`。
- TDD の手順として `/Users/cancer/.claude/skills/test-driven-development/SKILL.md` に従わせる。
- ゴール、二値に落とした完了条件、やらないこと、対象ファイル、触ってはいけない範囲。
- プロジェクトの `CLAUDE.md` から読んだ固有ルールの内容そのもの。パスだけで済ませない。
- 依存インストール、ビルド成果物、lockfile、キャッシュなどの副産物を許すか、消して戻すか。
- git 操作の範囲。コミットは許可し、push は禁止する。squash もしない。
- issue 起点なら、コミットと明示依頼があって作成する PR 本文に `Closes #<番号>` を含める。PR を作成した場合は完了後に issue へ PR 報告コメントを投稿する。
- 完了前に lint / format check、型検査、ユニットテストを実行し、緑を確認すること。全出力の貼り付けは求めない。

実装者はプロトタイプでも TDD とユニットテストを維持する。実装コードより後にテストを足す発注にしない。
依頼文に必要以上の自由度を残さない。判断を任せるほど、速度優先のはずの作業が調査と手戻りへ変わる。

### 発注前の選択

- 実装の推論量は `medium` を既定にする。要件定義と分解計画は `max` にする。
- 依頼文の内容に対して選択したモデルと推論量、その理由を、発注前にユーザーへ短く伝える。
- モデルと推論量は規模ではなく、必要な判断量と依頼文の一意性で決める。
- 大きなツール出力を生成させない。ファイルは検索または必要な範囲だけ、検査結果は合否と該当箇所だけ報告させる。

## 6. 検収（1周で決める）

Codex の報告は自己申告であり、成果の証明ではない。報告を読んで完了にしない。

検収はタスクごとに独立し、先に報告が返ったタスクから始める。他タスクの完了を待たない。

1. `git diff` で実際の変更を読む。対象ファイルと触ってはいけない範囲を突合する。
2. lint / format check、型検査、ユニットテストを頭脳が自分で実行し、生の出力を見る。
3. 実行できなかった検査は「未実行」と記録し、PASS と読み替えない。
4. 要件定義で二値にした完了条件を、頭脳が実際に実行して確認する。
5. 設計品質レビュー、テスト妥当性レビュー、統合後レビューは回さない。未検証の範囲として報告する。

`git diff`、機械的チェック、完了条件の確認で指摘があれば、新しいスレッドへタスク単位で一度だけ差し戻す（1 周はタスク単位で数える）。
差し戻し依頼文には、元の依頼文の絶対パス、実装時に確定した判断、指摘と根拠、触ってはいけない範囲を含める。
差し戻し後も収束しなければ、追加の差し戻しへ進まず停止し、`dev-workflow` へ切り替えるか続行するかをユーザーへ確認する。

複数タスクを並列にした場合は、各タスクの検収後に Codex へ統合を委任し、依存順に作業ブランチへマージさせる（squash しない）。統合後の作業ブランチで、頭脳が機械的チェックと完了条件の確認を自分で実行する。統合で問題があれば、同じ 1 周ルールで差し戻す。

## 7. 出口

1. 作業ブランチへコミットさせる。`gh-commit` 相当で行い、squash しない。
2. Codex のペインを片付ける。worktree は検収を終えたタスクからその時点で片付ける。中断時や判断待ちでも、走っていないものを残さない。
3. PR は作成しない。「PR にして」と明示された場合だけ `create-pr` を回す。
4. 完了報告を行う。ブランチ名とコミットを含める。

## 8. 完了報告に必ず含めるもの

- 実施作業の要約、確定した完了条件、判定結果、実行したコマンドと生の結果。
- lint / format check、型検査、ユニットテストのコマンドと合否。未実行は明記する。
- 使ったモデルと推論量。
- 設計品質レビュー、テスト妥当性レビュー、統合後レビューを行っていないこと。
- やらないことに置いた範囲と未実装の機能。
- 差し戻しの有無と、その内容。差し戻しは最大 1 周である。
- 並列に走らせたタスクと依存関係（直列にしたものはその理由）。
- ブランチ名とコミット。PR を作成した場合は URL と、明示依頼があったこと。

## 9. 昇格（プロトタイプを本番化するとき）

成果物をそのまま育てる判断が出たら、`dev-workflow` へ引き継ぐ。
引き継ぎ時には、本スキルで省いた `verify-task` / `test-review` / `code-review` と統合後レビューが未実施であることを明示する。
本スキルのコミットを品質保証済みの本番コードとして扱わない。未検証範囲を明らかにすることが昇格の出発点である。

## 10. 完了前チェックリスト

- [ ] 依頼の目的で本スキルの適用を判定し、育てるかどうかで振り分けずに着手した。
- [ ] 空ディレクトリからの初期構築を `init-project` へ振り分けた。
- [ ] GitHub 番号の issue / PR を `gh api` で確認した。
- [ ] 完了条件を二値に落とし、依頼文に書いた。
- [ ] 依存グラフから同時着手できる工程を洗い出し、依存の無いものを並行して走らせた（計画の列挙順のまま直列に流していない）。
- [ ] 並列に発注したタスクの境界の契約を先に確定し、両側の依頼文へ書き切り、書き込みを伴う並列委任を worktree で分離した。
- [ ] やらないことを列挙し、依頼文に書いた。
- [ ] 曖昧な点を自分で解釈せず、ユーザーに確認した。
- [ ] 実装・調査をすべて `delegate-to-codex` へ委任した。
- [ ] 依頼文に `write-code` の絶対パス、副産物の扱い、git 操作の範囲を書いた。
- [ ] TDD とユニットテストの緑を実装者に確認させた。
- [ ] 検収を `git diff` と、頭脳が自分で実行した機械的チェックで行った。
- [ ] 完了条件の実行確認を自分で行い、生の出力を見た。
- [ ] 差し戻しを 1 周で打ち切り、収束しない場合はユーザーへ報告した。
- [ ] 省いた検証を完了報告に明記した。
- [ ] 作業ブランチへコミットし、PR は明示依頼がある場合だけ作成した。

## 適用範囲外

- 本番投入を前提とする実装・修正は `dev-workflow` の領分である。
- 空ディレクトリからの新規プロジェクト初期構築は `init-project` の領分である。

## 注意事項

- 速度優先は、要件定義・TDD・ユニットテストを削る理由にならない。
- 検収の簡略化で失った設計・テスト・統合の保証を、完了報告で隠さない。
- ユーザーが明示的に許可しない限り、push・デプロイ・PR 作成を指示しない。
- 指示と反する判断が必要になったら、根拠を示してユーザーに確認する。
