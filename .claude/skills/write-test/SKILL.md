# テストファースト

本番コードを書く前に、仕様からテストを書く。

テストを先に書く目的は、実装に引きずられずに「何をすべきか」を期待結果として固定することである。実装の後に書いたテストは「実装が何をしているか」をなぞり、誤った振る舞いを正解として固定してしまう。

## 手順

1. 実装対象の仕様（write-code Step 0 で確認したもの）から、検証すべき振る舞いを洗い出し、テストをまとめて書く
2. 全体設計を踏まえて実装する
3. 全テストを通す

テストを 1 件ずつ書いて実装する反復や、実装前に失敗を観察する手順は要求しない。ただしバグ修正は例外とする（後述）。

## 書くときの規律

- **テストは実装をなぞらず、仕様からアサーションを書き起こす。** 既存実装や書きかけの実装を見てアサーションを決めると、実装の誤りごと固定する
- **実装を先に書いていることに気づいたら、その時点で実装の手を止め、テストに戻る。** 書き足すほど未検証のコードが積もり、テストが実装に引きずられる
- **テストが書きにくいのは設計が悪い兆候として扱う。** テストが難しいならインターフェースを簡素化する。全部モックが要るなら結合が強すぎるので、依存を注入して差し替え可能にする（判断基準は knowledge `tech/design`）

## バグ修正

バグ修正では、まずバグを再現するテストを書き、**修正前にそのテストが失敗することを確かめてから**直す。修正前に失敗しないテストは、そのバグを捉えている根拠にならない。

## 例外（ユーザーに確認してから）

以下はテストファーストを適用しない。適用しない場合は、事前にユーザーに確認する。

- 使い捨てのプロトタイプ
- 生成コード
- 設定ファイル

## 品質基準

書くテストの品質バーは **`test-review` スキルが検査する観点そのもの**とする。品質基準を write-test 側に二重に持たず、単一の情報源に従う。

- 観点の一覧: `test-review` の SKILL.md（機械検出の項目と、テスト戦略・テスト意図のレビュー）
- 観点ごとの判断基準: `test-review/references/review-lenses.md`
