# コード実装の共通方針

コードを実装・修正する際は、以下の方針に従うこと。

## 作業フロー

以下の順序で作業を進めること。順序を入れ替えてはならない。

### Step 1: テストを書く
- 実装対象の振る舞いを検証するテストファイルを作成・編集する
- テストのみを書き、実装コードにはまだ触れない

### Step 2: コードを書く
以下のサイクルを、すべてのテストが通るまで繰り返す。

#### 2-1: RED — テストが失敗することを確認する
- テストを実行し、失敗であることを確認する
- この時点で通ってしまう場合、テストが不十分なので Step 1 に戻る

#### 2-2: GREEN — テストを通す
- テストが通る最小限の実装コードを書く
- きれいなコードである必要はない。まず動かすことが目的

#### 2-3: Refactor — リファクタリングする
- テストが通った状態を維持しながら、コードを改善する
- リファクタリング後、テストを再実行して壊れていないことを確認する

### Step 3: 検証
- `npm run check` / `npm run typecheck` を実行する
- `code-review` スキルでセルフレビューする
- 指摘があれば修正し、Step 1 からやり直す

## 厳守事項

- **指示された範囲のみ変更すること**（指示にない範囲の「改善」や「リファクタリング」を追加しない）
- **コードを自然言語に翻訳しただけのコメントを書くことを禁止**（例: `// iを1増やす` `// userを返す` 等。コードを読めばわかることをコメントしない）
- **既存のコードベースのスタイル・パターンに従うこと**
- ソフトウェアエンジニアリングの原則に従い、堅牢性・変更容易性・低認知負荷を意識したコードを書くこと

**堅牢性**
- エッジケースを必ずテストする（null/undefined、空配列、境界値など）
- エラーは握りつぶさず、適切に伝播・通知する
- フェイルファスト — 異常な状態は早期に検出して即座に失敗させる
- 型で不正な状態を表現不可能にする（any/asを避け、型を最大限活用する）。ただし型パズルや、型安全性のためだけに実装を歪めることは禁止
- 引数や共有データを直接変更しない（不変性を保つ）

**変更容易性**
- SOLID原則に従う
  - 関数の変更理由が複数ある場合は分割する
  - 新しいケースの追加にswitch/ifの分岐追加で対応せず、パターンで拡張する
  - 親クラスのメソッドを空実装やthrowでオーバーライドしない
  - インターフェースは利用者が必要とするメソッドだけを含める
  - 外部依存（DB・API・ファイルシステム）は差し替え可能にする
- 重複を避ける（DRY） — コードの見た目ではなく知識・ロジックの重複を排除する
  - 共通の意味・意図を持つ知識・変数・ロジックは単一の情報源にする
  - コードだけでなくコメント・ドキュメントもDRYの対象とする
  - 見た目が似ているだけで意味が異なるコードはまとめない
- 隠れた依存・グローバル状態を避け、依存を明示的にする

**低認知負荷**
- 変数・関数名は意図が一目でわかる名前にする（略語・汎用名を避ける）
- 早期リターンを活用し、ひとつの関心事の処理が終わり結果が導かれた時点で関数を抜ける
- 条件分岐が複雑にならない設計をする
