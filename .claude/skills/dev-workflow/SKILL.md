コードを書く依頼を受ける唯一の入口として、要求をワークフローで遂行してください。

## 引数
$ARGUMENTS

## 引数の形式

以下のいずれかを受け付ける。

1. **GitHub issue**: URL / `owner/repo#番号` / 番号のみ
2. **仕様書のパス**: プロジェクト内のファイルパス
3. **自由記述**: やりたいことの説明

## 役割分担

**あなたは頭脳であり、手足は Codex である。**

- **頭脳（Claude）**: 要求の分解、発注設計、モデルと推論量の選択、依頼文の作成、検収の判断、統合方針の決定、ユーザーへの報告。判断そのものは委任しない
- **手足（Codex）**: コードベースの調査、ファイルの変更、テストの追加と実行、lint / typecheck の実行、git 操作、issue 操作、PR 作成の実務

委任は `delegate-to-codex` スキル経由で行う。**これが唯一の委任経路である。** `codex exec` や codex プラグインの経路へ退避しない。実測では、それらの経路は結果を回収できないまま停止する事例が繰り返し出ている。経路が使えるかどうかの判定と、使えないときの扱いは `delegate-to-codex` の責務であり、ここでは持たない。

各工程の作業手順は既存スキル（`plan`・`write-code`・`verify-task`・`code-review`・`create-pr`・`comment-issue` 等）が定めている。それらを Codex に実行させるので、**依頼文には従わせるスキルの SKILL.md の絶対パスを書き、読んでから作業するよう指示する。** スキル本文をコピーしない（更新が追随しなくなる）。

```
以下のスキルを読み、その手順に従って作業してください。
- /Users/cancer/.claude/skills/write-code/SKILL.md
```

**モデルと推論量の選択は、この工程を発注する時点で頭脳が決める。** 各スキルはモデル選択の判断を持たない。段の基準は `delegate-to-codex` の `references/model-routing.md` にある。

### 絶対規律

- **禁止**: 自分で Edit / Write を使って実装すること。規模が小さくても委任する。例外は誤字・formatter 相当の明白な一行修正のみ
- **Bash の用途は限定する**: 検収（`git diff`・検査コマンドの実行）、状態確認、watchdog に限る。実装・調査を Bash で代行しない
- **Red Flag**（この思考が出たら委任に戻す）:
  - 「これくらい自分で直接やった方が早い」
  - 「1ファイルだけだから委任は大げさ」
  - 「issue を自分で読んでしまおう」

自分では実装しないことで、**書いた者と検収する者が分離**される。加えてモデルが異なるため、実装者の思い込みが検収へ伝播しない。

### 委任経路が使えないとき

`delegate-to-codex` は委任経路が無い場合にその旨を返して止まる。**その報告を握り潰さない。** 何が使えないのかをユーザーへ伝え、どう進めるか（復旧を待つ、別のワーカーで進める、自分でやる）の指示を仰ぐ。

ここで頭脳が実装を肩代わりしない。肩代わりすると、書いた者と検証する者の分離が消える。

## ワークフロー

### Phase 0: 起点の整備

1. 現在のブランチを確認し、デフォルトブランチにいるなら作業ブランチを作成する（`create-branch` 相当）
2. **プロジェクト規約を読み取る**（Codex へ委任してよい。`-s read-only` で発注する）:
   - PR / ブランチ戦略
   - **1PRあたりのコミット数上限**（プロジェクトにより有無が異なる）
   - CLAUDE.md の設計原則・制約・禁止事項・命名規則

### Phase 1: intake分析

要求内容の分解計画を Codex へ委任する。`-s read-only` で発注し、issue の読み込み（`gh issue view` ＋コメント）・コードベース調査・分解計画（対応一覧・依存・対象ファイル・検証方法）を出させる。

**この工程は段を上げる。** どこを見に行くかの判断そのものを渡すため、依頼文で探索範囲を決め切れない。`references/model-routing.md`（`delegate-to-codex` 配下）の基準では `sol + high` に当たる。実装工程で `luna` を使うのとは判断が別である。

計画を受け取ったら、頭脳が読んで妥当性を判断する。計画の採否は委任しない。

### Phase 2: タスク化とPR粒度の決定

1. 計画の対応一覧をもとに `TaskCreate` でタスクを作り、依存を `TaskUpdate` で設定する。**タスクの状態管理は頭脳が行う。** Codex は `TaskUpdate` を呼べないため、ワーカーの自己申告に任せる設計は成立しない
2. **PR粒度を決める**（コミットの squash はしない。整えない）:
   - デフォルトは **1依頼 = 1PR**
   - Phase0 のコミット上限があり、想定コミット数が上限を超えるなら、**依存・論理境界で複数PRに分割**（各PR ≤ 上限）。分割したら必ず報告に含める

### Phase 3: 実装委任

タスクごとに Codex へ委任する。

#### 並列化と作業ツリー

**書き込みを伴う委任を同一の作業ツリーで並列に走らせない。** ペインを分けても作業ツリーは共有されるため、ペインの分離は並列化の根拠にならない。

独立に並列化できるタスクは、タスクごとに `git worktree` を切り、`delegate-to-codex` へ `--cwd` をそのツリーへ向けて発注する。読み取りだけの委任（調査・レビュー）は同一ツリーで並走してよい。

依存のあるタスクは依存元の完了を待って発注する。

#### ペインの配置

2つ目以降のエージェントは、最初のエージェントペインを下へ分割して積む（`--pane <最初のpane_id> --direction down`）。指揮者のペイン幅を削らずに済む。分割後の幅が80桁を下回るなら別タブへ移す。

#### 依頼文に必ず含めるもの

依頼文は単体で完結させる。Codex は会話を見ていないので、次を本文に書き切る。

- ゴールと完了条件
- 対象ファイルと、触ってはいけない範囲
- 計画で判明した関連ファイル・設計意図・制約
- **CLAUDE.md のプロジェクト固有ルールは内容そのものを引用する**（worktree の Codex は上位の指示ファイルを読めない場合がある）
- **作業の副産物の扱い**（依存インストール、ビルド成果物、lockfile を許すか消すか）。書かないと Codex は自分の副産物を指示違反と見なし、素性の調査と削除に時間を使う
- **git 操作の範囲**: コミットは許可するか、push は禁止か。統合は頭脳が行うので push は禁じる
- **issue 起点の場合**: コミットと PR 本文に `Closes #<番号>` を含めること、完了後に issue へ PR 報告コメントを投稿すること

**依頼文に裁量を残さない。** 実測では、範囲を広く書いた委任が調査ワークフローに入って26分停止し、対象と変更内容を絞って投げ直すと2分半で完了した。設計判断（基準・境界・命名・分割の方針）を決め切ってから発注する。

#### 発注前の報告

選んだモデル・推論量・その理由を、発注ごとにユーザーへ短く伝える。委任先の選択をユーザーが是正できる唯一のタイミングなので、事後報告にしない。

#### 記録

発注ごとにエージェント名 / pane_id / worktree のパス / 対応するタスクIDを保持する。watchdog の検知結果を発注へ対応づけるために使う。

### Phase 4: 個別検収

**Codex の報告は自己申告であり、成果の証明ではない。** ペインに見えているのも Codex が描いた画面であって、コマンドの生出力ではない（ツール出力は畳まれる）。報告と画面が食い違ったら、どちらも信じずに差分で確かめる。

1. `git diff` で実際の変更を読む。報告を読んで済ませない
2. `delegate-to-codex` 経由で `verify-task` を実行させる（**実装した Codex とは別のスレッド**で発注する）。依頼文に `/Users/cancer/.claude/skills/verify-task/SKILL.md` のパスと、指示内容・worktreeパス・issue参照を渡す。`-s read-only` で発注する
3. FAIL なら該当スレッドへ差し戻す。同じ名前へ `agent prompt` を送れば同じスレッドが続く
4. 差し戻しは2回までを目安にする。上限に達したら、原因と残る不確定事項をユーザーへ報告して判断を仰ぐ

差し戻しで段を上げるのは既定にしない。範囲が限定された時点で必要な判断量は減っている。原因が依頼文の不備なら、同じ段で条件を書き直して出し直す。

### Phase 5: 統合と統合後レビュー

全対象タスクの個別検収が PASS したら:

1. **統合**: Codex へ委任し、対象ブランチを依存順に統合ブランチへマージさせる（**squash しない**。PR粒度が複数なら各PR分の統合ブランチを構成）
2. **統合後レビュー**: **実装した Codex とは別のスレッド**を立て、`delegate-to-codex` 経由で `code-review`（`/Users/cancer/.claude/skills/code-review/skill.md`）を統合ブランチの結合 diff に対して実行させる。観点は品質に加えて結合特有の整合性:
   - 同一ファイルの競合・マージ後の不整合
   - API・型・スキーマの不整合（片方の変更を他方が古いまま参照）
   - 設計方針の矛盾・命名/パターンの不一致
   - 重複実装・重複テスト
3. 指摘があれば原因側のスレッドへ差し戻し、修正後に該当検収をやり直す
4. 調整方針を頭脳が判断できない場合のみ `AskUserQuestion` でユーザーに諮る

### Phase 6: PR作成と完了

1. 統合後レビュー PASS 後、PR 作成を Codex へ委任する（`create-pr` 相当）。1〜N PR、各PR ≤ コミット上限。issue 起点なら `Closes #<番号>`
2. 使い終わった Codex ペインを閉じ、worktree を片付ける。差し戻しが想定される間は閉じない。閉じる前にセッション UUID を控えておくと、後から同じスレッドへ戻れる
3. watchdog の Monitor を `TaskStop` で止める
4. ユーザーに完了報告する（下記「成果物」）

## 承認を求められたとき

`agent_status` が `blocked` になったら、`herdr agent read <名前> --source detection` で何を聞かれているかを読む。**画面を見ずにキーを送らない。**

- **通常の確認ダイアログ**（ディレクトリの信頼、更新の可否、上書きの確認など）は、選択肢を読んだうえで意図する番号を明示して送る。`herdr pane send-text <pane_id> '<番号>'` のあとに `send-keys <pane_id> enter`。**素の `enter` を単独で送らない。** 既定の選択が意図と違う場合があり、実測では更新プロンプトで `enter` を送って `brew upgrade` が走った
- **サンドボックス外への権限昇格の承認**は代行しない。Claude Code の classifier が代理入力を止めるうえ、昇格の是非はユーザーの判断である。何を求められているかを伝えて待つ。却下（`herdr agent send-keys <名前> esc`）は通る
- 却下した直後は Codex が指示待ちで `blocked` のままなので、通常の `agent prompt` を送れば `idle` に戻る

ペイン経路を選んでいる理由がここにある。ユーザーの画面に見えているので、判断が要る場面をユーザーが直接処理できる。

## 無応答の検知

`delegate-to-codex` は `agent prompt --wait` で完了を待つため、通常は状態遷移で完了が分かる。ポーリングは不要である。ただし次の場合に沈黙と停止を区別できない。

- 実装を伴う委任は20分を超えることがあり、Bash ツールの上限は10分である。**長い委任は `run_in_background: true` で投げ、完了通知を受けてから読む**
- herdr 側の状態が失われた、ペインを閉じた、`--wait` のタイムアウトが実作業より短かった

### watchdog

Phase 3 で全タスクを発注した直後に、`Monitor` を `persistent: true` で1つだけ張る。Codex は自分の実行ログを `~/.codex/sessions/<年>/<月>/<日>/rollout-<時刻>-<UUID>.jsonl` へ追記し続けるので、**その mtime の停滞が「何も出していない時間」**を表す。

```bash
THRESHOLD=600        # 秒。長い調査中も追記は続くが、テスト実行中は止まることがある
reported=" "
while true; do
  sleep 60
  now=$(date +%s)
  for u in <発注ごとのセッションUUIDを空白区切りでここに直接展開する>; do
    case "$reported" in *" $u "*) continue ;; esac
    f=$(ls -t ~/.codex/sessions/*/*/*/rollout-*-"$u".jsonl 2>/dev/null | head -1)
    if [ -z "$f" ]; then echo "NOLOG $u"; reported="$reported$u "; continue; fi
    age=$(( now - $(stat -f %m "$f") ))
    if [ "$age" -ge "$THRESHOLD" ]; then echo "STALE $u ${age}s"; reported="$reported$u "; fi
  done
done
```

- **UUID はスクリプト本文に直接列挙する**。シェルは zsh であり、未クォート変数は単語分割されない。`IDS` 変数に入れて `for u in $IDS` と書くとループが1回しか回らない
- **`ls -t | head -1` で最新のログを拾わない**。別のタスクや他のリポジトリで走っている Codex のログを掴む。必ず UUID でファイルを特定する
- `STALE` は「死亡」ではなく「確認せよ」の信号である。受け取ったら、対応する発注のペインを `agent get` と `agent read --source visible` で確認する
- `NOLOG` はそのスレッドを watchdog で見張れないことを意味する。**沈黙を成功と解釈せず**、ペインの直接確認のみで追う旨をユーザーへ報告する
- **この Monitor に渡すのは上記の生存確認スクリプトのみ**。実装・調査・git 操作にシェルを使ってはならない

### セッション UUID の取得

`herdr agent get` は `agent_session` を返さない（`herdr integration status` が `codex: not installed` の状態）。UUID が要るなら `herdr integration install codex` を入れるか、rollout ログのファイル名を起動時刻で絞って拾う。watchdog を使うなら前者を先に済ませる方が確実である。

### 待ちに入る時点での確認

watchdog は一度報告したスレッドを再報告しないため、待ちの入口を取りこぼしの受け皿にする。次の時点で、未完了の発注それぞれについて `agent get` の状態とペインの画面を確認する。

- 全タスクを発注し終え、報告を待つ状態に入るとき
- ある発注の報告を処理し終え、未報告の発注が残っているとき
- Phase 4 で差し戻し、修正報告を待つとき

確認できた事実だけを報告する。エージェント名 / 担当タスク / `agent_status` / 画面から読み取れる状態 / 取った処置。未確定のものは未確定と書く。進捗や成果を推測で埋めてはならない。

## 成果物（完了報告）

- 実施作業の要約
- 各委任の担当と成果、使ったモデルと推論量
- 各委任の `verify-task` 結果（PASS/FAIL 履歴）と差し戻し回数
- 統合後レビューの結果（検出した指摘と対応）
- 作成した PR（URL）とブランチ名。複数PRに分割した場合はその理由
- 承認をユーザーに委ねた場面があればその内容

## 報告の事実性

- 報告に含める原因・理由は、実際に検証された事実・プロジェクトで既知の事実・公式ドキュメント等ソースを提示できるものに限る
- 「おそらく」「〜と思われる」等の推測を確認済み事実であるかのように報告しない
- Codex からの報告を中継する際は、差分で照合したかどうかを明記する。照合していないなら未確認と書く

- [ ] 依頼文に副産物の扱いと git 操作の範囲を書いた

## 適用範囲外

- 「使い捨て」「テスト不要」とユーザーが明示した単発コードは本ワークフローの対象外。呼ばれてしまった場合は、委任・TDD・PR の儀式を回さず、その旨を伝えて inline での直接対応を促す

## 注意事項

- 頭脳自身はコードを書かない。すべて委任する
- Codex に守らせたい前提（変更範囲、抽象化の扱い、テストの書き方）は理由を添えて依頼文へ織り込む。禁止事項を積み上げるより意図を渡す
- ユーザーが明示的に許可しない限り、コミット・push・デプロイを Codex に指示しない
- 指示された内容と反する判断が必要になったら、必ずユーザーに確認する
