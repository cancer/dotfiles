タスク定義の中の 1 タスクを受け取り、実装 → 検収 → 成果物の確定のループを回してください。ループの中ではユーザーに諮らない。

## 引数
$ARGUMENTS

## 引数の形式

次の3つを必ず受け取る。

1. **タスク定義ファイルのパス**: `/Users/cancer/.claude/skills/run-implement/references/task-format.md` の形式（タスク・完了条件・契約）で書かれたファイル
2. **`--task T<n>`**: 回すタスクの ID。タスク定義に 1 件だけ存在すること
3. **`--effort low|mid|high`**（下記「effort」）

タスク定義と全体設計は本スキルの外で決まっている前提とする。本スキルはタスクの分解・依存の判断・設計判断をしない。タスク定義が上記の形式を満たさない（完了条件や契約が欠けている、指定 ID が無い・重複している、effort mid / high で成果物の命題が無い）なら、補わずにループを抜ける（「ループを抜けるとき」）。

## effort

effort は**品質をどの軸で評価・改善するか**だけを表す。回数ではなく軸を選ぶ。選んだ軸のレビューは、どれも指摘が無くなるまで反復する（上限3周、「レビューの反復」）。レビューで落ちた状態のまま放置して終えることはできないので、軸を選んだら途中で打ち切らない。委任・成果物の確定など他の工程は effort で変えない。

| effort | `verify-task`（機能の完了） | `test-review` | `code-review` | 拾う指摘 | テスト |
|---|---|---|---|---|---|
| low | 回さない | 回さない | 回さない | ― | 書かない。実装して実測の生の出力を返す |
| mid | 回す | 回す | 回さない | 重要度 high / mid のみ。low は落とし、完了報告に残す | テストファースト |
| high | 回す | 回す | 回す | low まですべて | テストファースト |

統合後の結合レビューは本スキルでは回さない（merge-prs が effort high のときに回す）。

「拾う指摘」の重要度は品質のレビュー（`test-review` / `code-review`）の指摘にだけ適用する。`verify-task` は「できているか、いないか」の二値なので程度差が無く、FAIL・判定不能は mid / high のどちらでも拾う。落とした指摘は「採るべき指摘」に数えないので、反復の継続条件にもならない。

`verify-task` は mid / high で回す。指示どおり完了しているかは品質の軸ではなく作業の成否だからである。

**low は PoC 用である。** PoC の完了は仮定が決着したことで、成立・不成立のどちらも完了なので、`verify-task` も回さない。テストを書かせず、`write-code` / `write-test` を読ませない（`write-code` はテストファーストを必須としている）。成果物は実測の生の出力であり、合否の判定は呼び出し側が行う。

effort は呼び出し側（主スレッド）が会話から判断して渡す。本スキルの中で決めない。渡されていなければ、推測で埋めずにループを抜ける。

「レビューの反復」の不変条件（修正後に PASS が無効になったレビューを回し直す）は、effort で選んだ軸の中で適用する。回さない軸は「回し直す対象」に含めない。

以下の本文で「3種のレビュー」と書いた箇所は、effort で選んだ軸のレビューに読み替える（mid なら `verify-task` と `test-review` の2種、low なら無し）。

## ループを抜けるとき

次の事態では、ループを抜けて状況を呼び出し側（主スレッド）へ返す。ユーザーに諮らない。原因は入力の側にあるので、直すのはタスク定義を作る側である。

- effort が無い、タスク定義が形式を満たさない、委任経路が使えないなど、入力・環境の不備
- 3周で収束しない（「上限は3周」）
- 指摘の矛盾が既定の解決順で解けない（「指摘が矛盾する場合」）
- 実装中に契約が成立しないと分かった（「契約の扱い」）
- 推論量 `max` でも進まない（Phase 2）
- 成果物の命題から、成果物の種類（PR / コミット）や base を特定できない
- 指示と反する判断が要る
- サンドボックス外の操作を頭脳が代行しようとして拒否された（権限設定・classifier による拒否。「却下した操作は頭脳が代行する」）

**抜けるときはそのタスクの worktree とブランチ（作っていれば PR も）を残して返す。** タスク定義が直されると、検収を通ったタスクも前提が変わって無効になりうるためである。走っていないペインは閉じ、watchdog の Monitor を止める。

返す報告には次を含める。

- 抜けた理由と、該当する節が求める報告内容（例: 3周で収束しないなら「上限は3周」の報告項目）
- そのタスクの worktree のパス・ブランチ名・PR（あれば）・状態（実装中 / 検収中 / 検収 PASS など）

## 役割分担

**あなたは頭脳であり、手足は Codex である。**

- **頭脳（Claude）**: タスク定義からの発注設計、モデルと推論量の選択、依頼文の作成、検収の判断、成果物の確定（create-pr の呼び出しと CI の確認）、呼び出し側への報告。判断そのものは委任しない
- **手足（Codex）**: コードベースの調査、ファイルの変更、テストの追加と実行、lint / typecheck の実行、git 操作の実務

委任は `delegate-to-codex` スキル経由で行う。**これが唯一の委任経路である。** `codex exec` や codex プラグインの経路へ退避しない。実測では、それらの経路は結果を回収できないまま停止する事例が繰り返し出ている。経路が使えるかどうかの判定と、使えないときの扱いは `delegate-to-codex` の責務であり、ここでは持たない。

各工程の作業手順は既存スキル（`write-code`・`verify-task`・`code-review`・`test-review` 等）が定めている。それらを Codex に実行させるので、**依頼文には従わせるスキルの SKILL.md の絶対パスを書き、読んでから作業するよう指示する。** スキル本文をコピーしない（更新が追随しなくなる）。

```
以下のスキルを読み、その手順に従って作業してください。
- /Users/cancer/.claude/skills/write-code/SKILL.md
```

**モデルと推論量の選択は、この工程を発注する時点で頭脳が決める。** 各スキルはモデル選択の判断を持たない。段の基準は `delegate-to-codex` の `references/model-routing.md` にある。

### 絶対規律

- **禁止**: 自分で Edit / Write を使って実装すること。規模が小さくても委任する。例外は誤字・formatter 相当の明白な一行修正のみ
- **Bash の用途は限定する**: 検収（`git diff`・検査コマンドの実行）、状態確認、watchdog に限る。実装・調査を Bash で代行しない
- **Red Flag**（この思考が出たら委任に戻す）:
  - 「これくらい自分で直接やった方が早い」
  - 「1ファイルだけだから委任は大げさ」
  - 「コードベースを自分で調べて対応箇所を洗い出そう」

**委任するのは実装と調査であって、タスク定義の読み取りではない。** タスク定義のそのタスクが何を求めているかは、頭脳が自分で読んで確定する。ここを省くと、誤った前提を含む依頼文がそのまま Codex へ渡り、作業全体が的外れになる。「自分で読むのは委任違反ではないか」という迷いが出たら、読む方を選ぶ。

自分では実装しないことで、**書いた者と検収する者が分離**される。加えてモデルが異なるため、実装者の思い込みが検収へ伝播しない。

### 委任経路が使えないとき

`delegate-to-codex` は委任経路が無い場合にその旨を返して止まる。**その報告を握り潰さない。** ループを抜け、何が使えないのかを呼び出し側へ返す。

ここで頭脳が実装を肩代わりしない。肩代わりすると、書いた者と検証する者の分離が消える。

## レビューの反復

**各レビューは、指摘が無くなるまで「実行 → 修正 → 再実行」を繰り返す。** 1回の指摘に対応して終わりにしない。修正が新しい問題を持ち込むことがあり、修正後に再実行していない状態は「指摘が解消された」ことの証明にならない。この規律は `verify-task`・`test-review`・`code-review` のいずれにも同じように適用する。

### 不変条件

> **レビューの PASS は、そのとき見たツリーに対してのみ有効である。修正が入ったら、その修正を見ていないレビューの PASS はすべて無効になる。無効になったものを回し直す。**

保つべきものは「最終ツリーに対して、すべてのレビューが指摘0で通っている」という状態であって、レビューを回した回数ではない。この不変条件があれば、どのレビューをどの順で回すかは決める必要がなくなる。**最後に回したレビューだけが最終ツリーを見ている状態を、収束と呼ばない。**

適用先はレビューの種類を問わない。`test-review` の指摘を修正すれば `verify-task` の PASS も無効になり、CI の失敗を修正すれば、`verify-task` と `test-review` の PASS が無効になる。

各レビューの周回は独立に数える。関心ごとに上限へ達するかを判定できるので、収束しなかったレビューを名指しして報告できる。全レビューを毎周まとめて回す運用にはしない。片方の関心しか変わっていない周でも両方を実行することになり、上限もどちらの関心が収束しなかったのかを表さなくなる。

### 1周の構成

1. レビューを実行させる（実装したスレッドとは別のスレッド）
2. 指摘の採否を頭脳が判断する。採る指摘を**新しいスレッドへ差し戻す**
3. 修正の報告を受けたら `git diff` で実際の変更を確認する
4. **同じレビューを、新しいスレッドで再実行させる。** 修正後のコードは新しいレビュー対象である。スレッドを使い回すと、前の周の指摘と自分の判断が残り、レビュアーの独立性が周をまたいで失われる
5. **そのレビューが収束したら、修正で PASS が無効になった他のレビューを回し直す**（不変条件）。Phase 3 の3種は同時に発注して指摘を1回の差し戻しにまとめるため、周ごとに3種とも再実行する（どれを回し直すかを個別に判断しない）。**修正のたびには回さない。** 周回の途中はまだ指摘が残っている状態であり、そこで他のレビューを回しても、次の修正でまたその PASS が無効になる

### 終了条件

**採るべき指摘が 0 件になった時点で終わる。** 判断は次のとおり分ける。

- **指摘**（根拠・影響・確信度・区分が揃っているもの）が残っていれば、周回を続ける
- **質問**（根拠が揃わず「未解決の質問」に置かれたもの）は指摘ではない。中継して回答を得るか、「記録が残っていない」という事実として確定させる。周回の継続条件にはしない
- **未計測の範囲**も継続条件にはしない。ただし「問題なし」と読み替えず、完了報告に残す
- 頭脳が判断して**採らなかった指摘**は解消済みではない。理由とともに完了報告へ残す。一度「不採用」と決めた指摘は、次の周で再び出ても採否を判断し直さず、「採るべき指摘」に数えない（下記「指摘が矛盾する場合」）

`test-review` は指摘が 0 件でも「テストは十分」とは書かない設計である。**その出力を「十分である」と読み替えない。**

### 指摘が矛盾する場合

**片方の指摘を解消すると他方の指摘が復活する組み合わせがある。** そのまま周回を続けると、修正のたびに逆向きの指摘が出て往復し、上限に達するまで止まらない。上限で止まっても、報告は「収束しなかった」としか言えず、原因が矛盾であることを名指しできない。

矛盾はレビューの種類をまたいでも、1つのレビューの中でも起こる。`test-review` の「モック偏重」を解消するために本物の依存を使えば「外部依存」の指摘が立つ。`code-review` の観点自体にも「過剰な分割の禁止」と「1ファイル1関心事」のように、押し引きの関係にある対がある。

#### 検知

**直前の修正を打ち消す向きの指摘が出たら、その時点で周回を止める。** 上限まで待たない。修正した箇所と、新たに出た指摘の所在が一致し、要求の向きが逆であることが判定条件である。

#### 解決（この順に試す）

1. **両方の根拠が成り立つ第三の形を探す。** 多くは矛盾ではなく、両立する設計が存在する。この場合は両方の指摘とそれぞれの根拠を添えて**新しいスレッドへ差し戻す**。**手段は指定しない**（レビューが対応内容を書かないのと同じ理由による）
2. **根拠の種類で決める。** 仕様に紐づく根拠（`--spec` の命題、タスク定義の完了条件、既知の不具合）は、原則に紐づく根拠より優先する
3. **原則同士がぶつかっているなら、既定は `test-review` を正とする**（下記）
4. **既定を適用できないなら決めない。** ループを抜けて呼び出し側へ返す

#### 原則同士の衝突は `test-review` を正とする

テスト容易性と現状の設計がぶつかったとき、誤っているのは設計側である、という判断は既に置かれている（`write-test` の書くときの規律: 「テストが書きにくいのは設計が悪い兆候」「全部モックが要るなら結合が強すぎる」）。矛盾の多くはこの型なので、既定を `test-review` に倒す。

**倒すのは原則同士の衝突に限る。** `test-review` は既定では仕様の妥当性を判断しない（`--spec` が渡されていない場合）。「テストの方が要件に近いから常に正」ではなく、根拠の種類による順序（上記 2）が上位に残る。

既定を適用しない例外は次の2つで、いずれかに当たれば `code-review` 側を採る。

- `test-review` の指摘の**確信度が低い**、または区分が**人による最終判断**である。根拠が揃っていないものを正にはできない
- 採用した結果が**プロジェクトの CLAUDE.md の明示ルール**に反する。プロジェクト規約が上位である

**テスト都合で無条件に抽象を挟まない。** 依存性逆転は業務処理が外部実装へ依存している境界にだけ置くものであり、テストのために全面へ広げる根拠にはならない。この型の衝突は 1 の両立形で解けることが多いので、既定へ飛ばす前に 1 を試す。

#### 決定後の扱い

- 採らないと決めた指摘は**不採用として固定する**。レビュースレッドは毎回新しく立つため同じ指摘が再び出るが、採否を判断し直さず、周回の継続条件から外す
- **決定の記録を実装スレッドに残させる**（コードコメントまたはコミットメッセージ）。頭脳は書かない。記録が無いと、次に触る者が同じ往復を繰り返す
- 周回のカウントは、矛盾の解決に要した差し戻しも含めて数える

#### 報告

矛盾で止めた場合は、「3周で収束せず」とは別の内容を報告する。

- 矛盾した2つの指摘と、それぞれの根拠・所在
- 試した両立形と、成立しなかった理由
- 決定（または解けずにループを抜けた旨）と、その根拠

### 上限は3周

**周回は収束エピソード単位で数える。** 1つのエピソードは、あるレビューの指摘に対する連続した修正の系列である。他のレビュー起点の修正によって PASS が無効になり回し直す場合は、**新しいエピソードとして数え直す**。これを通算にすると、CI の失敗を1件直しただけで既に3周使ったレビューが回せなくなり、不変条件（無効になったものを回し直す）と衝突して止まる。数え直しても往復が無限にならないのは、レビューをまたぐ振動は矛盾検知（直前の修正を打ち消す向きの指摘で即停止）が受け持つためである。

**1つのエピソードの中で3回修正しても指摘が無くならない場合、ループを抜けて呼び出し側へ返す。** 4周目に入らない。同じ箇所の指摘が3周残るのは、修正で埋まる欠陥ではなく、設計・仕様・依頼文の前提に原因があることを示す。周回を続けても収束せず、レビューと修正のコストだけが積み上がる。

報告には次を含める。

- どのレビューが、どの対象で、何周して止まったか
- 各周で出た指摘と、それに対して何を修正したか（`git diff` で確認した内容）
- 残っている指摘と、その根拠・確信度・区分
- 収束しない原因についての頭脳の見立てと、その根拠。**根拠を示せないなら「原因は特定できていない」と書く**

**周回中に段（モデル・推論量）を上げるのは既定にしない。** 範囲が限定された時点で必要な判断量は減っている。原因が依頼文の不備なら、同じ段で条件を書き直して出し直す。

## ワークフロー

### 工程の並列化

**このスキルが回すのは 1 タスクである。** 他タスクとの並列化と待ち合わせは呼び出し側が行う。タスクの中では、待ち合わせの要らない工程を並行させる。

**短縮は品質を変えない範囲で行う。** 次の規律は並列化を理由に緩めない。緩めた時点で短縮ではなく手抜きである。

- 書き込みを伴う委任は、そのタスクの worktree だけで行う（Phase 2「作業ツリー」）
- 実装スレッドと、`verify-task` / `test-review` / `code-review` のスレッドを分ける
- 修正が入ったら、その修正を見ていない PASS を回し直す（「レビューの反復」の不変条件）
- 機械的チェックは頭脳が自分で実行する

| 並行して走らせる | 直列に待たせる |
| --- | --- |
| 同一タスク内の3種のレビュー（`verify-task` / `test-review` / `code-review`）。同じ diff を読むだけなので待ち合わせない | 同一の作業ツリーへ書き込む委任 |
| 読み取りだけの委任（調査・レビュー）は同一ツリーで並走してよい | 同一タスク内の検収の順序（機械的チェック → 3種のレビュー） |
| | 機械的チェックが FAIL のときのレビュー発注（発注しない） |
| | 無効になった PASS の回し直し（飛ばして成果物の確定へ進まない） |

#### 契約の扱い

1. **契約はタスク定義が決めている。** 頭脳は契約を決め直さない
2. **依頼文へ、そのタスクが提供・利用する契約をタスク定義からそのまま書き切る。** 契約を書かないと、ワーカーが別の形を発明し、他タスクと噛み合わなくなる
3. **実装中に契約が成立しないと分かったら、ループを抜ける。** 頭脳が契約を書き換えて続けない。契約の変更はタスク定義の変更であり、その契約を利用する他タスクの前提も変わるためである

### Phase 0: 起点の整備

1. 現在のブランチを確認し、デフォルトブランチにいるなら作業ブランチを作成する（`create-branch` 相当）
2. **プロジェクト規約を読み取る**（Codex へ委任してよい。`-s read-only` で発注する）:
   - ブランチ戦略
   - CLAUDE.md の設計原則・制約・禁止事項・命名規則

### Phase 1: 作業ツリーと命題

1. 指定タスクの状態を `TaskCreate` で 1 件作り、頭脳が管理する。Codex は `TaskUpdate` を呼べないため、ワーカーの自己申告に任せる設計は成立しない
2. そのタスク用に `git worktree` を切る。同じタスクのブランチが既にあれば、それを使う（下記「成果物の確定」の再開）
3. **effort mid / high では、そのタスクの完了条件をその worktree の `.claude/verify-task/propositions.json` へ `statement` として書く。** 形式は `/Users/cancer/.claude/skills/verify-task/references/prepare.md`「propositions.json の書き方」に従い、各命題に対応する `question`・`rule` を添える。命題はタスク定義で承認済みなので、`verify-task` に導かせない。成果物の命題 `pN_deliverable` は書かない（Phase 3 の時点ではまだ満たせないため。Phase 4 で頭脳が確かめる）

### Phase 2: 実装委任

指定タスクを Codex へ委任する。

#### 作業ツリー

**書き込みを伴う委任を同一の作業ツリーで並列に走らせない。** ペインを分けても作業ツリーは共有されるため、ペインの分離は並列化の根拠にならない。

Phase 1 で切った worktree へ `delegate-to-codex` の `--cwd` を向けて発注する。読み取りだけの委任（調査・レビュー）は同一ツリーで並走してよい。

#### ペインの配置

2つ目以降のエージェントは、最初のエージェントペインを下へ分割して積む（`--pane <最初のpane_id> --direction down`）。指揮者のペイン幅を削らずに済む。分割後の幅が80桁を下回るなら別タブへ移す。

#### 推論量

**推論量は既定を置かず、発注のたびに分類する**（`references/model-routing.md`「推論量の決め方」）。成果物が依頼文と既存コードだけで一意に定まるなら `high`、Codex が何かを決める必要があるなら `max` で出す。

**`max` でも抜けないなら上げ先は無い。** 依頼文を作り直し、それでも進まないならループを抜ける。

#### 依頼文に必ず含めるもの

依頼文は単体で完結させる。Codex は会話を見ていないので、次を本文に書き切る。

- **従わせるスキルの絶対パス**（effort mid / high）: `/Users/cancer/.claude/skills/write-code/SKILL.md`（読んでから作業するよう指示する）。write-code は「REQUIRED: `write-test` スキルに従い、本番コードより先にテストを書く」を定めており、**テストファーストを守らせる経路はこの1行しかない**。書き忘れると、テストが後付けになったまま実装が進む
- **effort low では逆に、テストを書かないこと・`write-code` と `write-test` を読まないことを明記し、実測の生の出力（応答・計測値・エラー）をそのまま報告させる**
- ゴールと完了条件（タスク定義のそのタスクの完了条件。成果物の命題は頭脳が成果物の確定で満たすので、実装者には成果物の作成を頼まない）
- **そのタスクが提供・利用する契約**（タスク定義の「契約」の内容をそのまま）
- 対象ファイルと、触ってはいけない範囲
- タスク定義で判明した関連ファイル・設計意図・制約
- **CLAUDE.md のプロジェクト固有ルールは内容そのものを引用する**（worktree の Codex は上位の指示ファイルを読めない場合がある）
- **作業の副産物の扱い**（依存インストール、ビルド成果物、lockfile を許すか消すか）。書かないと Codex は自分の副産物を指示違反と見なし、素性の調査と削除に時間を使う
- **git 操作の範囲**: コミットは許可するか、push は禁止か。PR の作成と push は頭脳が成果物の確定で行うので、実装者には push を禁じる
- **完了前に lint / 型検査 / テストを自分で通しておくこと**（effort mid / high）。その全出力は報告させない。検査結果を次の依頼文へ含める場合は、呼び出し側が実行し、コマンドと結果だけを貼る。**その結果を検収の根拠にはしない**。Phase 3 で頭脳が同じ検査を自分で実行し、そちらを正とする（実装者が自分の成果の計測値を作る構図を避けるため）

- **大きなツール出力を生成させない。** ファイルは丸ごと読ませず、範囲または検索で絞らせる。テスト・ビルド・lint の全出力は呼び出し側が実行し、結果だけを依頼文へ貼る。大きな diff は対象を絞る

ターン n で s トークンの出力が出ると、そのセッションの残り (N−n) ターン分だけ s が再送され続けるため、同じ大きさの出力でも早く出るほど高くつく。

**依頼文に裁量を残さない。** 実測では、範囲を広く書いた委任が調査ワークフローに入って26分停止し、対象と変更内容を絞って投げ直すと2分半で完了した。設計判断（基準・境界・命名・分割の方針）を決め切ってから発注する。

#### 発注前の報告

選んだモデル・推論量・その理由を、発注ごとにユーザーへ短く伝える。委任先の選択をユーザーが是正できる唯一のタイミングなので、事後報告にしない。

#### 記録

発注ごとにエージェント名 / pane_id / worktree のパス / 対応するタスクIDを保持する。watchdog の検知結果を発注へ対応づけるため、およびループを抜けるときにそのタスクの worktree とブランチを返すために使う。

### Phase 3: 個別検収

**effort low では本 Phase を行わない。** `git diff` で変更を確認し、実測の生の出力を回収して成果物の確定へ進む。合否は判定しない（呼び出し側が判定する）。

**Codex の報告は自己申告であり、成果の証明ではない。** ペインに見えているのも Codex が描いた画面であって、コマンドの生出力ではない（ツール出力は畳まれる）。報告と画面が食い違ったら、どちらも信じずに差分で確かめる。

#### 差し戻し

**差し戻しは新しいスレッドで出す。** 同じスレッドで差し戻しを続けると、2 プロンプト目以降は育った文脈を再送するため、1 呼び出しあたりの入力が初回の 66,000 から 97,000〜190,000 へ増え、543 ターンの実装セッションでは compact が 4 回起きた。差し戻し先で元の判断が必要になる懸念は、依頼文に情報を書き切って埋める。

差し戻し依頼文も「依頼文は単体で完結させる」の原則に従い、次の4項目を必須欄として書き切る。

- 元の依頼文の絶対パス
- 実装時に確定した判断（何をなぜそう決めたか）
- 指摘とその根拠（どのファイルのどの行が、指示のどの行に違反しているか）
- 触ってはいけない範囲

#### セッションの引き継ぎ

委任中のセッションは、ターン数ではなく文脈量で打ち切りを判断する。目安として、`last_token_usage.input_tokens` が 120,000 トークンを超えたら、または compact が 1 回起きたら、そのスレッドを打ち切り、状態を依頼文へ落として新しいスレッドへ引き継ぐ。ターン数で切ると、巨大な出力が早期に 1 回出たケースを取り逃すため、基準にしない。

1. `git diff` で実際の変更を読む。報告を読んで済ませない
2. **機械的チェックを頭脳が自分で実行する**（下記）。FAIL なら3種のレビューを発注せず差し戻す
3. **3種のレビューを同時に発注する**（それぞれ**実装した Codex とは別のスレッド**）。対象はいずれも**そのタスク単体の diff** である
   - `verify-task`（指示どおり完了しているか。下記「`verify-task` へ渡すもの」）
   - `test-review`（テストそのものの妥当性。下記）
   - `code-review`（実装の品質。下記）
4. 3種の結果が揃ってから採否を判断し、**採る指摘をまとめて1回の差し戻しにする**。1件ずつ直列に返すと、修正のたびに他2つの PASS が無効になり（「レビューの反復」の不変条件）、周回だけが増える。差し戻し依頼文は「差し戻し」節の4項目を満たす
5. 修正後は**機械的チェックを回し直したうえで、3種とも新しいスレッドで再実行する**。指摘が無くなるまで繰り返し、上限は3周（「レビューの反復」）
6. 3種とも指摘が無くなったらそのタスクのペインを閉じる。worktree は成果物の確定を終えるまで残す（ループを抜けたときに返すため）

#### 機械的チェック（頭脳が自分で実行する）

**判定が機械的に決まるものを委任しない。** 委任すると結果が Codex の自己申告として返り、生の出力ではなくなる（Phase 3 冒頭で戒めている形そのものである）。同じ入力に同じ結果を返す検査は、頭脳が自分で走らせて生の出力を見る。これは絶対規律の例外ではなく、Bash の許された用途（検収＝検査コマンドの実行）そのものである。

対象は次の3つで、worktree（`--cwd` 相当のパス）で実行する。コマンドはプロジェクトの `package.json` / `Cargo.toml` / CLAUDE.md から決める（Phase 0 で読み取った規約に含まれる）。

- lint / format check
- 型検査
- テスト実行。**このとき JSON レポートを出力させる**（`--reporter=json`、nextest の libtest JSON など）。`test-review` の計測入力になる

**1つでも落ちていれば、3種のレビューを発注しない。** 落ちたツリーに対する検収と、そこで得たカバレッジ・不安定さの計測値は、いま守れている範囲を表さない（`test-review` 自身も `failing_test` を打ち切り条件にしている）。落ちた出力をそのまま差し戻す。

**テストの計測値は頭脳の実行結果を正とする。** 実装者が出したレポートを `test-review` の入力にしない。検証される側が自分の計測値を作る構図になる。

**実行できなかった場合は「未実行」と記録する。** 依存の取得や環境構築が要るなら、サンドボックス外の操作として頭脳が代行する（「却下した操作は頭脳が代行する」）。代行が拒否されたらループを抜ける。**未実行を PASS と読み替えない。**

#### `verify-task` へ渡すもの

機械的チェックの結果（コマンドと合否、失敗時の該当行）を依頼文に貼り、**再実行させない**。`verify-task` に残すのは3軸の列挙と突合（指示突合・挙動の保存・検証の保存）である。判断が要る部分に集中させる。

`verify-task` は Jev API を呼ぶため、`delegate-to-codex` で Codex を起動するときは `-c sandbox_workspace_write.network_access=true` を追加する。作業ディレクトリは worktree 直下の `.claude/verify-task/` なので `-s read-only` は付けず、依頼文で書き込み範囲をそこに縛る。

**命題は Phase 1 でタスク定義の完了条件から書いてある。** 依頼文には「`.claude/verify-task/propositions.json` の命題をそのまま使い、命題を導かない・書き換えない」と書く。差し戻し後の再実行でも作り直させない。周ごとに命題が変わると、前の周に無かった命題で FAIL が出て収束しない。

**中断時も片付ける。** ワークフローがエラーで止まったとき、ループを抜けるときも、走っていないペインは閉じる。片付けを「完了時にやること」にすると、完了しなかった場合に誰も片付けない。ただしループを抜けるときは worktree とブランチを残す（「ループを抜けるとき」）。

#### テストの妥当性検証（`test-review`）

`verify-task` が見るのは「指示どおり完了しているか」であって、**テストが正しいものを検証しているかではない**。テストファーストは依頼文で従わせる規律にすぎず、規律が守られたことの証明にはならない。テストが空検証・モック偏重・無効化のまま緑になっていても、`verify-task` は PASS を返しうる。機械的に検出できる欠陥は検出を前提とする、というのがここでの根拠である。

**実装した Codex とは別のスレッド**を立て、`delegate-to-codex` 経由で `test-review`（`/Users/cancer/.claude/skills/test-review/skill.md`）を実行させる。

- **`-s read-only` を付けない。** このスキルは機械検出スクリプト3本を走らせ、結果を対象リポジトリ直下の `.claude/test-review/*.json` へ書く。read-only で発注すると手順1で止まる。代わりに依頼文で書き込み範囲を縛る: **出力してよいのは `.claude/test-review/` 配下の JSON のみで、レビュー対象のコード・テストを変更してはならない**（スキル側の禁止事項と一致する）
- `--cwd` をそのタスクの worktree へ向ける
- `--base` を明示する（worktree の分岐元）。省略時の推定は worktree では作業ブランチを指さないことがある
- 実装委任で取得させたテストランナーの JSON レポートがあれば `--test-json` / `--nextest-json` などで渡す。渡さない項目は `not_measured` として返るので、**「未計測」を「問題なし」と読み替えない**
- `--implementer` は渡さない。SendMessage は Codex から使えないため機能しない。実装者への問い合わせは下記の中継で行う

#### 未解決の質問の中継

`test-review` の成果物は結論ではなく**根拠付きのレビュー候補**であり、根拠が足りないものは「未解決の質問」として返る。**質問を受け取ったまま終えない。** 実装時の判断はそのスレッドのコンテキストにしか無いので、頭脳が中継する。

1. 質問（`Q1` 等の ID 付き）を実装スレッドへ `agent prompt` で送る。**当時の判断を問う情報質問として送り、修正を依頼しない。** 修正が返ると `test-review` は再評価を reject する（回答ではなく修正だから）
2. 回答を同じ ID の形式でファイルへ書く
3. `--answers <path>` `--previous <前回結果>` `--use-cache` を付けて `test-review` を再実行させる。全体をやり直させない
4. 実装スレッドが答えを持たない場合、それは「記録が残っていない」という確定した事実である。推測で埋めない

**この中継のために、実装スレッドのペインは `test-review` が終わるまで閉じない。**

#### 指摘の採否

`test-review` は対応内容を書かない（意図的に、手段は実装者が導く領域だから）。**どの指摘を差し戻すかは頭脳が判断する。** 判断の材料は指摘に付いた 根拠 / 影響 / 確信度 / 区分 の4項目である。差し戻すと決めたら「差し戻し」節の4項目を依頼文に書き、新しいスレッドへ送り、修正後に `test-review` を再実行させる（「レビューの反復」）。**再実行時は `--answers` / `--use-cache` を付けない。** コードが変わっているため再評価モードは成立せず、スキル側も修正を回答として受け取ることを reject する。採らなかった指摘は理由とともに完了報告へ残す。

#### 実装品質の検証（`code-review`）

`verify-task` は「指示どおり完了しているか」、`test-review` は「テストが正しいものを検証しているか」を見る。**どちらも実装そのものの品質は見ない。** 指示を満たし、テストも妥当なまま、設計・命名・重複・境界の扱いが悪いコードは通る。

**実装した Codex とは別のスレッド**を立て、`delegate-to-codex` 経由で `code-review`（`/Users/cancer/.claude/skills/code-review/skill.md`）を実行させる。

- 対象は**そのタスク単体の diff**（worktree の作業ブランチ vs 分岐元）。`--base` に相当する分岐元を依頼文で明示する
- `-s read-only` で発注する。`--cwd` をそのタスクの worktree へ向ける
- 依頼文にスキルの絶対パスと、タスクのゴール・制約・触ってはいけない範囲を書く（レビュアーは会話を見ていない）
- 指摘の採否は頭脳が判断する。採らない指摘の扱いは「指摘が矛盾する場合」の「決定後の扱い」に従う

### Phase 4: 成果物の確定

Phase 3 の検収を通ったら（effort low では実装報告を受けたら）、タスク定義のそのタスクの成果物の命題 `pN_deliverable` に従って成果物を確定する。

- 成果物が PR: `/Users/cancer/.claude/skills/create-pr/SKILL.md` に従って PR を作る（push を含む。頭脳が行う）。続けて `/Users/cancer/.claude/skills/watch-ci/SKILL.md` に従って CI を待ち、報告（チェック名・種別・原因・ログ抜粋）を受け取る。CI が失敗したら、その報告を指摘として新しいスレッドへ差し戻し、修正後に Phase 3 の検収（機械的チェックは頭脳が自分で、選んだ軸のレビューは新しいスレッドで）をやり直してから CI を待ち直す。この周回は「上限は3周」に数える
- 成果物がコミット: 検収を通ったツリーがタスクのブランチにコミットされていることを確かめて終える（PR は作らない）
- effort low（PoC）: 成果物の命題を持たないので、PR もコミットも作らず、実測の生の出力を回収する

成果物の命題は、頭脳が機械的に確かめる。PR なら `gh pr view <PR> --json state,mergeable,headRefName,baseRefName` と watch-ci の報告（全チェック成功）で、ブランチ・base・競合なし・CI 成功を確かめる。コミットならタスクのブランチの `git log` で確かめる。判定が機械的に決まるので委任しない（「機械的チェック（頭脳が自分で実行する）」と同じ理由）。

再開: 同じタスクのブランチや PR が既にあれば（成果物の命題のブランチ名で特定する）、それを引き継ぐ。完了条件のうち既に真のものはやり直さず、偽のもの（base との競合、CI の失敗を含む）だけを、差し戻しのループで満たす。base と競合していれば、競合を指摘として差し戻し、解消後に Phase 3 の検収をやり直す。

### Phase 5: 完了

本ワークフローは成果物の確定と完了報告で終わる。

1. Codex ペインと worktree を片付ける。**個別検収（3種のレビューの指摘対応まで）を終えたタスクのペインは、Phase 5 を待たずその時点で閉じる。** 最後にまとめて片付ける運用にすると、ワークフローが途中で終わったときに全部残る
2. watchdog の Monitor を `TaskStop` で止める
3. 呼び出し側に完了報告する（下記「成果物」）

## 承認を求められたとき

`agent_status` が `blocked` になったら、`herdr agent read <名前> --source detection` で何を聞かれているかを読む。**画面を見ずにキーを送らない。**

- **通常の確認ダイアログ**（ディレクトリの信頼、更新の可否、上書きの確認など）は、選択肢を読んだうえで意図する番号を明示して送る。`herdr pane send-text <pane_id> '<番号>'` のあとに `send-keys <pane_id> enter`。**素の `enter` を単独で送らない。** 既定の選択が意図と違う場合があり、実測では更新プロンプトで `enter` を送って `brew upgrade` が走った
- **サンドボックス外へ出る操作の要求は却下する**（`herdr agent send-keys <名前> esc`）。却下した直後は Codex が指示待ちで `blocked` のままなので、通常の `agent prompt` を送れば `idle` に戻る

### 却下した操作は頭脳が代行する

Codex にサンドボックス外の権限を渡さない。代わりに、**その操作だけを頭脳が自分の手で実行し、結果を依頼文で Codex へ返す。** サンドボックス外の操作は、原則としてすべて頭脳が代行する。

- 外部ネットワークを要する取得（依存の取り寄せ、API の応答確認）→ 頭脳が実行し、得られた事実を依頼文へ貼る
- 作業ツリーの外への書き込み → 頭脳が実行する。Codex には作業ツリー内の作業だけを残す

**代行そのものが権限設定・classifier に拒否された場合だけ、ループを抜ける。** 拒否を迂回する手段を探さない。

代行した内容は完了報告に含める。**Codex の成果として報告しない。** 誰がどこまでやったかが混ざると、検収の対象が曖昧になる。

ペイン経路を選んでいる理由がここにもある。何が要求されたかが画面に残るので、代行の記録と突き合わせられる。

## 無応答の検知

`delegate-to-codex` は `agent prompt --wait` で完了を待つため、通常は状態遷移で完了が分かる。ポーリングは不要である。ただし次の場合に沈黙と停止を区別できない。

- 実装を伴う委任は20分を超えることがあり、Bash ツールの上限は10分である。**長い委任は `run_in_background: true` で投げ、完了通知を受けてから読む**
- herdr 側の状態が失われた、ペインを閉じた、`--wait` のタイムアウトが実作業より短かった

### watchdog

Phase 2 で全タスクを発注した直後に、`Monitor` を `persistent: true` で1つだけ張る。Codex は自分の実行ログを `~/.codex/sessions/<年>/<月>/<日>/rollout-<時刻>-<UUID>.jsonl` へ追記し続けるので、**その mtime の停滞が「何も出していない時間」**を表す。

```bash
THRESHOLD=600        # 秒。長い調査中も追記は続くが、テスト実行中は止まることがある
reported=" "
while true; do
  sleep 60
  now=$(date +%s)
  for u in <発注ごとのセッションUUIDを空白区切りでここに直接展開する>; do
    case "$reported" in *" $u "*) continue ;; esac
    f=$(ls -t ~/.codex/sessions/*/*/*/rollout-*-"$u".jsonl 2>/dev/null | head -1)
    if [ -z "$f" ]; then echo "NOLOG $u"; reported="$reported$u "; continue; fi
    age=$(( now - $(stat -f %m "$f") ))
    if [ "$age" -ge "$THRESHOLD" ]; then echo "STALE $u ${age}s"; reported="$reported$u "; fi
  done
done
```

- **UUID はスクリプト本文に直接列挙する**。シェルは zsh であり、未クォート変数は単語分割されない。`IDS` 変数に入れて `for u in $IDS` と書くとループが1回しか回らない
- **`ls -t | head -1` で最新のログを拾わない**。別のタスクや他のリポジトリで走っている Codex のログを掴む。必ず UUID でファイルを特定する
- `STALE` は「死亡」ではなく「確認せよ」の信号である。受け取ったら、対応する発注のペインを `agent get` と `agent read --source visible` で確認する
- `NOLOG` はそのスレッドを watchdog で見張れないことを意味する。**沈黙を成功と解釈せず**、ペインの直接確認のみで追う旨をユーザーへ報告する
- **この Monitor に渡すのは上記の生存確認スクリプトのみ**。実装・調査・git 操作にシェルを使ってはならない

### セッション UUID の取得

`herdr agent get` は `agent_session` を返さない（`herdr integration status` が `codex: not installed` の状態）。UUID が要るなら `herdr integration install codex` を入れるか、rollout ログのファイル名を起動時刻で絞って拾う。watchdog を使うなら前者を先に済ませる方が確実である。

### 待ちに入る時点での確認

watchdog は一度報告したスレッドを再報告しないため、待ちの入口を取りこぼしの受け皿にする。次の時点で、未完了の発注それぞれについて `agent get` の状態とペインの画面を確認する。

- 全タスクを発注し終え、報告を待つ状態に入るとき
- ある発注の報告を処理し終え、未報告の発注が残っているとき
- Phase 3 で差し戻し、修正報告を待つとき

確認できた事実だけを報告する。エージェント名 / 担当タスク / `agent_status` / 画面から読み取れる状態 / 取った処置。未確定のものは未確定と書く。進捗や成果を推測で埋めてはならない。

## 成果物（完了報告）

- 実施作業の要約と、受け取った effort
- effort low では、そのタスクの実測の生の出力（加工・要約・合否判定をしない）
- 回さなかった軸（effort low ならすべて、effort mid なら `code-review`）と、effort mid で落とした重要度 low の指摘
- 各委任の担当と成果、使ったモデルと推論量
- 機械的チェックの結果（実行したコマンドと合否。実行できなかったものは「未実行」と明記）
- 各委任の `verify-task` 結果（PASS/FAIL 履歴）と反復した周回数
- 各委任の `test-review` 結果（反復した周回数、採った指摘と対応、採らなかった指摘とその理由、未解決のまま残った質問、未計測の範囲）
- 各委任の `code-review` 結果（反復した周回数、採った指摘と対応、採らなかった指摘とその理由）
- watch-ci の結果（CI の成否と、失敗時の差し戻しの周回）
- 指摘の矛盾を検知した場合は、矛盾した指摘の組と決定・その根拠
- 成果物（PR の URL、またはブランチ名とコミット。effort low なら実測の生の出力）
- 頭脳が代行したサンドボックス外の操作があればその内容

ループを抜けた場合は、完了報告ではなく「ループを抜けるとき」の報告を返す。

## 報告の事実性

- 報告に含める原因・理由は、実際に検証された事実・プロジェクトで既知の事実・公式ドキュメント等ソースを提示できるものに限る
- 「おそらく」「〜と思われる」等の推測を確認済み事実であるかのように報告しない
- Codex からの報告を中継する際は、差分で照合したかどうかを明記する。照合していないなら未確認と書く

## 注意事項

- 頭脳自身はコードを書かない。すべて委任する
- Codex に守らせたい前提（変更範囲、抽象化の扱い、テストの書き方）は理由を添えて依頼文へ織り込む。禁止事項を積み上げるより意図を渡す
- ユーザーが明示的に許可しない限り、コミット・push・デプロイを Codex に指示しない
- 指示された内容と反する判断が必要になったら、ループを抜けて呼び出し側へ返す
