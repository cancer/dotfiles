アプリのコンセプトをユーザーと決め、リポジトリ直下の `CONCEPT.md` に定義・維持する。コンセプトを決めるのはユーザーであり、こちらは質問と根拠のある推奨で判断を助ける。未決事項を仮置きして決定済みのように書かない。

## 引数

$ARGUMENTS

## モードの判定

`git rev-parse --show-toplevel` で対象リポジトリのルートを調べ、その直下に `CONCEPT.md` があるか確認する。無ければ新規作成モード、あれば照合モードで進める。

README や既存コードなど、リポジトリ内の事実は自分で調べる。ユーザーに確認するのは事実ではなく、コンセプト上の判断である。

## CONCEPT.md の形式

次の見出し構成を固定で使う。

```markdown
# <アプリ名> コンセプト

## 誰に

## 何を

## 目的

## すること

## しないこと
```

- 「誰に」は届ける相手、「何を」は届ける価値、「目的」はなぜそれを届けるかを書く。
- 「すること」と「しないこと」は箇条書きにする。「しないこと」の各項目には `理由:` を必ず付ける。理由が無い除外は、後の仕様変更で根拠なく覆されるためである。
- 技術スタック、画面構成、実装手段は書かない。これらはコンセプトとは由来が異なり、実装判断が変わるたびにコンセプトまで揺れて見えるためである。
- 変更履歴の節は作らない。経緯は git の履歴に任せる。

## 新規作成モード

決定は上流から一問ずつ進める。順序は「誰に」→「目的」→「何を」→「すること」→「しないこと」とし、前提が未決の問いを先に出さない。答えを受け取ってから次の一問を選ぶ。一度に複数の質問をまとめず、未回答の項目を仮置きで埋めない。

各質問は次の形式で出す。推奨には根拠と懸念を添える。根拠を示せない場合は推奨を書かず、その旨を明示する。

```text
❓ **<質問の見出し>**: <質問の本文。選択肢を並べてよい>

➡️ **推奨**: <こちらの推奨する答え>
   **根拠**: <コードベース内の参照、公式ドキュメント、issue・PR・仕様書、調査結果、ユーザーの発言など>
   **懸念**: <推奨を採ったときの最大の懸念、または棄却条件>
```

質問は「誰に」から始め、決まった回答を次の判断の前提にする。コンセプト上の「すること」と「しないこと」を決めた後、アプリ名が未確定なら一問で確認する。名前や価値判断もこちらで補わない。

全節が決まったら、上記の見出し構成に沿った `CONCEPT.md` の全文を提示する。ユーザーが内容を承認してから、リポジトリ直下へ書き込む。

## 照合モード

変更要求を `CONCEPT.md` の「誰に」「何を」「目的」「すること」「しないこと」と照合する。食い違う箇所があれば、変更要求と該当する行の引用を並べてユーザーに示す。

照合に必要な情報が足りず判定できない場合は、根拠のある質問を一問ずつ行い、回答を受けてから照合する。

食い違いが無い場合は「コンセプト変更は不要」と報告して終える。ファイルは変更しない。

食い違いがある場合は、ユーザーに (a) 変更要求を取り下げる・修正する、(b) コンセプトを改訂する、のどちらかを選んでもらう。(a) で要求を修正した場合は、修正後の要求を再照合し、食い違いが解消したことを確認してから呼び出し元へ返す。決着するまで呼び出し元の作業へ進まない。

(b) なら、影響する節だけを改訂し、他の節に波及しないか確認する。改訂後の差分を提示し、承認を得てから書き込む。「しないこと」から項目を外すときは、元の理由がなぜ成り立たなくなったかをユーザーに確認する。

照合結果と決着内容（要求の取り下げ・修正、または改訂した節と内容）を呼び出し元へ返す。呼び出し元はその結果を受けて元の作業へ戻る。

## 完了条件

新規作成では、`CONCEPT.md` の6見出しがすべて埋まり、「しないこと」の各項目に理由があり、ユーザーが内容を承認していること。照合モードで変更不要の場合は、その報告をもって完了とする。

## 対象外

- 実装の依頼を作業に渡す場合は、会話で内容を固めた後に judge-request が作業可否を判定し、ready なら run-implement が進める。タスク分割は define-tasks が担う。
- 仕様書の点検は `spec-review` の領分である。
- コンセプト以外の題材を扱う壁打ちは `kabeuchi` の領分である。
