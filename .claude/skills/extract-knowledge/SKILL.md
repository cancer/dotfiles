# セッションからのユーザー知識の抽出

このスキルの仕事は **knowledge の抽出**。セッションログから、ユーザー自身が持つ再利用可能な普遍的知識を抽出して `/Users/cancer/repos/knowledge`（ユーザーの知識ベース）に集約する。目的は、ユーザー（や将来のチーム）が再導出・再発見せずに済み、今後の業務を速くすること。

## 何が knowledge か（抽出する／しないの線引き）

**knowledge＝抽出対象：** ユーザー自身が持つ、プロジェクトに依存しない技術・設計・工学の知識と洞察。読み手（本人・チーム）がそれ自体から学べる、**宣言的な事実・理解**。
- 例（宣言形で書く）：
  - 「シーケンス図の『依頼・要求』は外部システムとのやり取りを表す語であり、内部ドメインはそれに当たらない」
  - 「ユースケースのアクターはそのUCが誰のためかで決まる。UC 内で満たす前提（ログイン）はアクターの属性ではない」
  - 「設計と文書は意図の層で不可分である」

**knowledge ではない＝このスキルは扱わない：**
- **Claude への指示・矯正**（「Claude は〜せよ」と読めるもの。例：コストより正しさを優先せよ／重複は文言レベルで判定せよ／自律的に動け）。これは AI 行動メモリ＝memory の領分。
- **命令・規約にしかならないもの**（説明可能な知識が背後に無く「〜せよ／〜するな／〜で統一」としか言えないもの。例：「箇条書きは正常系→異常系の順で統一」）。これは指示・取り決めであって知識ではない。
- **プロジェクト固有の事実**（そのドメイン/リポジトリでしか成り立たない購読モデル・spec の意味・repo 規約）。プロジェクト側に属す。knowledge リポジトリはポータブルな普遍知識だけを集める。

**knowledge は memory ではない。** memory（プロジェクト固有・Claude 指示）の保存・ルーティングはこのスキルの管轄外。該当しないものは抽出しない（行き先を世話しない）。

判別テスト（両方を満たすものだけ抽出）：
1. **声**：「**X とは〜である／〜のとき〜になる。なぜなら〜**」と**宣言形**で言えるか。「〜せよ／〜するな」としか言えないなら指示・規約であって知識ではない。元が矯正・命令でも、背後に説明可能な知識があれば宣言形に言い換えて採る（言い換えられないなら捨てる）。
2. **射程**：他者が学べ、プロジェクトをまたいで持ち出せる、ユーザー自身の知識か。「Claude への指示」「特定プロジェクト依存」は no。

## 引数
$ARGUMENTS

- **第1引数（対象）**: `2026-06-23`（その日、JST 0:00〜23:59）/ `7d` `2w`（直近期間）。省略時 `1d`。
- **第2引数（スコープ）**: パッケージ/プロジェクトのパス（そのパス配下＋worktree のセッションに限定）。`--all` で全プロジェクト横断。省略時は現在のプロジェクト＋その worktree。

## 原則

1. **根拠は逐語引用必須。** 各候補にユーザー発言の verbatim 引用 + timestamp を添える（根拠なき候補は捨てる）。
2. **重複判定は文言レベル。** knowledge リポジトリの索引・一行要約だけで「既出」と判断しない。**既存エントリ本文を実際に Read** して照合する（「雰囲気カバー」「示唆されている」は判定ではない）。
3. **深さで採る。薄いものから捻り出さない。** 採否は「再利用可能な知識・洞察を含むか」で決める。手順書・runbook に落ちる情報は採らない。トラブルシューティングは knowledge に昇華できる場合のみ。設定手順・単純な作業ログしかないセッションは「該当なし」と正直に報告し、1事例を無理に一般化しない。
4. **抽出が成果物、保存は履行。** まず抽出結果を報告し、照合を生き残ったものだけを保存する。ファイルの乱造を license にしない。
5. **プライバシー。** セッションログはユーザーのプライベートデータ。外部送信は絶対にしない。

## 実行手順

### Step 1: 対象セッションの特定

セッションログは `~/.claude/projects/<cwd をダッシュ連結したディレクトリ>/<uuid>.jsonl`。**1つの論理パッケージが複数ディレクトリに分散する**：本体ディレクトリ、サブディレクトリ cwd の派生、worktree 版とそのサブ。スコープ指定時はデコードしたパスが対象パッケージの配下または worktree であるディレクトリを**すべて**列挙する（worktree を取りこぼさない）。

```bash
ls -d ~/.claude/projects/*packages-docs* 2>/dev/null   # 例: docs パッケージ＋worktree
```

**日付は JST で判定（timestamp は UTC）。** JST の 1 日は UTC `前日T15:00`〜`当日T14:59`。各 jsonl の対象窓内エントリ数を数えて活動セッションを拾う。各候補の全 timestamp 範囲も確認し、**日付をまたぐセッションは活動の主体がどちらの日かで帰属を判断する**（末尾だけが対象日にかかるものは前日扱いにし、その旨を報告に明記。黙って落とさない）。

### Step 2: セッションごとの候補抽出（subagent に委譲）

セッションは大きい。**1セッション = 1 subagent**（`Agent`, `subagent_type: "general-purpose"`）で並列に読ませる（独立作業なので1メッセージ内で同時起動）。各 subagent への指示：

- ユーザー発言を**全件**読む（`jq` で時系列抽出してから精読）。
- **抽出対象＝ユーザーの普遍知識：** (a) ユーザーが述べた技術・設計の知識、(b) ユーザーが下した設計・技術判断の背後にある知識・理由、(c) 議論・考察・深い洞察（最も価値が高い。積極採用）。
- **宣言形テストを必ず適用：** 各候補を「**X とは〜である／なぜなら〜**」と宣言形で書けるか確かめ、書けるなら**宣言形に言い換えて**出す。「〜せよ／〜するな／〜で統一」としか言えないものは指示・規約なので捨てる。元発言が矯正・命令でも、背後の知識を宣言形で取り出す。
- **除外（抽出しない）：** Claude への指示・矯正（「Claude は〜せよ」）、命令・規約にしかならないもの、プロジェクト固有の事実、手順書・runbook、コード/git から自明な事実、Claude が自発的に出した提案。
- 議論の途中で覆った見解は**最終的に確定したものだけ**を採る。
- 出力は候補ごとに【一行要約 / **宣言形の知識本文** / 逐語引用+timestamp（出典）/ 主題（ジャンルの当たり）】。

ユーザー発言の抽出（subagent 内）：

```bash
jq -r 'select(.type=="user") | .message.content | if type=="string" then . elif type=="array" then (map(select(.type=="text").text)|join("\n")) else "" end' "$f"
```

### Step 3: 中央での重複排除（skill 本体が実行・委譲しない）

subagent の全候補を集約し、**自分で**照合する（subagent は互いの結果も既存エントリも知らない）。

1. knowledge リポジトリの索引/既存エントリで重複の当たりを付ける。
2. 重なりそうな**既存エントリ本文を実際に Read** する。
3. 各候補を本文と文言レベルで照合し、3 分類：
   - **新規** … 既存のどの本文ともずれている → 新規作成。
   - **既存を鋭利化** … 同主題だが新しい例・区別・反例を足せる → 既存を **in-place 更新**（近似重複の新ファイルを作らない）。
   - **カバー済み** … 本文に既出 → 捨てる（報告には残す）。
4. 並行編集の可能性があるので、保存直前に索引を読み直す。

### Step 4: knowledge リポジトリへの保存

保存先：`/Users/cancer/repos/knowledge`（「知見バンドル OKF v0.1」）。

**フォーマットを推測でハードコードしない。リポジトリ自身の規約に従う：**

1. repo の **README / フォーマット仕様（OKF）/ 既存エントリ / `.textlintrc.json`** を Read し、frontmatter・配置・ジャンル命名の規約を把握する。既存エントリがあれば倣う。
2. **声は「ユーザーの知識記事」。** 「Claude はこう適用せよ（How to apply）」の枠は使わない。「**X とは〜である。〜のとき〜する。なぜなら〜**」という、本人・チームがそのまま読んで使える宣言的な知識として書く。逐語引用は出典として残す。
3. **ジャンルは主題（subject）で決める。** リポジトリ全体が知見なので `documentation` 等「形式・役割」の名前は使わない（同語反復）。技術・設計の知識は設計主題のジャンル（例：`design`）へ。
4. 該当ジャンルや規約が**未整備なら自動生成せず、命名・配置をユーザーに確認**する。仕様が判別できない（README も既存例もなく OKF の形が不明）なら、**書き込まず仕様を確認**する。推測で独自形式のファイルを置かない。
5. プロジェクト固有の例しか根拠がない知識を出すときは、知識を一般化し、固有例は「例：」として添える（裸のプロジェクト依存記述を残さない）。
6. 書き込み後 `npm run lint:fix`（textlint）を repo で実行する。索引ファイルがあれば規約どおり追記する。

### Step 5: 報告

セッション 1 つずつのテーマと、各候補の処遇（新規/鋭利化/カバー済み）を表で報告する。最後に「新規 N 件・鋭利化 M 件」のサマリ。ジャンル/仕様の確認待ちで保留した候補、並行プロセスの先行保存があれば明記する。

## 注意事項

- 感情・評価を含めない。知識と洞察のみ。
- 既存エントリが誤りだと判明した場合は報告し、ユーザー確認の上で訂正・削除する（勝手に消さない）。
- 「knowledge か（Claude 指示・プロジェクト固有ではないか）」の判定に迷えば、推測で決めずユーザーに確認する。
- knowledge リポジトリの規約・ジャンルが不明/未整備なら、推測で独自形式のファイルを置かず確認する（CLAUDE.md「根拠を示せないなら判断を保留」）。
