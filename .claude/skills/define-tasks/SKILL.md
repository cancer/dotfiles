judge-request が ready と判定した State を入力に取り、作業係（サブエージェント。Claude Code の Plan サブエージェントとして実行される想定）が従うタスク定義を作成する。コードベースと関連資料を調査して分割し、タスク定義ファイルを出力する。要件や前提が決着していない場合は、推測で埋めずに companion へ差し戻す。

## 引数

`$ARGUMENTS` に指定するのは、judge-request が作成した `state.txt` の絶対パスである。GitHub issue URL、issue 番号、仕様書パス、自由記述は入力として受け付けない。

State から、要求、受け取りたい成果物の形、制約、完了条件に必要な情報を読む。State を読めない場合は「不明点」として「companion への差し戻し形式」に従って返し、聞くべき項目に有効な State ファイルの絶対パスを記す。

## 実行手順

### Step 1: 関連資料と実装を調べる

リポジトリの `CLAUDE.md` に記載された調査方針に従い、State の要求に関係する以下の情報源を確認する。

- コードベースと既存のテスト
- 仕様書、ADR、アーキテクチャ文書
- リポジトリ直下に `CONCEPT.md` があれば、その内容

調査で確認できた根拠をタスクの対象・完了条件・契約に反映する。調べれば分かる事項は、資料やコードを読んで確定させる。

`CONCEPT.md` と要求が食い違う場合、または適合するか判定できない場合は「不明点」として差し戻す。`app-concept` は呼び出さない。

### Step 2: 不明点を判定する

要求や根拠に不明点があり、複数の解釈でタスクの対象・完了条件・成果物が変わる場合は、タスク定義を作らず「companion への差し戻し形式」に従って返す。不明点ごとに、companion が尋ねるべき項目を具体的に記す。

根拠のない推測で不明点を埋めてはならない。不明点を解消するために必要な情報が State に足りない場合も同様に差し戻す。

### Step 3: 実測が要る仮定を判定する

タスク定義が次のいずれかの仮定に依存する場合は、タスク定義を作らず「companion への差し戻し形式」に従って返す。

- 公式ドキュメントで決まらない挙動
- 実行環境で成立するか未確認の技術
- 計測しないと判定できない性能要件
- 実測値でしか選べない設計案

「調べれば分かる」事項は実測が要る仮定に含めない。資料やコードを調べて決着させ、タスク定義に反映する。

差し戻しでは、仮定ごとに「仮定の内容」「決め手となる 1 点（何を実測すれば決まるか）」「合否の条件（成立・不成立を二値で判定できる形）」を記す。該当する不明点と仮定が両方ある場合は、種別ごとに分けて併記する。どちらの場合も `tasks.md` は作成しない。

### Step 4: タスクを分割する

不明点と実測が要る仮定が残っていない場合に限り、`task-format.md` の形式でタスク定義を作る。形式の詳細は `/Users/cancer/.claude/skills/run-implement/references/task-format.md` を参照し、このスキル内に形式本文を複製しない。

分割時は次の規則を守る。

- 各タスクの完了条件は、成否を二値で判定できる命題にする。
- タスク間の依存は記載せず、境界を契約で表す。契約で境界を作れないタスクは 1 つにまとめる。
- タスクごとの「対象」に列挙するファイルを、タスク同士で重ねない。対象ファイルが重なるタスクは 1 つにまとめる。
- State の「受け取りたい成果物の形」を各タスクに反映し、各タスクの完了条件に成果物の命題 `pN_deliverable` を 1 行含める。PR の場合は「<ブランチ> から <base> への PR が作成され、base と競合せず、CI が通っている」、コミットの場合は「<ブランチ> にコミットされている」とする。
- State の受け取りたい成果物の形をタスクの成果物の命題に定められない場合は「不明点」として差し戻す。

### Step 5: タスク定義を出力する

完成したタスク定義を、State と同じディレクトリに `tasks.md` として書き出す。タスク定義は `task-format.md` の形式に従い、調査根拠と食い違わないことを確認する。

## companion への差し戻し形式

タスク定義を作れない場合は `tasks.md` を作成せず、次の形式で companion に返す。

```markdown
## 差し戻し

### 不明点
- 種別: 不明点
- 聞くべき項目:
  - <companion が尋ねる項目>

### 実測が要る仮定
- 種別: 実測が要る仮定
- 仮定:
  - 仮定の内容: <仮定>
    - 決め手となる 1 点: <確認・計測すること>
    - 合否の条件: <二値で判定できる条件>
```

該当する種別だけを残す。複数の項目がある場合は、項目ごとに列挙する。

## 他スキルとの境界

- `kabeuchi` は、未決定の構想・方針・判断を対話で決めるためのスキルである。define-tasks は ready の State をタスクに分割し、未決事項は「companion への差し戻し形式」に従って返す。
- `app-concept` は `CONCEPT.md` を作成・改訂するためのスキルである。define-tasks は `CONCEPT.md` を調査対象として読み、矛盾や判定不能を「companion への差し戻し形式」に従って返す。

## 完了前チェックリスト

タスク定義を出力する前に、次を確認する。不明点または実測が要る仮定が残っていれば、タスク定義ではなく「companion への差し戻し形式」に従って返す。

- [ ] 入力が judge-request の `state.txt` の絶対パスであり、要求と受け取りたい成果物の形を State から読んだ
- [ ] コードベース、関連する仕様書・ADR、および存在する `CONCEPT.md` を調査した
- [ ] 各タスクに対象・二値判定可能な完了条件・契約がある
- [ ] タスク間の依存を書かず、契約で境界を作れないタスクをまとめた
- [ ] タスク間で対象ファイルが重ならず、重なるタスクをまとめた
- [ ] 各タスクの完了条件に、State の成果物の形を反映した `pN_deliverable` が 1 行ある
- [ ] `task-format.md` の形式に従い、State と同じディレクトリの `tasks.md` に出力した
