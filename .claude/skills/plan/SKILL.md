要求を分析し、コードベースを調査して、実装計画書を作成してください。計画書を作るだけで、実行はしません。計画書はそのまま dev-workflow の入力になります。

## 引数
$ARGUMENTS

## 引数の形式

以下のいずれかの形式で要求を受け付けます：

1. **GitHub issue URL**: `https://github.com/owner/repo/issues/123`
2. **issue番号**: `#123` または `123`（現在のリポジトリのissueとして扱う）
3. **仕様書のパス**: プロジェクト内のファイルパス
4. **自由記述**: やりたいことの説明

## 実行手順

### Step 1: 要求の情報収集

引数の形式に応じて情報を収集する。

**GitHub issueの場合:**
```bash
gh issue view <number> --repo <owner/repo> --json number,title,body,labels,assignees,comments
```
issue本文に加え、コメント欄にも要件や補足がないか確認する。

**仕様書パスの場合:**
指定されたファイルを読み込む。

**自由記述の場合:**
そのまま要求として扱う。

### Step 2: 仕様書・ADRの確認

CLAUDE.mdにドキュメント関連の指示がある場合はそれに従い、関連する仕様書やADR（Architecture Decision Records）を確認する。

1. プロジェクト内で仕様書・ADR・アーキテクチャドキュメントを検索する
2. 関連ドキュメントが見つかった場合は内容を読み込み、計画に反映する

- リポジトリ直下に `CONCEPT.md` があれば読み、要求を「誰に／何を／目的／すること／しないこと」と照合する。
- 食い違う、または判定できない場合は `app-concept` を呼び、取り下げまたは改訂が決着するまで計画を進めない。
- `CONCEPT.md` が無ければこの手順を飛ばす。

### Step 3: 既存コードベースの調査

要求に関連する既存コードを調査し、以下を把握する：

- 既存の実装パターン・コードスタイル
- 変更が必要なファイルの特定
- 既存のテストパターン
- 依存関係・影響範囲

### Step 4: 不明点の確認

要求に曖昧な点や、複数の解釈が可能な点がある場合は、ユーザーに確認する。確認せずに推測で進めない。

### Step 5: 実測が要る仮定の判定

計画が次のいずれかの仮定に依存する場合は、計画書を作らずに呼び出し側へ差し戻す。dev-workflow はループの中で人に諮らないため、実測で覆りうる仮定を抱えた計画を渡すと、ループの途中で前提が崩れて全タスクがやり直しになるからである。

- 公式ドキュメントで決まらない挙動
- 実行環境で成立するか未確認の技術
- 計測しないと判定できない性能要件
- 実測値でしか選べない設計案

「調べれば分かる」仮定はここに含めない。ドキュメントやコードを調べて決着させ、計画に反映する。

差し戻すときは、仮定ごとに次を列挙する。呼び出し側はこれをもとに PoC を回し、決着後に plan を呼び直す。

- 仮定の内容
- 決め手となる 1 点（何を実測すれば決まるか）
- 合否の条件（成立・不成立を二値で判定できる形で）

### Step 6: 計画書の作成

以下のフォーマットで計画書を作成し、出力する。

---

## 計画書のフォーマット

```markdown
# 計画: <タイトル>

## Context
- 要求の背景と目的を簡潔に
- 関連する issue・仕様書・ADR への参照

## タスク

### T1: <タスク名>
- 対象: <変更・作成するファイル>
- 完了条件:
  - p1_<短い名前>: <命題を 1 文で>
  - p2_<短い名前>: <命題を 1 文で>
- 契約: 提供 C1 / 利用 なし

### T2: <タスク名>
- 対象: ...
- 完了条件:
  - p1_<短い名前>: ...
- 契約: 提供 なし / 利用 C1

## 契約

### C1: <契約名>
- 提供: T1 / 利用: T2
- 内容: <型・関数シグネチャ・API のパスと入出力・スキーマ・イベント・エラー種別・命名>

## 検証方法
- 実行すべきテスト・検証コマンド
- 手動確認が必要な項目
```

- 完了条件の各行は、verify-task の `propositions.json` の `statement` にそのまま写せる命題で書く。dev-workflow はこれを写して検収するため、成否を二値で判定できない文は検収に使えない
- タスク間の依存は書かない。依存は契約で切り、全タスクを並列に回せるようにする。契約で切れない組は 1 つのタスクにまとめる。dev-workflow は依存を判断しないためである

## 完了前チェックリスト

計画書を出力する前に、次を満たすことを確認する。文脈を持たない実装者がそのまま着手できる粒度が目標。

- [ ] 各タスクに対象と完了条件があり、完了条件は二値で判定できる命題になっている
- [ ] タスクをまたぐ境界はすべて契約で覆われ、各タスクの提供・利用が契約セクションと一致している
- [ ] タスク間に依存が無い（契約で切れない組は 1 タスクにまとめた）
- [ ] 実測が要る仮定が残っていない（残っていれば Step 5 で差し戻している）
- [ ] 検証方法（テスト・確認コマンド）が具体的に書かれている
- [ ] 曖昧点はユーザーに確認済み

## 注意事項

- 計画書を作成するだけで、コードの変更は一切行わない
- 不明点がある場合は推測せずユーザーに確認する
- 既存のコードベースのパターンを十分に調査したうえで計画を立てる
