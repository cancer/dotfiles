herdr のペインで Codex を動かし、1 件のタスクを委任して報告を回収する。

この経路を使う理由は、Codex の動作がユーザーに見え、承認を求められてもユーザーが押して復旧でき、差し戻しが同じスレッドで続くことにある。`codex exec` のような非対話経路へ退避すると、この 3 つがすべて失われる。

## 引数

$ARGUMENTS

- **依頼内容**: Codex に何をさせるか（必須）
- **`--model <ID>` / `--effort <推論量>`**: 呼び出し側が段を指定する場合。未指定なら `references/model-routing.md` に従って自分で選ぶ
- **`--read-only`**: 調査・レビューだけで書き込みが不要な場合
- **`--cwd <パス>`**: 作業ディレクトリ。未指定なら現在のディレクトリ

## 責務の境界

**このスキルが担うのは委任の実行だけである。** 成果物の検収（`git diff` の確認、テストが変更を検証しているかの判定）、差し戻し、PR 作成、issue 操作は行わない。回収した報告と識別子を呼び出し側へ返して終わる。

Codex の報告は自己申告であり、ペインに見えているのは Codex が描いた画面であってコマンドの生出力ではない（Codex はツール出力を `… +464 lines` のように畳む）。**報告を成果の証明として扱わない。** 呼び出し側が差分で検収する前提で返す。

## 前提の確認

herdr のペイン内にいることが唯一の前提である。

```bash
test "${HERDR_ENV:-}" = 1
```

**偽なら委任しない。** 別経路へ退避せず、「この委任経路は herdr のペインだけなので、herdr 内で実行してほしい」と伝えて止まる。ここで自分が作業を肩代わりすると、ユーザーが期待した「別モデルに任せる」が消える。ユーザーが自分でやれと指示したなら、このスキルを離れて通常の作業として扱う。

## 手順

### 1. 段を決める

`--model` / `--effort` が渡されていればそれを使う。渡されていなければ `references/model-routing.md` を読んで決める。既定は `gpt-5.6-luna` + `high`。

選んだモデル・推論量・その理由の 3 点を、発注前にユーザーへ 1〜2 行で伝える。委任先の選択はユーザーが是正できる唯一のタイミングなので、事後報告にしない。

### 2. 依頼文をファイルへ書く

**Write ツールでファイルへ書いてから渡す。ヒアドキュメントも直接埋め込みも使わない。** 依頼文中のバックティックがシェルのコマンド置換として実行され、その部分が依頼文から欠落したまま Codex へ渡る（実運用で `` `wrangler dev` `` が起動して残り、仕様の核が欠けた依頼文が渡った事例がある）。加えて、サンドボックスや権限に触れる文言を含むヒアドキュメントは Claude Code の classifier に止められることがある。

依頼文は単体で完結させる。Codex は呼び出し側の会話を見ていないので、前提・対象ファイル・完了条件・触ってはいけない範囲を本文に書き切る。確かめていない事実は書かない（誤った前提は Codex がそのまま採用する）。

**作業の副産物をどう扱うかを依頼文に書く。** 依存のインストール、ビルド成果物、ロックファイル、キャッシュなど、頼んだ作業の実行に伴って出るものを許すのか、消して戻すのか、判断を委ねるのかを明示する。書かないと Codex は自分が作った副産物を「指示外の変更」と見なし、それが依頼前から在ったのか自分が作ったのかの調査と後片付けに時間を使う。実測では、テスト1ファイルの作成を頼んだ委任が25分かかり、そのうち大半が `npm install` で生成された `node_modules/` と `package-lock.json` の素性調査と削除だった（2026-08-12）。成果物そのものは数分で出ている。

範囲を狭く書くほどこれは起きやすい。「出力先は1ファイルのみ」と書いたうえで検証のために依存インストールが要る依頼は、その2つが依頼文の中で矛盾している。テストの実行まで求めるなら「実行に必要な依存のインストールは許可する。生成された `node_modules/` と lockfile は成果物に含めない」のように、許す副産物を名指しする。

**終端マーカーを依頼文に入れない。** 完了の検知は herdr の `--wait` が状態として返すので二重になるうえ、報告の読み取りは常に下端が基準で、失われるのは先頭である。機械的に印を付けたいなら報告の**先頭**へ置く。

### 3. ペインを用意する

```bash
herdr pane split --current --direction right --cwd "$PWD" --no-focus
```

右分割を既定にする。分割直後のペインはまだシェルプロンプトに達していないことがあり、その状態で次の `agent start` を叩くと `agent_pane_busy`（`is not an available shell`）で失敗する（2026-08-12 実測）。失敗したら 2 秒ほど空けて数回まで再試行する。ペインは作られているので、`pane split` からやり直さない。分割後の幅が 80 桁を下回るなら `--direction down` へ切り替える（80 桁は Codex の TUI が崩れない実測下限）。

2 つ目以降のエージェントは、右へ割り続けず**最初のエージェントペインを下へ分割して積む**（`--pane <最初のpane_id> --direction down`）。呼び出し側のペイン幅を削らずに済む。

### 4. Codex を起動する

```bash
herdr agent start <名前> --kind codex --pane <pane_id> --timeout 60000 \
  -- --model <モデルID> -c model_reasoning_effort=<推論量> \
     -c service_tier=<luna なら priority / sol なら default> --no-alt-screen
```

`--` 以降は Codex のネイティブ引数としてそのまま渡る。

- **`--no-alt-screen` を必ず付ける。** Codex の TUI をインラインで描くので出力がスクロールバックに残り、報告を回収できる。付けないと `agent read --source recent` が終了コード 0 で 0 行を返し、報告の先頭は `--lines` を増やしても戻らない（2026-08-12 実測）。
- ファイル変更に追加フラグは要らない（`workspace-write` が既定）。調査だけなら `-s read-only` を付ける。
- ループバックへの listen を伴う検証（開発サーバーの起動など）を頼むなら `-c sandbox_workspace_write.network_access=true` を足す。要らない発注には付けない。
- 承認方針は既定（`on-request`）のまま起動する。`-a untrusted` は `ls` や `find` まで承認へ上げるので、そのペインで作業が進まなくなる。

**起動後、発注前に画面を確認する。**

```bash
herdr agent read <名前> --source visible
```

**起動直後の確認は `visible` を使う。** `--no-alt-screen` を付けていても、起動直後はまだスクロールバックへ流れていないので `recent-unwrapped` は 0 行を返す（2026-08-12 実測）。`recent-unwrapped` は報告の回収（手順 6）で使う。

`agent start` は Codex の更新プロンプト（`1. Update now / 2. Skip / 3. Skip until next version`）が出ている状態でも `idle` かつ `interactive_ready: true` を返す（2026-08-12 実測）。そのまま発注すると依頼文が選択肢の入力として食われる。

**この画面で素の `enter` を送らない。** 既定の選択は `1. Update now` なので、`brew upgrade --cask codex` が走り、Codex が入れ替わって起動し直しになる（2026-08-12 に実際に発生させた）。抜けるなら選択肢を読み、Skip に当たる番号を明示して送る。

```bash
herdr pane send-text <pane_id> '2'
herdr pane send-keys <pane_id> enter
```

ユーザーの環境を更新するかどうかは委任の判断ではないので、勝手に更新しない。

### 5. 発注して待つ

```bash
herdr agent prompt <名前> "$(cat <依頼文のパス>)" --wait --timeout 1800000
```

`agent get` を自分でポーリングしない。`--wait` が返した `agent_status` で分岐する。

- `idle` / `done`: 区別せず完了として扱い、報告の回収へ進む
- `blocked`: 下記「承認を求められたとき」へ

読み取りだけの小さな依頼で 12〜40 秒、実装を伴う依頼は 20 分を超えることがある。**Bash ツールの上限は 10 分なので、実装の委任は `run_in_background: true` で投げ、完了通知を受けてから読む。**

待っている間に同じ作業ツリーを触らない。**書き込みを伴う委任を、同一の作業ツリーで並列に走らせない。** ペインを分けても作業ツリーは共有されるので、ペインの分離は並列化の根拠にならない。並列に書かせるなら別の worktree を用意して `--cwd` をそちらへ向ける。`-s read-only` の調査委任どうしは同じツリーで並走してよい。

ファイルが未変更でも失敗と判断しない。Codex は数分から十数分を調査に使ってから書き始める。

### 6. 報告を回収する

```bash
herdr agent read <名前> --source recent-unwrapped --lines 600
```

`recent-unwrapped` はソフトラップを繋ぎ直すので、ペイン幅は精度に影響しない。

### 7. 片付けて返す

セッション UUID を控えておくと、ペインを閉じたあとでも `herdr agent start <名前> --kind codex --pane <新pane_id> -- resume <UUID> …` で同じスレッドへ戻れる（素の shell で `codex resume` を叩かない。herdr がエージェントとして認識せず、以後 `agent prompt` も `blocked` の検知も効かなくなる）。

ただし **`herdr agent get` は `agent_session` を返さない**（`herdr integration status` が `codex: not installed` の状態、2026-08-12 実測）。UUID が要るなら `herdr integration install codex` を入れるか、`~/.codex/sessions/<年>/<月>/<日>/rollout-<時刻>-<UUID>.jsonl` のファイル名から起動時刻で絞って拾う。`ls -t | head -1` で最新を拾うと別タスクの Codex を掴むので、時刻で照合する。

**報告を回収したら、自分が作ったペインを閉じる。** `herdr pane close <pane_id>`。自分が作ったペインだけを閉じる。

```bash
herdr pane close <pane_id>
```

閉じるのが既定である。「差し戻すかもしれない」は残す理由にならない。差し戻しは常に起こりうるので、それを条件にすると全てのペインが残り、画面が使い物にならなくなる。UUID を控えてあれば `-- resume <UUID>` で同じスレッドへ戻れるので、残しておく利点は「1回の起動を省ける」だけである。

残してよいのは、**呼び出し側がその場で差し戻す**と決めている場合に限る（検収の結果を待っている、修正指示を出す直前）。その場合も、返すときに「ペインを残した」と明示し、閉じる責任が呼び出し側へ移ったことを伝える。

委任が失敗したとき、中断したとき、途中でユーザーに判断を仰いで作業が止まったときも、ペインは閉じる。**成功した場合だけ片付ける、にしない。**

## 承認を求められたとき

`blocked` が返ったら、`herdr agent read <名前> --source detection` で何を聞かれているかを読む。

**画面を見ずにキーを送らない。** 何を聞かれているかで対応が分かれる。

- **通常の確認ダイアログ**（ディレクトリの信頼、更新の可否、上書きの確認など）は、選択肢を読んだうえで意図する番号を明示して送る。`herdr pane send-text <pane_id> '<番号>'` のあとに `send-keys <pane_id> enter`。**素の `enter` を単独で送らない**（既定の選択が意図と違うことがある。手順 4 の実測を参照）
- **サンドボックス外への権限昇格の承認**は代行しない。Claude Code の classifier が代理入力を止めるうえ、昇格の是非はユーザーの判断である。何を求められているかを伝えて待つ

却下は通る（`herdr agent send-keys <名前> esc`）。却下した直後は Codex が指示待ちで `blocked` のままなので、通常の `agent prompt` を送れば `idle` に戻る。

この経路を選んだ理由がここにもある。ペインはユーザーの画面に見えているので、判断が要る場面をユーザーが直接処理できる。

## 呼び出し側へ返すもの

回収した報告に加えて、次を必ず添える。検収と差し戻しは呼び出し側が行うので、その材料が要る。

- エージェント名 / pane_id / セッション UUID（ペインを残したか閉じたかも）
- 使ったモデルと推論量、`-s read-only` などのフラグ
- Codex の報告（要約せずに渡すか、要約するなら要約であると明示する）
- 未確認事項: 報告の内容を差分で照合していないこと

## 適用範囲外

- **Claude 自身のサブエージェントで足りる作業**: 別モデルに出す理由がないなら `Agent` ツールを使う。このスキルはペインでの可視性と承認の復旧が要る場面、または明示的に Codex を指名された場面のための経路である
- **検収・差し戻し・PR 作成**: 呼び出し側（`dev-workflow` など）の責務
- **herdr のペイン外**: 委任経路が無いので実行しない
